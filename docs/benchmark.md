# 检索性能基准

> 本文是 roadmap **M2 验收标准 ①**（「10 万 chunk 规模下混合检索 P95 实测」）的实测记录。
> 载体是 `tools/bench-search.mjs` —— 里面的每一个数字都能被**重跑复现**，
> 也能在下次改动后**看出回归**。没有这个脚本，"实测"就只能靠嘴说。

---

## 0. 口径说明（**先读这段，否则下面的数字会被误读**）

| 项 | 事实 |
|---|---|
| 语料 | **合成**中文文本（32 个主题 × 200 篇文档 × 5 段 × 约 145 字），不是真实企业资料 |
| 向量 | **确定性伪随机**造的（主题方向 + 噪声），不是真实 embedding |
| 查询向量 | 由一个**本机 stub 服务**返回（真 HTTP 往返，约 1 ms 量级），不是真实模型服务 |
| 它回答的问题 | 「**这个规模下，这一层要花多少时间**」 |
| 它**不**回答 | 「接上你的真实模型有多快」—— 真实模型延迟取决于服务商，不取决于本脚本 |

**所以**：文本检索与向量扫描这两条线是**本仓库的真实开销**（CPU / 磁盘 / SQLite 决定，与应用无关）；
服务层混合检索那条线**额外包含一次本机 stub 往返**，接真实模型时要把这一段换成真实的网络 + 推理延迟。

---

## 1. 怎么复现

```bash
node tools/bench-search.mjs --json > bench.txt    # 默认就是 10 万 chunk / 256 维 / 每查询 40 次（前 10 次预热丢弃）
```

常用参数：

```bash
node tools/bench-search.mjs --chunks=200000 --dim=768
node tools/bench-search.mjs --no-embed            # 只测两路检索器，不起 stub embedding
node tools/bench-search.mjs --repeats=60          # 增大样本量
```

脚本自带临时数据目录、临时端口，**不碰你真实的 `data/`**；末行输出 `DONE fails=N`
（`N` 是**基准断言**不达标的条数，不是用例数）。零第三方依赖。

| 空间 | 30 | `fts:phrase` | 346.92 ms | 375.90 ms |

| **全部（330 样本）** | — | — | **364.64 ms** | **430.11 ms** |

按档位汇总：

| 档位 | 样本 | P50 | P95 |
|---|---|---|---|
| `fts:phrase`（保序精确） | 300 | 364.48 ms | 427.98 ms |
| `fts:or`（换序宽松） | 30 | 364.97 ms | 446.73 ms |

**怎么读这组数字**：

- **常见词（数千命中）** P95 ≈ **430 ms**。这是「命中集很大、要吐 5000 行再排序」的成本 —— 与命中数成正比，与库总量**无关**。
- **稀有词** P95 ≈ **0.9 ms**，比常见词快 **约 480 倍**。这两个数是同一张表、同一条 SQL，差别只在命中集大小 ——
  **这正是「查询计划没退化成全库扫描」的证据**（退化了的话两者会一样慢，见 §6）。
- 换序查询（「管理权限」）走 `or` 档，**仍然命中 30 条**。这是刻意的：`AND` 档在换序时会 **0 命中**
  ——因为「管理权限」切出的 bigram「理权」在原词「权限管理」里根本不存在。

## 4. ② 向量检索 `searchVector`（暴力扫描 100,000 × 256 维）

| 查询 | 扫描行数 | P50 | P95 |
|---|---|---|---|
| 空间参考系 | 100,000 | 969.10 ms | 1216.01 ms |
| 数据治理 | 100,000 | 934.01 ms | 1142.65 ms |
| 权限管理 | 100,000 | 930.98 ms | 1101.87 ms |
| 精度说明 | 100,000 | 923.69 ms | 1088.32 ms |
| 管理权限 | 100,000 | 1117.62 ms | 1337.29 ms |
| 数据 | 100,000 | 958.76 ms | 1668.01 ms |
| 权限 | 100,000 | 936.93 ms | 1149.16 ms |
| 精度 | 100,000 | 1016.98 ms | 1329.51 ms |
| 空间 | 100,000 | 934.50 ms | 1171.28 ms |
| 奇特点编号A00 | 100,000 | 934.63 ms | 1099.03 ms |
| 奇特点编号A07 | 100,000 | 935.29 ms | 1154.56 ms |
| **全部（330 样本）** | 100,000 | **950.03 ms** | **1231.25 ms** |

**怎么读**：

- 每个查询都**扫满 100,000 行** —— 这是暴力扫描的**定义**，与查询内容无关。
  所以「稀有词」在这里**不会变快**（0.93 s vs 常见词 0.95 s，噪声级差异）。
- **≈ 0.95 s / 10 万 × 256 维** 是这台 CPU 的**扫描下限**：一趟要把每一行的向量 BLOB 读出来做点积。
- **规模外推**（线性）：20 万 → ≈ 1.9 s；50 万 → ≈ 4.8 s；100 万 → ≈ 9.5 s。
  **这就是 `VectorIndex` 抽象预留的原因**（抽象落在 `retrievers/index.mjs` 的 `createVectorIndex()`，
  换 ANN 不改 service 调用方），也是 roadmap 风险表里「暴力向量检索在百万级失效」那条的实测依据。
- 真实模型接进来后：**向量这一路的耗时主要取决于扫描（本仓库），而不是 embedding（服务商）** ——
  因为一次查询只需要 **1** 次 embedding，却要扫 **10 万** 行。

| 查询 | 返回 | P50 | P95 | 内部 fts | 内部向量 |
|---|---|---|---|---|---|
| 空间参考系 | 10 | 1648.78 ms | 2107.27 ms | 496 ms | 1328 ms |
| 数据治理 | 10 | 1808.09 ms | 2057.24 ms | 439 ms | 991 ms |
| 权限管理 | 10 | 1587.59 ms | 2026.16 ms | 389 ms | 1025 ms |
| 精度说明 | 10 | 1380.79 ms | 1818.98 ms | 330 ms | 928 ms |
| 管理权限 | 10 | 1191.97 ms | 1646.91 ms | 313 ms | 853 ms |
| 数据 | 10 | 1246.54 ms | 1629.26 ms | 447 ms | 1181 ms |
| 权限 | 10 | 1173.71 ms | 1524.18 ms | 288 ms | 852 ms |
| 精度 | 10 | 1233.32 ms | 1761.03 ms | 287 ms | 882 ms |
| 空间 | 10 | 1388.63 ms | 1651.19 ms | 340 ms | 958 ms |
| 奇特点编号A00 | 10 | 975.98 ms | 1101.66 ms | **1 ms** | 1100 ms |
| 奇特点编号A07 | 10 | 1093.50 ms | 1133.85 ms | **2 ms** | 1092 ms |
| **全部（330 样本）** | 10 | **1274.98 ms** | **1930.82 ms** | — | — |

**怎么读**：

- **瓶颈完全是向量那一路**。稀有词那两行最直观：FTS 只花 **1 ms**，但混合检索仍然要 **1101 ms** ——
  因为混合是「两路都跑完再融合」，快的那一路**不会**让整条链变快。
- P95 **1930 ms ≈ 2 s**：这是「10 万 chunk + 暴力向量 + 这台 15W CPU」的真实成本。
- **可以立刻改善的两条路**（其中 ② 已落地）：
  1. 配一个**真实**的向量服务（本机 stub 段只是 1 ms，不是瓶颈，换掉它改善有限）；
  2. 给 `VectorIndex` 做**预过滤** —— ✅ **已落地**（配置项 `prefilterVector`，**默认关**）。
     它不是"纯优化"：会改变最终答案，所以默认关、且代价必须被量出来 ——
     延迟与**召回损失**的实测对照见 **§9**；
  3. 上**近似索引**（HNSW / IVF），或换掉 `node:sqlite` —— 都属 M5 之后的事。

## 6. ④ 正确性抽检与算法回归守卫

**为什么要有这一段**：性能数字**光快没有意义** —— 空转最快。
这一段专门防「快来自没做对的事」。

| # | 断言 | 实测 |
|---|---|---|
| 1 | 稀有词 `奇特点编号A00` 必须排第 1（FTS） | ✅ 模式 `fts:phrase`｜命中 1 |
| 2 | 稀有词 `奇特点编号A07` 必须排第 1（FTS） | ✅ 模式 `fts:phrase`｜命中 1 |
| 3 | **稀有词检索成本与库内总量无关**（< 50 ms） | ✅ P95 **0.91 ms** @ 100,000 chunk |
| 4 | 常见词（数千命中）P95 < 1500 ms | ✅ P95 **465.47 ms** |
| 5 | 稀有词的专属向量方向必须命中它自己 | ✅ top cosine **0.6796** |
| 6 | 服务层混合检索必须返回带引用链的结果 | ✅ RRF=0.0164｜引用 `基准文档 001.md › 基准文档 › 基准章节 0` |
| 7 | **大规模**下跨租户 FTS 仍然 0 命中 | ✅ 命中 **0** |
| 8 | **大规模**下跨租户向量仍然 0 命中 | ✅ 命中 **0** |

**汇总：8 项全 ✓，`DONE fails=0`。**

第 3 条是**算法回归守卫**：如果哪天有人把 `fts.mjs` 里的 `CROSS JOIN` 改回普通 `JOIN`，
第 3 条会立刻从 0.91 ms 涨到几百毫秒然后报红 —— **把它写下来，就是为了让退化在当天被发现，而不是等到线上**。
第 7、8 条是 **M2 验收标准 ③**（越权检索两条路径都测）在大规模语料上的复验。

## 7. 顺带修掉的两个真实性能缺陷

跑基准之前，这两个缺陷**都看不出来** —— 功能全对、结果全对，只是慢，而且慢得不明显。

### 7.1 FTS 查询计划退化为全库扫描

**现象**：命中集的大小**不影响**耗时 —— 常见词和稀有词一样慢。

**原因**：`FROM chunk_fts JOIN chunks c ON c.id = chunk_fts.rowid` 被 SQLite 重排成
「先按 `kb_id` 走 `idx_chunks_kb` 扫出**库内全部 chunk**，再逐条回查 FTS 虚拟表」：

```
SEARCH c USING INDEX idx_chunks_kb      ← 先扫全库
SCAN chunk_fts VIRTUAL TABLE INDEX 0:=M2 ← 再逐条回查
```

代价 **O(库内分块总数)**，与查询无关。

**修法**：改成 `CROSS JOIN`，强制 MATCH 驱动：

```
SCAN chunk_fts VIRTUAL TABLE INDEX 0:M2      ← 先走 MATCH
SEARCH c USING INTEGER PRIMARY KEY (rowid=?) ← 再按主键回填
```

**实测（2 万 chunk）**：

| 查询 | 修前 | 修后 | 提升 |
|---|---|---|---|
| 常见词（数千命中） | 1150 ms | **17 ms** | **68×** |
| 罕见词（1 命中） | 299 ms | **0.32 ms** | **900×** |

> `app/platform/knowledge/retrievers/fts.mjs` 里留了长注释说明这段为什么必须是 `CROSS JOIN` ——
> 谁把它「整理」回普通 `JOIN`，`bench-search.mjs` 的第 3 条断言会立刻红。

### 7.2 向量扫描白读了 (N − K) 行的正文

**现象**：一趟扫描要把范围内**每一行**的整条记录都读出来，但最后只留 top-K（K=10）。
99990 行的 `body`、`meta_json`、标题全是**白读**的。

**修法**：**两步法** —— 第一趟只取窄投影（`chunk_id + dim + vec`），算出 top-K 后再按主键回填正文。

**实测（2 万 chunk）**：

| 阶段 | 修前 | 修后 |
|---|---|---|
| 扫描趟（宽查 vs 窄投影） | 53.8 ms | **21.5 ms** |
| 端到端 | 158 ms | **137 ms** |

> 第二趟是 K 次主键点查（K=10），成本可忽略；
> 随着 `body` 变长（真实文档比合成语料长得多），这个收益会**更大**。

## 8. 结论：规模边界写在明处

| 规模（chunk × 256 维） | FTS 常见词 P95 | 向量暴力扫描 P95 | 混合检索 P95 |
|---|---|---|---|
| **100,000（本次实测）** | **430 ms** | **1231 ms** | **1931 ms** |

按线性外推（向量那一路线性、FTS 那一路基本持平）：

| 规模 | 向量扫描 P95（外推） | 判断 |
|---|---|---|
| 10 万 | ≈ 1.2 s | ✅ 可用（本次实测） |
| 20 万 | ≈ 2.4 s | ⚠️ 开始影响体验 |
| 50 万 | ≈ 6 s | ❌ 需要预过滤（**已提供，默认关**，见 §9）或近似索引 |
| 100 万 | ≈ 12 s | ❌ 必须换索引方案 |

**这条边界不藏在代码里，写在这里**，并且在运行时也会提示：
`vector.mjs` 在扫描量超过 `BIG_SCAN = 50000` 时会返回 `notes` 说明「当前是暴力扫描、规模已偏大」。

> roadmap 风险表里「暴力向量检索在百万级失效 / 对策：`VectorIndex` 抽象预留（装配点见 `retrievers/index.mjs`）+ 文档写明 10 万量级边界」
> —— 本文就是那条「写明边界」的落点。

## 9. ⑤ 向量预过滤对照（B2）：延迟与**召回损失**一起量

体检报告 B2 的处置是「先预过滤（用文本命中缩候选）再算余弦」，并明确要求**能证伪**。
这一节就是那个证伪器 —— **同一批查询跑两次**（`prefilter:false` 全量精确 vs `true` 预过滤），
同时量**延迟**与**召回**。

> ⚠️ **只报"快了几倍"而不报"丢了什么"，是做了一半。**
> 所以下面这张表**必须整行读**，尤其是"结果重合"那一列 —— 它才是这个功能真正的价格标签。

### 9.1 实测（10 万 chunk × 256 维；11 查询 × 3 次取分位；2026-10-02 批次）

| 查询 | 形态 | 扫描（全量 → 预过滤） | **结果重合** | 延迟 P95（全量 → 预过滤） |
|---|---|---|---|---|
| 空间参考系 | long | 100,000 → **512** | 4/10 | 1302 → **733 ms** |
| 数据治理 | long | 100,000 → **512** | 4/10 | 1341 → **742 ms** |
| 权限管理 | long | 100,000 → **512** | 3/10 | 1299 → **713 ms** |
| 精度说明 | long | 100,000 → **512** | 4/10 | 1298 → **742 ms** |
| 管理权限 | long | 100,000 → **512** | 3/10 | 1249 → **663 ms** |
| 数据 | short | 100,000 → **512** | 2/10 | 1290 → **727 ms** |
| 权限 | short | 100,000 → **512** | 1/10 | 1280 → **626 ms** |
| 精度 | short | 100,000 → **512** | 3/10 | 1246 → **629 ms** |
| 空间 | short | 100,000 → **512** | 4/10 | 1219 → **665 ms** |
| 奇特点编号A00 | needle | 100,000 → 100,000 | **10/10** | 949 → 943 ms |
| 奇特点编号A07 | needle | 100,000 → 100,000 | **10/10** | 954 → 922 ms |

**汇总**：

| 指标 | 读数 |
|---|---|
| 生效查询 | **9 / 11**（两条稀有词查询按设计**退化**） |
| 延迟（生效查询的平均 P95） | **1280 → 693 ms（快约 1.85 倍）** |
| 召回（全部查询合计） | **保留 48/110 条**（丢 62 条）—— 最终 top-10 只有 **4 成左右**与全量精确一致 |

> 交叉参考：本批次的混合检索 P95 是 **1649 ms**，而 §8 那一批是 **1931 ms**。
> 两批差的那 ~15% 是同一台 15W 笔记本 CPU 的**批次间抖动**（该批 `--repeats=40`，本批 `--repeats=15`），
> 不是代码变了 —— 读数时请把两批的**内部对比**（同一批内 prefilter on/off）当作结论，
> 跨批次的绝对值只作量级参考。

### 9.2 怎么读（这段决定你要不要开它）

**① 收益是实的，且随规模放大。** 向量扫描从 10 万条降到 512 条；规模越大，
省下的绝对时间越多（向量那一路是**线性**的，候选量却是**常数**）。

**② 代价也是实的，而且不小 —— 但必须分清"机制"与"真实召回损失"。**

本语料的向量是**伪随机方向**（按主题 + 噪声合成），字体命中集与向量近邻集本就几乎不重叠。
所以「重合 4/10」说明的是**机制**：预过滤**会换掉相当一部分结果**，而不是
"真实语料下也只留 4 成" —— 真实语料里"字面命中"与"语义相关"的相关性高得多。
**但反过来说：本仓库手上没有任何真实语料下的召回实测，所以谁也不能保证真实场景下损失有多小。**
这正是它**默认关**的原因，而不是"文档里补一句小心使用"就完了。

**③ 安全阀按设计生效（这条比收益更重要）。** 两条稀有词查询的候选只有 1 条，
低于阈值（`max(32, limit*3)`）→ **自动退化为全量扫描**，扫描量仍是 100,000，
且结果与基线 **10/10 完全一致**。也就是说：

> 预过滤**只对"文本命中足够多"的查询生效**；字面 0 命中或极少的查询（纯语义、精确查找）
> 自动回到**召回无损**的那条路，只是没变快。**没有任何查询会因为开了它而静默返回空结果。**

**④ 结论：默认关（`prefilterVector: false`）。** 判断依据：

| 场景 | 建议 |
|---|---|
| 库 > 10 万 chunk，且查询以**字面词**为主 | 开（收益随规模放大；接受 top-K 会变） |
| 召回质量优先 / 查询常靠语义命中 | **关** |
| 拿不准 | 用知识库页检索区的**三态开关**做 A/B，看自己语料上的重合度 |

### 9.3 断言（计入 `DONE fails`，与 §6 同级）

| # | 断言 | 实测 | 它防的是 |
|---|---|---|---|
| 9 | 预过滤至少对一个查询生效 | ✅ 9/11 | "全是退化"= 这个功能**根本没被触发**，等于白做却看起来已完成 |
| 10 | 生效时扫描量必须小于全量 | ✅ 100,000 → 512 | 它退化成"装饰"（配了开关但没真的缩范围） |
| 11 | 字面 0 命中必须退化为全量扫描，且向量路径不被饿死 | ✅ `reason=too_few_candidates`｜仍扫描 100,000 条｜返回 10 条 | **整套预过滤里最容易静默失效的地方** —— 纯语义查询拿到空候选集后静默返回空结果 |

## 10. 别把这些数字读成什么

- ❌ **不是「生产 QPS 上限」**。全部是**单请求串行**测量，没有并发。
  并发下的表现取决于 SQLite 单写与 CPU 核数 —— 那一路**已经单独测了**，
  见 [`benchmark-concurrency.md`](benchmark-concurrency.md)（`tools/bench-concurrency.mjs`）。
- ❌ **不是「真实语料的速度」**。合成语料每块约 145 字；真实文档的块更长 → 向量扫描更快（BLOB 大小不变，但 FTS 取正文更慢）。
- ❌ **不是「语义质量」**。向量是伪随机的，第 5 条断言只验证「**机制通了**」（专属方向能命中自己），
  不验证「搜得准不准」—— 那是真实模型 + 真实语料下的评估，不在本脚本职责内。
- ✅ **是**「**这一层代码在 10 万规模下要花多少时间**」的、可重跑的、有断言守卫的真实数字。
