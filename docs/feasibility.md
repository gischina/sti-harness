# 可行性与风险评估

> 本文回答四个问题：**规划可行吗 / 能落地吗 / 作为企业级平台够用吗 / 还漏了什么**，
> 并专章分析 **DSH 上游升级的影响面** 与 **安装·部署·集成·打包方案**。
>
> 体例：所有结论必须有依据。**已实测的标「实测」，推断的标「推断」，未验证的标「待验证」。**

---

## 0. 结论摘要

三条判断，先给结论再给证据：

**判断一：技术前提成立，但「零依赖」的可行性在三个点上被打折，必须显式接受代价。**
数据层与鉴权层的能力已经实测通过（见 §1.1）。但有三个原本被乐观假设的环节经检验需要修正：
中文全文检索（§1.2.1，**实测证伪**）、高频写入下的并发模型（§1.2.2）、
模型层的事前治理能力（§1.2.3）。修正后方案仍成立，但不能假装它们不存在。

**判断二：架构方向正确，但「四项能力塞进一个大版本」偏激进，建议重切里程碑。**
契约优先 + DSH 隔离这套纪律是本项目相对 dsh-console 的最大增量，方向没问题。
问题在排期：首期同时落地身份、知识、治理、能力分发，四项都是「大」级规模，
且 M2 内部还压着三级解析链路与混合检索。**建议把首个对外可用版本定在 M0–M3**（一个能登录、
能查企业资料、能审计、能授权的平台），M4/M5 作为第二个版本。理由见 §2.3。

**判断三：作为「企业级 Agent 生产平台」，首期是必要地基，但还不是完整平台。**
对照企业级平台应有的 34 项能力，首期覆盖约 19 项、部分覆盖 7 项、**明确缺失 8 项**
（会话协作、定时任务、通知集成、内容安全、模型网关、可观测性、行级权限、SSO 实装）。
另有一个**硬天花板**：单进程 + SQLite 单写者，决定了适用规模上限（§3.3）。
**这不是缺陷，是定位**——但必须写进对外承诺，否则会在真实客户处翻车。

| 你问的问题 | 直接回答 |
|---|---|
| 整体规划可行性 | **成立**。技术前提已实测；架构纪律正确；但三个假设需修正（§1.2） |
| 是否能落地 | **能**。技术风险可控；真实风险在**规模与排期**，不在可行性（§2） |
| 是否够用 | **分场景**。部门级内网单点够用；集团级/高并发/SaaS 多租户不够用（§3） |
| 是否还有遗漏 | **有 8 项能力缺口 + 4 项工程遗漏**（§4） |
| DSH 升级影响 | **可控，预计小时~天级**，前提是守住三条加固措施（§6） |
| 安装部署集成打包 | 沿用 dsh-console 的 `dist.cmd` 体系并增强；**但安全模型必须分叉**（§7） |

## 1. 整体规划可行性

### 1.1 已验证成立的前提（实测）

全部在本机实测通过，无需任何第三方包：

| 前提 | 方案 | 实测结论 |
|---|---|---|
| 业务数据库 | `node:sqlite` `DatabaseSync` | ✓ Node 22.22 / 24.10 均可用（SQLite 3.50.4） |
| 全文检索 | FTS5 虚拟表 | ✓ 可创建；`trigram` tokenizer 亦可用 |
| 向量存储 | `Float32Array` → BLOB | ✓ 往返一致（3×float32 = 12 字节校验通过） |
| JSON / WAL | json1 / WAL | ✓ 可用 |
| 口令 | `crypto.scryptSync` + `timingSafeEqual` | ✓ 内置 |
| 令牌 | HMAC-SHA256 + `randomUUID` | ✓ 内置 |
| 凭据加密 | AES-256-GCM | ✓ 内置 |
| 后台任务 | `worker_threads` | ✓ 内置 |
| 回归测试 | `node:test` | ✓ 内置 |
| 实时流 | 自研 WS 字节管道桥 | ✓ dsh-console 已有可复用实现 |

**结论**：数据层、鉴权层、任务层、测试层四项基础设施都不需要引入依赖，零依赖路线在**这四层**成立。

### 1.2 三个需要修正的假设（这部分是本文最重要的内容）

#### 1.2.1 中文全文检索：架构文档写的 `unicode61` **实测不可用**

`docs/architecture.md` §6.3 原写「中文用 unicode61」。**实测证伪**，三组对照数据：

| tokenizer | 原文：`企业级智能体生产平台的权限管理` | 查询「权限管理」 | 查询「权限」 | 查询「管理」 | 前缀「企业*」 |
|---|---|---|---|---|---|
| **unicode61**（默认） | — | **0 命中** | **0 命中** | **0 命中** | 1 命中 |
| **trigram** | — | 1 命中 | **0 命中** | **0 命中** | 1 命中 |
| **自建 bigram + unicode61** | bigrams = `企业 业级 级智 … 权限 限管 管理` | **1 命中** | — | **1 命中** | 1 命中 |

原因（实测确认）：**unicode61 把一整段连续汉字当成「一个 token」**——CJK 字符在 unicode61 里被视为
alphanumeric，且汉字之间没有分隔符，于是「企业级智能体生产平台的权限管理」整体成为单个词条。
后果是：只有**整句精确匹配**或**前缀匹配**才命中，任意子串检索全部落空。
英文场景不受影响（靠空格切词，`permission` 正常命中）。

- **trigram** 是 SQLite 3.34+ 内置：对 **≥3 字**的中文查询可用，但**2 字词（「权限」「管理」「平台」
  这类极高频词）召回为 0**——因为 trigram 的最小匹配单元是 3 个字符。中文场景里 2 字词占比极高，
  这个缺陷是致命的。
- **自建 bigram 预处理**（把文本预切成重叠双字串，用空格分隔后交给 unicode61 索引）：
  **任意长度的中文查询都能召回**，零依赖、跨 SQLite 版本稳定（不依赖 3.34+ 的新 tokenizer）。
  代价：索引体积膨胀（约 2 倍词条数）、查询需先做同样的 bigram 切分、
  且**「管理权限」这类换序查询会失败**（短语顺序敏感），需要退化为 bigram 的 `AND` 组合查询。

**修正方案（应写入架构文档）**：
采用 **bigram 预处理 + unicode61 索引** 作为中文主路径，并在检索层做：
1. 查询侧同样 bigram 切分，先按**短语**匹配（保序，精确）；
2. 短语 0 命中时退化为 **bigram AND 组合**（保召回，容忍换序）；
3. 单字查询（bigram 产不出）退化为 `LIKE` 前缀扫描（量小可接受）；
4. 英文/数字仍走 unicode61 原生路径（按空格切词），中英混排按字符类别分段处理。
5. **对外必须如实标注当前分词方案**——这延续「诚实数据源」原则，不假装是「智能分词」。

> **这条是本轮分析里最有价值的发现**：如果按原文档直接实现，知识库的中文检索会「看起来能建库、
> 实际搜不到东西」，而且失败得非常隐蔽（不报错、只是召回为 0）。必须现在改掉。

#### 1.2.2 并发模型：SQLite 是**单写者**，单进程是**单事件循环**

原文档把「单进程 + WAL」当作已解决并发。实际上有两个叠加约束（推断 + 部分实测）：

- **SQLite 写串行**：即使开了 WAL（WAL 只让「读」不等「写」），**写事务之间仍然串行**，
  同一时刻只有一个写者。本项目的高频写入点是 `events` 表——一轮对话会产生几十到上百条事件。
  多用户并发对话时，事件写入会互相排队。
- **单进程单事件循环**：CPU 密集任务（分块、向量化、bigram 预处理）已规划进 `worker_threads`，
  这部分没问题；但**数据库写入是主线程的**，无法并行。

**修正方案**：
1. **写合并（write coalescing）**：`events` 与 `usage_records` 不逐条 `INSERT`，
   改为在内存队列里按 **session 分批**、每 N 毫秒或每 M 条批量提交一个事务
   （`BEGIN … 多条 INSERT … COMMIT`）。实测基线：批量提交比逐条提交快一个量级（推断，需在 M1 实测）。
2. **事件表分区策略**：`events` 按 `session_id` 索引，历史会话事件可归档/分表，避免单表无限膨胀。
3. **明确写入配额**：单进程的写入吞吐上限要在文档里给出**实测数字**（不是「很快」），
   超限时在页面明确提示「当前部署已达写入上限」而非静默变慢。
4. **为多实例留路但不实现**：把「进程内状态」全部收口到 `db + 缓存接口`，
   将来换掉驱动（见 §1.2.5）就能多实例共享库。

#### 1.2.3 模型治理：没有 model gateway，就**只能事后统计，不能事前管控**

这是与 MOVO 的一处**实质性架构差异**，原文档没有点出：

- MOVO 的做法是**反向回调**：`chat-api` 暴露 `/internal/dsh/model/generate`，
  `dsh-runtime-host` 通过 MOVO 的 **model gateway** 回调——于是配额、限流、脱敏、审计
  **卡在模型调用这一层**，是**事前**的。
- 本项目原设计里，DSH 是独立进程、按自己的配置直连模型，平台**只能从事件流里读到 `usage`
  事件后统计**——是**事后**的。

后果：**配额只能「记账」不能「刹车」**。用户超了配额，平台能记下来、能告警，但**拦不住**
（除非平台有能力中断会话，那也只是事后中断，不是事前拒绝）。

**必须做决策**（见 §8 决策点 2），三选一：
- **A. 接受事后统计**：把配额定位为「计量 + 告警 + 事后阻断会话」，写进产品承诺。实现最简。
- **B. 引入 model gateway**：平台提供**协议兼容**的模型代理端点，
  **要求 DSH 把模型 base URL 指向平台**。这样配额能在调用前检查。
  这是对齐 MOVO 的做法，但多一层转发与一次上游依赖。
- **C. 混合**：默认事后统计；部署时若 DSH 可配置 base URL，则自动挂上 gateway 并升级为事前管控。

我建议 **C**，并在 M0 验证「DSH 是否支持自定义模型 base URL」这个前提。

#### 1.2.3.1 ✅ 前提验证结果：**DSH 支持自定义 base URL，决策点 2 选 B/C 成立**

**验证时间**：2026-09-30｜**验证对象**：本机安装的上游内核 `@deepseek-ai/dsh@0.2.0-rc.2`

**结论：支持，而且是官方明确设计意图，不是我们绕出来的。** 但**有 5 条硬约束**，
不写进方案就会变成「能配、配了不通」。

证据（`dsh-llm-deepseek` 包）：

```js
// lib/index.js:311 — baseURL 是一等配置项
const deepSeekConfigFields = { baseURL: z.string().volatile(), … }
// lib/index.js:336-339
const PUBLIC_BASE_URL = "https://api.deepseek.com/anthropic";
const BASE_URL_ENV = "DEEPSEEK_BASE_URL";
// lib/index.js:421 — 解析优先级：显式配置 > 环境变量 > 官方 root
const baseURL = config.baseURL ?? environment?.get(BASE_URL_ENV)?.value ?? "https://api.deepseek.com/anthropic";
// lib/index.js:423 — 校验：必须是裸 HTTP(S) root
if (!["http:","https:"].includes(parsed.protocol) || parsed.username || parsed.password
    || parsed.search || parsed.hash)
  throw new Error("llm-deepseek: Messages baseURL must be an HTTP(S) root without credentials, query, or fragment");
```

官方 README 更直接（`dsh-llm-deepseek/README.md:36`）：

> Choose this adapter for DeepSeek's official API **or a Messages-compatible gateway through `baseURL`**.

以及源码注释（`lib/index.js:386-388`）表达了设计意图：

> Every layer may supply an endpoint: the product trusts the project it is launched in,
> so a checkout can point its own agent at **the gateway that checkout is meant to use**.

**🟥 五条硬约束（必须写进 M3 的实施前提）**

| # | 约束 | 后果 |
|---|---|---|
| 1 | Gateway 必须实现 **Anthropic Messages 协议**（`POST /v1/messages`），**不是** OpenAI Chat Completions | 原 roadmap 写的「OpenAI 兼容端点」是**错的**，按它做接不通 |
| 2 | DSH 会向 base root **追加 `/v1/messages` 与 `/v1/files`**（末段正好是 `/v1` 时复用） | Gateway 必须同时提供这两个路径；`/v1/files` 至少要有明确的错误语义，不能 404 成"服务坏了" |
| 3 | baseURL 必须是**不带 credentials / query / fragment** 的裸 HTTP(S) root | **不能把平台令牌写进 URL**。Gateway 鉴权只能走请求头，或限制为仅本机/内网监听 |
| 4 | 「协议」本身**不可配置**：`throw new Error("llm-deepseek: protocol is not configurable")` | 不能指望上游帮我们转协议，转换责任在 gateway 侧 |
| 5 | **不是所有 adapter 都必然暴露 baseURL** | 部署时须逐个确认目标 adapter；已确认支持的是 `dsh-llm-deepseek`（`baseURL`）与 `dsh-llm-pi-ai`（每路由 `baseURL` + `api` 指定线协议） |

**额外收益**：`dsh-llm-pi-ai` 支持**多 provider + 手写 gateway** 由 catalogs 驱动，
若要统一收口多模型（DeepSeek + 其他），它是比 `dsh-llm-deepseek` 更合适的挂载点。

**净效果**：决策点 2 从「看运气」变成「**可行，且有明确施工约束**」。
「部门级可用版」可以先按 A（事后统计）交付，「完整企业版」再挂上 gateway 升级为事前管控 —— 与建议的 C 一致。

#### 1.2.4 补：`node:sqlite` 的 experimental 状态（原文档已覆盖，但风险等级需上调）

`node:sqlite` 在 Node 22/24 上仍打印 `ExperimentalWarning`。
原文档已用「驱动收口 + 稳定 SQL 子集 + 可降级」缓解。**但要补一条**：
本项目对 FTS5、BLOB 向量、json1 的依赖**较深**，一旦驱动层发生不兼容变更，
「降级为 JSON 仓储」的路径会**同时失去全文检索与向量检索**——即**知识库功能整体不可用**。
所以降级路径不是「能力受限」，而是「知识库不可用」。这必须在自检里**明确区分**并告警，不能含糊。

#### 1.2.5 补：第三方依赖破例的位置，建议从「数据库驱动」放宽到「驱动 + 分词」

原文档写「唯一允许破例引入第三方依赖的位置是数据库驱动」。
经 §1.2.1 的实测，**中文分词**是第二个现实缺口：自建 bigram 可用，但质量上限低于
专业中文分词（如 jieba/ICTCLAS 类）。若目标客户对中文检索召回质量要求高，
需要预留第二个破例位：**可选接入外部分词服务（HTTP）或 WASM 分词库**，
探测不到时回退 bigram 并如实标注。**建议现在就把它写成「第二个破例位」**，而不是将来临时开口子。

### 1.3 可行性判断

| 维度 | 判断 | 依据 |
|---|---|---|
| 数据层 | **高**（有条件） | 实测通过；风险在 experimental 与中文分词 |
| 鉴权/加密层 | **高** | 全部内置能力实测通过，无缺口 |
| 知识层 | **中** | 检索需修正；**解析是最大短板**（PDF/DOCX 靠外部命令） |
| 治理层 | **中高** | 审计哈希链、配额记账可实现；**事前管控受 DSH 约束** |
| 能力分发 | **中高** | 依赖 dsh-console 已有的插件/MCP 探测经验，可迁移 |
| 架构纪律 | **高** | 契约优先 + 隔离是成熟做法，MOVO 已验证 |
| 并发/规模 | **中低** | 单进程 + SQLite 单写是硬天花板 |

**综合：规划可行，但需要 4 处修正（中文分词、写合并、模型治理定位、破例位定义）。**

> ✅ **唯一的待验证前提已于 2026-09-30 验证完毕（§1.2.3.1）**：
> DSH **支持**自定义模型 base URL，且上游源码明确把自己定位为「可指向企业网关」。
> 结论是「可行 + 5 条硬约束」，不再是未知数。原风险矩阵第 5 条随之降级。

## 2. 能否落地

### 2.1 技术层面：能

没有发现「技术做不到」的环节。所有难点都有已知的降级路径，
且**降级都会在界面与自检里如实标注**（这是 dsh-console 已经验证过的做法）。

### 2.2 规模层面：这是真实体量，不是小项目

对照参照系（实测统计）：

| 项目 | 后端 | 前端 | 基础设施 | 交付形态 |
|---|---|---|---|---|
| dsh-console | `server.cjs` 2512 行 | `app.js` 12461 行 | 无（`.json` 快照） | 单文件 + 双击 |
| MOVO | ~1313 个 Python 文件 | 165 个 `.vue` + 218 个 `.ts` | Mongo + Redis + Weaviate，12 容器 | Compose |
| **sti-harness（规划）** | 目标 5 层 ~20 模块 | 渐进复用 dsh-console 前端 | 单文件 SQLite | 单进程 + 双击 |

**诚实的判断**：本项目后端规模会**明显小于 MOVO**（因为砍掉了多服务、多语言、多存储），
但**不会小一个数量级**——四项企业能力本身是实打实的功能量。
粗略量级（用于排期，不用作承诺）：M0 约相当于 dsh-console 后端的 1/4；
M1+M2 合计约相当于**再写一个 dsh-console 的后端**；M3+M4 各约一半。
**总工作量大致是「2.5～3 个 dsh-console」**。

### 2.3 排期层面：建议重切里程碑（重要建议）

原路线图把四项能力压进「一个大版本」。风险在于：**M2（知识）是四项里最重且最不确定的一块**
（三级解析链路 + 混合检索 + Worker 池 + 引用溯源），它一旦延期，整个大版本一起延期，
就变成「什么都做了一半、什么都不可用」。

**建议改为两个可交付版本：**

| 版本 | 包含 | 对外可用性 |
|---|---|---|
| **「部门级可用版」** | M0 骨架 + M1 身份权限 + M3 治理审计 + **精简 M2**（纯 Node 格式 + bigram 检索 + 无 embedding 降级） | **可登录、可管人、可审计、可查资料**——一个真能给部门用起来的平台 |
| **「完整企业版」**（即后来的 `0.6.0`） | 补全 M2（外部解析 + 向量混合检索）+ M4 能力分发 + M5 收口 | 完整四项能力 |

理由：**治理与身份是「能不能用」的门槛，知识检索是「好不好用」的加分。**
先交付前者，能最早拿到真实反馈；知识检索先用 bigram 纯文本路径跑起来（零依赖、零外部服务），
向量与复杂解析后补。这样也把「embedding 需要外部服务」这个企业内网红线问题**推到后面再决策**。

### 2.4 最可能延期的三处（提前标记）

1. **前端迁移**：原计划「先复用 dsh-console 的 `app.js`（12461 行）再按需拆分」。
   这个文件是单体巨型文件，把它**先搬进新项目、再拆、再叠加登录/权限/知识/治理四套新界面**，
   工作量与风险都被低估了。建议：**不复用旧 app.js，直接按新架构重写前端骨架**，
   只从旧项目**摘取成熟组件与交互逻辑**（如 WS 流式渲染、轨迹时间线、MCP 探测视图）。
   > 这一条如果不动，会成为整个项目最大的隐性延期源。
2. **文档解析**：PDF/DOCX/XLSX/PPTX 靠 `pdftotext` / `libreoffice --headless`。
   这两个命令在目标客户机器上**是否安装、版本、中文支持**都不可控。
   需要在 M2 一开始就做**解析能力的现场探测矩阵**，而不是写完代码才发现对方没装 LibreOffice。
3. **SSO/LDAP 实装**：原计划只留接口。但企业客户的 SSO 方言差异极大
   （AD / LDAP / OIDC / CAS / 钉钉 / 企业微信），**每个客户一次定制**。
   建议接口留好，实装按项目走，**不计入通用版本**。

### 2.5 落地判断

**能落地，但需要三件事**：
① 重切里程碑（§2.3）；② 前端不复用旧 `app.js`，改为重写（§2.4.1）；
③ ✅ **已完成**：M0 内验证「DSH 自定义 base URL」前提 —— 结论「支持，有 5 条硬约束」（§1.2.3.1）。

### 3.2 结论：够用与否取决于目标客户规模

| 场景 | 判断 | 说明 |
|---|---|---|
| 部门级内网单点（几十~上百用户） | **够用** | 首期四项 + 「部门级可用版」切片即可交付 |
| 中小团队私有化部署 | **够用** | 备份恢复 + 能力分发补齐后完整 |
| 集团级（千人并发） | **不够用** | 单进程 + SQLite 单写是硬天花板（§3.3） |
| 要求 99.9% SLA / 高可用 | **不够用** | 无多实例、无故障转移（明确不做） |
| SaaS 多租户运营 | **不够用且不建议** | 逻辑隔离非物理；且许可证可能限制托管运营 |
| 合规敏感行业（内容安全红线） | **不够用** | 缺 DLP/敏感词，需先补 #26 |

### 3.3 硬天花板（必须写进对外承诺）

1. **单进程**：无水平扩展、无故障转移。进程挂 = 服务停。
2. **SQLite 单写者**：并发写入串行。高并发对话时事件落库会排队（§1.2.2）。
3. **向量暴力检索**：建议 ≤ 10 万 chunk。超限需引入 ANN（未实现）。
4. **知识库依赖外部服务才能有高质量语义检索**：embedding 需 OpenAI 兼容 / Ollama；
   企业内网若无，则降级纯文本检索（**且中文质量取决于 §1.2.1 的修正**）。

> 这四项不是设计缺陷，是「零依赖 + 单进程」这条价值主张的直接代价。
> **写清楚它们，比号称「企业级」却在客户处崩掉更专业。**

## 4. 遗漏项清单

### 4.1 能力遗漏（对应 §3.1 的 ○）

1. **会话共享与团队协作**——企业里「把这段对话给同事看」是高频诉求（MOVO 有专门 ADR）。
2. **定时任务 / 调度**——「每天早上汇总一份报告」这类需求，企业侧很常见。
3. **通知与集成**——完成/失败/超配额要能推到邮件、企业微信、钉钉、webhook。
4. **内容安全 / DLP / 敏感词**——国内企业采购的合规红线项，缺失会直接卡采购。
5. **模型网关**——多模型路由、限流、降级、成本归集的收口（见 §1.2.3）。
6. **可观测性**——健康检查端点、关键指标、慢查询/慢请求追踪。企业运维必需。
7. **行级 / 数据范围授权**——「本部门可见」「仅本人可见」细粒度。
8. **SSO / LDAP 实装**——每个客户的方言不同，需按项目定制。

### 4.2 工程遗漏（比能力遗漏更隐蔽）

9. **与 dsh-console 的边界没有定义**——这是最现实的遗漏。

   > 不决策 = 默认走 B，而 B 的成本通常被低估。
   > ✅ **已决策 A（2026-10-01，由项目负责人拍板）**：落地内容见 §8 决策点 1 与

## 6. DSH 版本升级影响分析

### 6.1 先看现状：dsh-console 的耦合面有多大（实测）

dsh-console 把 DSH 调用**散落在整个代码库**。实测统计：

- **约 100 处上游方法名/命名空间字符串**，横跨 `agentPresets` / `agents` / `approval` /
  `credentials` / `commands` / `directoryPicker` / `dynamicCordisRunner` / `feedback` /
  `fileUploads` / `goals` / `knowledge` / `llm` / `mcp` / `session` / `settings` / `skills`
  等 **20 余个命名空间**（含少量非 RPC 噪声）。
- **RPC 信封**：Typert Remote `{type:'client-request', rpcId, method, payload:{args}}`，
  分布在 `server.cjs` 与 `app.js` 两侧。
- **事件字段直映射**：`assistant/chunk`、`compaction/*`、`usage`（`cacheReadTokens` 等）
  的字段名被前端与落库逻辑直接引用。
- **鉴权**：`dsh web` 的 `?token=` → cookie 换取，在 `server.cjs`。
- **MCP 握手**：硬编码 `protocolVersion: '2024-11-05'`。
- **插件树合成**：依赖 `dsh --profile web --dump-config` 的 YAML 结构。

**含义**：在 dsh-console 里升级 DSH，影响面**是全库**——没有边界可依，
只能靠 `tools/test-api.mjs` 全量回归发现哪里红了。这是 dsh-console 作为「单体快速原型」的
合理代价，但**不能带进企业平台**。

### 6.2 新架构为什么影响面小

sti-harness 的设计把上面的耦合点**全部收口到一个目录**：

| dsh-console 里散落的东西 | 新架构中的位置（唯一） |
|---|---|
| RPC 信封 | `app/kernel/dsh-provider/transport.mjs` |
| 约 100 处方法名/命名空间 | `app/kernel/dsh-provider/client.mjs` |
| 事件字段映射 | `app/kernel/dsh-provider/events.mjs` |
| 鉴权（token→cookie） | `app/kernel/dsh-provider/client.mjs` |
| MCP 握手 / 插件树 / Skills 探测 | `app/kernel/dsh-provider/capability.mjs` |
| 版本相关的行为差异 | `app/kernel/dsh-provider/compat/<版本>.mjs` |

**硬规则（必须进 CI）**：`app/platform/**` 与 `public/**` 中
**零 DSH 专有名词命中**，由 `tools/audit-layering.mjs` 拦截。
只要这条守得住，**DSH 升级的改动范围就是可枚举的 5 个文件 + 1 个 compat 垫片**。

### 6.3 升级时具体要动什么（按可能性排序）

| 上游变更类型 | 影响文件 | 工作量 |
|---|---|---|
| 方法改名 / 参数变更 | `client.mjs` | 小~中 |
| 事件字段改名（**最隐蔽**） | `events.mjs` + `compat/` | 中 |
| RPC 信封变更 | `transport.mjs` | 小 |
| 鉴权模型变更 | `client.mjs` | 小~中 |
| 插件树 YAML 结构变更 | `capability.mjs` | 小 |
| MCP 协议版本升级 | `capability.mjs` | 小 |
| 全新能力（如新增审批类型） | `contract.mjs` + `platform/` | 中~大（新功能，非兼容） |

> **最危险的是「事件字段改名」**：它不会报错，只会让某几个字段**静默变空**
> （比如 `usage` 的 token 数变 0），报表看起来还在跑，数字却是错的。
> 所以下面 §6.4 的 fixtures 机制是重中之重。

### 6.4 四项必须现在就做的加固

1. **事件语义归一（而非字段直映射）**
   落库 schema 用自己的**语义字段名**（`input_tokens` 等），上游字段名**只允许出现在
   `events.mjs` 里**。上游怎么改名，都只改映射点。
   **绝不**让 `events` 表列名直接等于上游字段名。

2. **契约 fixtures 回归（M0 就建）**
   把真实上游的事件流**录制成本地 JSON fixtures**（脱敏后），
   在 `tools/test-core.mjs` 里跑「fixtures → events.mjs → KernelEvent」的断言。
   **升级 DSH 的第一步就是跑这个回归**：红的即兼容点，一眼看全。

3. **版本门禁（不是静默可用）**
   `describe()` 返回真实 DSH 版本（dsh-console 已有 `dshVersion()` 的实现可迁移）；
   `check.cmd` 与首页在版本**不在已验证矩阵内**时给**黄灯提示**
   （「DSH x.y.z 未经本版本验证」），而不是假装正常。

4. **升级入场证明（借 MOVO 的做法）**
   升级后必须自动化跑通：
   `创建 → 执行 → 取消 → 立刻再执行 → dispose → resume → 再执行`
   `+ 恢复上一版写入的会话 + 分叉 + 加载已装 Skill + 子代理委派`。
   这套「入场证明」比单点回归更能暴露破坏性变更。

### 6.5 版本策略结论

- **一次只支持一个 DSH 主版本**（对齐 MOVO 的整版对齐纪律，不混用版本）。
- **compat 垫片按版本命名**（`compat/0.1.5-rc.2.mjs`），纯函数优先，旧版本用完即删。
- **升级流程**：跑 fixtures 回归 → 定位红的映射点 → 改 `dsh-provider/` → 跑入场证明 → 更新版本矩阵。
- **预期影响**：**小时级到天级**（前提是 §6.4 四条守住）。
  若纪律失守（DSH 名词泄漏到产品层），影响面会退化到「全库」——与 dsh-console 今天的处境相同。

### 6.6 实测补充（2026-09-30）：上游已经在动，三条观察值得记下来

M0 实施期间对本机上游做了一次实际勘察，结论比原先的推测更有份量。

**观察 1：上游版本已经跑在验证矩阵之前。**

```
$ node -e "…dsh discover…"
[ { bin: "C:\nvm4w\nodejs\dsh.cmd",
    packageDir: "C:\nvm4w\nodejs\node_modules\@deepseek-ai\dsh",
    version: "0.2.0-rc.2" } ]
```

而本项目 `app/config.mjs` 里声明已验证的是 `0.1.5-rc.2` / `0.1.6-alpha.1`。
→ **版本门禁不是纸上条款，第一次实际勘察就已经黄灯了。** 这正是设计它的原因：
门禁的作用不是阻止启动，而是**在升级时先跑回归、再上生产**。
M0 的结论是**不把 0.2.0-rc.2 写进已验证矩阵**——因为本机上游需要会话鉴权，
契约回归**没能真跑**。没跑过就不许标"已验证"，这条纪律比多一个绿点重要。

**观察 2：上游自己就在做会话格式迁移，且是 v0 → v4 的链。**

上游安装包里有 `dsh-session-format-v0-to-v1`、`v1-to-v2`、`v2-to-v3`、`v3-to-v4`
四个迁移模块，另有 `dsh-session-query-sqlite` 与 `dsh-session-persistence-jsonl`。

→ **这是「不要把上游原生会话格式存进我们库里」这条决策的最强证据。**
如果我们当初图省事直接把上游会话格式落库，上游每次格式升级都等于要我们跟着做一次数据迁移
（而且是 v0→v1→v2→v3→v4 这种链式迁移）。现在我们的做法是
**只存归一化后的 `KernelEvent` + 自有的 `messages` 表**，上游格式怎么变都只影响
`events.mjs` 一个文件。

**观察 3：上游带着自己的 API 网关与鉴权栈。**

依赖里有 `dsh-api-gateway`、`dsh-authorization`、`dsh-credentials`、`dsh-permission-presets`。
→ 说明上游的**进程边界与授权模型已经成型**。我们**不要试图替换它**，
而是在它之上做企业级那层（多租户、RBAC 矩阵、审批、审计哈希链）。
§4.2 的分工纪律在这里得到第二个佐证。

**观察 4（对决策点 2 的直接支持）**：见 §1.2.3.1 —— base URL 前提已验证，
且上游源码注释里明确把自己定位为「可以指向本企业网关」。上游是**留了口的**。

## 7. 安装 · 部署 · 集成 · 打包

### 7.1 运行形态

| 环节 | 设计 | 与 dsh-console 的差异 |
|---|---|---|
| 启动 | 双击 `start.cmd`（Windows）/ `start.sh`（Linux/macOS）→ `node app/main.mjs` | 一致 |
| 首次启动 | 建 `data/` → 生成 `data/.secret`（0600）→ 跑迁移 → 空库则进**初始化向导**（建组织+管理员+配模型凭据） | **新增**（对齐 MOVO 的 `/admin/setup` 心智，但不需要容器） |
| Node 门禁 | **≥ 22.13**，启动器硬校验并给明确报错 | dsh-console 是 ≥18；本项目门槛更高（`node:sqlite` 解禁） |
| DSH 依赖 | **必配**（0.21.4 起）：无内核时平台拦住整站并给出接入入口；平台层（身份/知识/治理）的代码与数据不受影响 | **关键提升**：dsh-console 无 DSH 首页就是红条；本项目无 DSH 时降级为「暂无 Agent 能力」，平台功能照常 |
| 数据目录 | `data/`（SQLite + 上传 + 索引 + `.secret`）—— **不入版本库、不进分发包** | dsh-console 是散落的 `.json` |
| 优雅退出 | SIGINT/SIGTERM → 收尾写库 → 关连接 | **新增** |

### 7.2 ⚠️ 安全模型必须分叉（这是最重要的一条）

**dsh-console 刻意只绑 `127.0.0.1`**，因为它是单人本机工具，代理里含沙箱、凭据、文件下载。
**但企业平台天然多用户，必须监听局域网/内网地址——安全模型必须整体升级：**

| 项 | dsh-console（单人本机） | sti-harness（多用户） |
|---|---|---|
| 监听 | 仅 `127.0.0.1` | 可配监听地址（默认仍保守） |
| 传输 | HTTP 明文可接受 | **必须 HTTPS**（或明确要求置于反代之后） |
| Cookie | 简单 | **`Secure` + `HttpOnly` + `SameSite`** |
| CSRF | 不需要 | **必须**（写操作带 CSRF token） |
| 限流 | 不需要 | **登录限流 + 全局限流**（抗暴力破解） |
| 会话过期 | 无 | **过期 + 空闲超时 + 吊销** |
| 密码策略 | 无 | 最小长度 + 强度检查 |
| 审计 | 无 | 登录失败/权限拒绝**全部留痕** |
| 反代 | 不需要 | 提供 **Nginx / IIS 配置样例** |

> **这一条如果不做，平台上线即事故**：把含凭据代理与文件下载的服务暴露到内网，
> 却还用 cookie 明文和无 CSRF 防护，等价于把 DSH 的访问权交出去（dsh-console 文档里
> 明确警告过「不要改成 0.0.0.0」，本项目必须用完整的安全体系来换取监听多用户的能力）。

### 7.3 集成清单

| 集成对象 | 方式 | 备注 |
|---|---|---|
| DSH Runtime | `DSH_ORIGIN` / `DSH_TOKEN` 环境变量，或首次向导里配置 | 沿用 dsh-console 的环境变量契约 |
| 模型 | 部门级可用版：经 DSH 直连；完整企业版：经本平台 model gateway（`DEEPSEEK_BASE_URL` 指向平台） | ✅ 可行**且已验证**（§1.2.3.1）：gateway 须实现 **Anthropic Messages 协议**（`/v1/messages` + `/v1/files`），baseURL 不得带 credentials/query/fragment |
| Embedding | OpenAI 兼容 / Ollama / 无（降级纯文本） | 独立配置项，**不受上面 Messages 协议约束**（是平台自己调的） |
| 反向代理 / TLS | 部署者负责，提供 Nginx 样例 | 平台不内置 TLS 终止 |
| SSO / LDAP | 接口预留，按客户实装 | 不进通用版本 |
| 通知（邮件/IM/webhook） | **webhook 已交付**（0.8.0 / P1-2；0.11.1 补失败重投队列，见 §3.1 第 25 项；**0.13.0 起 5 类事件全部有产生方**，其中"会成串发生"的两类带 10 分钟合并窗口）；**邮件 / IM 仍未实装** | 集成点已在审计/配额处预留 |
| 监控 | **首期缺**，至少要有 `/healthz` 与关键指标端点 | 建议 M3 就加 |

### 7.4 打包方案（继承 `dist.cmd` 体系 + 四项增强）

**继承**（dsh-console 已验证有效）：
- 版本号单点维护在根目录 `VERSION` 文件。
- `tools/make-dist.mjs` → 产出 `dist/sti-harness-<版本>/` + 同名 `.zip`。
- terser `compress` + `mangle`（**不开顶层函数名混淆**，因为 `onclick="fn()"` 依赖顶层函数名——
  这条经验直接从 dsh-console 抄过来，能省一次踩坑）。
  > ⚠️ **实际交付未采用**：`tools/pack-release.mjs` 是**零依赖白名单打包**，不做压缩/混淆
  > （保持"零构建、打开即可读"，便于 `node --check` + `vm` 真跑回归）。这条因此不适用；
  > 且 0.9.0 起内联 `onclick` 已全部改为事件委托，这个坑本身也不存在了。
- 打包产物随附 `LICENSE` / `NOTICE` / 部署 README。

**四项增强**（因为现在有真数据库和密钥）：

1. **排除清单更严格**：`data/`（**数据库 + 上传 + `.secret` 密钥**）、
   `*.db` / `*.db-wal` / `*.db-shm`、运行时日志、`.env`。**脚本扫描断言 0 命中**。
2. **迁移自动执行**：升级包替换代码后，首次启动自动跑增量迁移（`migrations/NNNN_*.sql`）。
   **禁止跨大版本跳迁**——迁移链必须连续，跳跃则拒启动并提示。
3. **升级前置备份**：升级器先 `VACUUM INTO` 出一份库备份 + 打包存储目录，
   失败可回滚（对齐 dsh-console `backup`/`restore` 子命令的思路）。
4. **开机自启样例**：Windows（计划任务 / `nssm`）、Linux（systemd unit 模板）——
   企业部署常要求「重启机器后服务自动起」。

### 7.5 升级路径

| 对象 | 方式 | 纪律 |
|---|---|---|
| **平台自身** | 替换代码目录 → 自动迁移 | 迁移链连续；先备份；不回退历史迁移文件 |
| **DSH** | 独立升级，平台按版本矩阵适配 | 跑 fixtures 回归 + 入场证明（§6.4）；整版对齐 |

### 7.6 企业分发形态（一个需要你确认的冲突点）

架构文档 §10 写「**不做多容器编排**」。但**企业内网交付常要求 Docker / K8s 形态**。这两者会冲突。
折中建议：**提供一个官方 Dockerfile（单容器、单进程）**——不违背「单进程」原则，
只是把「双击运行」换成「容器运行」，并允许把 `data/` 挂载为卷。
→ ✅ **已决策：暂不提供**（2026-10-01，由项目负责人拍板）。理由与三条硬约束见 §8 决策点 5；
**客户提出容器需求时再补**。
