# 升级与兼容策略

> 适用：sti-harness `0.6.0` 及以后。升级前先读 `docs/deploy.md`，备份用
> `POST /api/operation/backup`（或直接复制 data 目录，**含 .secret**）。

## 1. 版本号的含义

- **单一真源**：仓库根目录的 `VERSION` 文件。启动横幅、自检、备份 manifest、
  发布包名都从它读 —— 改版本只改这一个文件。
- **里程碑即版本**：M0→`0.1.0`、M1→`0.2.0`、…、M5→`0.6.0`。里程碑未收口不升号
  （开发中的 M4 曾长期停在 0.4.0 跑 68 条路由，直到验收全过才升 0.5.0）。
- `0.6.0` 之后遵循语义化：**新增接口/字段 = 次版本号；破坏性变更 = 主版本号**。

## 2. 兼容承诺（什么算破坏，什么不算）

| 变更 | 类型 | 说明 |
|---|---|---|
| 新增 HTTP 路由 | ✅ 兼容 | 只增不改；路由表 `/api/system/routes` 是唯一清单 |
| 响应里**新增字段** | ✅ 兼容 | 消费方不得假设字段集合封闭 |
| 中间件新增（如 M3 的 quota/audit 转正） | ✅ 兼容 | 可能让原本 200 的请求变 403（配额/越权是治理语义，不是接口变更） |
| `x-sti-*` 辅助头消失/变化 | ⚠️ 观察 | `x-sti-passthrough` 在 M3 起消失（全部实装的信号）；辅助头不作为集成依据 |
| SQLite schema 变更 | ✅ 兼容 | **只增不改**（见 §3） |
| 契约方法新增/可选参数 | ✅ 兼容 | 如 M5 的 `listTools({ tenantId })`（不带参仍回保守并集） |
| 删除路由 / 语义变更 / 必填参数新增 | ❌ 破坏 | 主版本号 + 本文件记录迁移路径 |

## 3. 数据与迁移

- 迁移文件**只增不改**：`0001_init.sql`…依次叠加，已应用的文件任何人不得修改
  （自检第 4 项会校验断链与篡改）。升级 = 把新迁移文件带过去，启动时自动应用。
- 回滚 = 恢复备份（`tools/restore-backup.mjs`），不是"反向迁移"。
- 主密钥（`data/.secret`）**不在备份包里、不在发布包里**：换机器升级必须单独带走它，
  否则已加密凭据解不开（这是设计而非疏漏 —— 密钥与数据分开存放）。

## 4. 上游内核

- 平台对内核只依赖契约（`app/kernel/contract.mjs`），不依赖具体版本。
- 内核上游可按 `docs/deploy.md` §4 的方式接入（页面接入向导或 `DSH_ORIGIN` / `data/config.json`）。
  没接入时平台**不提供对话**（没有可降级的本地内核，见 `docs/deploy.md` §4），
  其他页面依然可用 —— 探测结果里 `source` 如实标注是哪一个 provider
  （`external-kernel` / `unconfigured`；回归用的替身是 `kernel-stub`）。
- 契约形状变更走 `CONTRACT_VERSION`；适配层（`dsh-provider`）独立演进。

## 5. 升级步骤（标准流程）

```bash
# 1) 停服务，做一次备份（在线方式需在停服前做）
curl -X POST -H "Authorization: Bearer <token>" http://127.0.0.1:3090/api/operation/backup

# 2) 换新代码（发布包解压到新目录，或 git pull）
# 3) 校验备份包
node -e "import('./app/platform/operation/backup.mjs').then(m => console.log(m.verifyBackup('data/backups/<备份文件>')))"

# 4) 启动新版本 —— 迁移自动应用；先跑自检
node app/main.mjs --check

# 5) 复跑回归（对齐本版本验收口径）
node tools/test-core.mjs && node tools/test-http.mjs && node tools/test-knowledge.mjs \
  && node tools/test-frontend.mjs && node tools/test-governance.mjs \
  && node tools/audit-layering.mjs && node tools/audit-tenant-isolation.mjs
```

降级（新版本有问题）：停服 → `tools/restore-backup.mjs <升级前备份> <data目录> --overwrite`
→ 跑旧版代码。**注意**：新版本期间产生的数据会回到备份时点 —— 先把差异导出来。

## 6. 本文件没覆盖的情况

遇到本文件没说的变更，按这条判断：**"升级后，升级前能跑通的调用方代码是否原样能跑通？"
是 → 兼容（次版本）；否 → 破坏（主版本 + 在这里写迁移路径）。**

## 7. 与同权利人早期作品的关系（决策「A 吸收」的落地说明）

> 本节记录的是**沿革与边界**，不是使用说明。日常部署与升级读 §1–§6 即可。

### 7.1 关系已定：A · 吸收

2026-10-01 由项目负责人拍板（`docs/feasibility.md` §8 决策点 1）：

- **本平台是继任者**；同权利人那份早期作品冻结为「轻量版」，**停止新增功能**，
  只做安全维护与必要的上游版本适配。
- 两者**目标用户不同**（早期作品 = 单机开发者控制台；本平台 = 企业多用户），
  因此早期作品不会下线，但**不再承接新需求**。
- 采纳 A 的核心收益：**DSH 升级不再需要设计两套方案**。
  「适配层收口到一个目录」这条纪律从早期作品里的散落分布，收敛为本平台的
  `app/kernel/dsh-provider/`（+ `compat/<版本>.mjs` 按版本命名的垫片）。
  上游升级流程两边**用同一套动作**：跑 fixtures 回归 → 定位红的映射点 → 改适配层 → 更新版本矩阵。

> **诚实边界**：A 说的「DSH 适配层两边共享」在本仓的落地方式是**契约与经验共享**，
> 而**不是**一个被两个进程同时引用的物理目录 —— 两个工程各自独立、各有 `VERSION`，
> 不存在软链或子模块。物理共享需要把适配层抽成独立包，那会引入本平台明确拒绝的
> 「发布物依赖管理」，因此**刻意不做**。适配层的共享是**设计同构 + 可搬运**，不是运行时耦合。

### 7.2 数据迁移：**不迁移，重新初始化**

结论先说：**不做自动数据迁移**，也不提供导入工具。理由不是"懒得写"，而是三条硬理由：

1. **结构不可对应**。早期作品用散落的 `.json` 快照存状态（无库、无 schema 版本、
   无外键）；本平台是带迁移链的 SQLite（`users`/`roles`/`role_bindings`/`sessions`/…）。
   把一堆无约束的 JSON 映射进有外键与租户隔离的库，映射规则本身就是一份
   **比目标 schema 更长的代码**，且没有任何回归能证明映射正确。
2. **安全模型不同**。早期作品是单人本机工具（只绑 `127.0.0.1`、无多用户）；
   本平台是多用户。把旧状态搬进来等于**把一条没有口令与权限约束的数据链路接进有权限体系的服务**。
3. **会造出一条明文密钥路径**。旧 `.json` 里可能**明文**存有 DSH 令牌。要"迁移"就得读它、
   搬到新地方 —— 而本平台的凭据是 AES-256-GCM 加密、密钥在 `data/.secret`。
   为了迁移而引入一条"从明文 JSON 读密钥"的代码路径，是把平台上唯一的密钥纪律挖个洞。

**正确做法（按顺序）**：

1. 部署本平台，走首次启动初始化向导（建组织 + 管理员 + 模型凭据）。
2. DSH 连接信息**重新配置**，不要从旧 `.json` 复制：
   - 通过环境变量 `DSH_ORIGIN`（可整段带 `?token=…`）或 `DSH_TOKEN`，或写进 `data/config.json`；
   - 因为本平台**不把令牌落进响应体与日志**，请把它当作独立密钥对待。
3. ⚠️ **轮换旧令牌**：旧 `.json` 里那份令牌既然曾以明文落盘，应视为已暴露。
   在 DSH 侧重签一份新的，旧的作废 —— 这是"不迁移"之外唯一必须做的安全动作。
4. 知识库文档从**源文件重新导入**（`POST /api/knowledge/bases/:id/documents`），
   不要搬旧工程的索引 —— 分块参数与向量维度可能不同，混用会让相似度失效。

### 7.3 不需要迁移、但需要对账的两件事

| 项 | 处理 |
|---|---|
| 上游内核版本矩阵 | 本平台自持一份（`app/config.mjs` 的 `KERNEL_VERIFIED_VERSIONS`）。别处验证过的版本**不能直接照抄** —— 矩阵只认"在本仓真跑过契约核实"的版本，见 `docs/history/assessment-0.6.0.md` §5 P0-A |
| 前端交互经验 | 只摘取**成熟交互**（WS/NDJSON 流式渲染、轨迹时间线、MCP 探测视图），**不复用**任何外部工程的前端单体文件（见 `feasibility.md` §2.4.1 的风险条目） |

### 7.4 迁移后回退

不需要回退动作 —— 因为**没有数据被搬动**，早期作品的数据目录原样保留、原样可用。
两边可以**同时运行**（默认端口刻意错开）。
