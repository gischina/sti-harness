# versioning.md · 版本号怎么算

> **属主：版本号与版本策略。** 任何地方要写本产品的版本号，以这份为准。
> 它不是设计文档也不是发布记录 —— 它只回答"这个数字什么时候该动、动哪一位"。

---

## 1. 三条规则

### 规则 1 · `1.0.0` 保留给正式版（GA）

**`1.0.0` 的含义是"公开 API 稳定、可用于生产"。** 本项目对外只承诺到
**受控内网试用**（见 `deploy.md` §10），没有外部用户，接口也还在动 ——
**所以当前所有版本都必须是 `0.x.y`。**

> 这不是格式偏好。写 `1.8.0` 而产品还没 GA，就是在文档里写一句与事实不符的话 ——
> 本项目对"陈述与事实不一致"的处理一向是当成缺陷，这条也不例外。

### 规则 2 · `0.<能力线>.<收口轮次>`

| 位置 | 什么时候 +1 | 例子 |
|---|---|---|
| **minor**（第二位） | **能力面或契约发生变化**：新模块 / 新路由族 / 新的可观测面 / 内核接入方式变了 | 知识库级 ACL、模型中心、真内核接入、定时任务底座 |
| **patch**（第三位） | **收口**：修 bug、补文档、补回归、补出口、工程化、更名 | 前端拆片、备份运维收口、门禁与孤儿审计 |
| **`-rc.N`** | **同一版本内的多轮验收**（不改变语义版本） | `0.14.0-rc.1`、`0.14.0-rc.2` |

判断口径只有一句：**"用户能不能用出一个新东西？"** ——
能，动 minor；只是"同一件事变得更靠谱/更清楚"，动 patch。

### 规则 3 · 另外两个版本序列与本产品版本**无关**

| 序列 | 值 | 说明 |
|---|---|---|
| **上游 DSH 版本** | `0.1.5-rc.2` / `0.1.6-alpha.1` / `0.2.0-rc.2` | 指 `@deepseek-ai/dsh`。兼容矩阵与垫片命名见 `compatibility.md` 与 `app/kernel/dsh-provider/compat/`（**垫片按文件名加载，改名即崩**） |
| **内核契约版本** | `app/kernel/contract.mjs` 的 `CONTRACT_VERSION`（当前 `1.1.0`） | 指 `KernelEvent` 的**形状**版本。**它可以是 1.x** —— 那是事件格式的成熟度，不是产品的 |

> ⚠️ **这三个序列会撞脸**：产品曾用过 `1.0.0` / `1.1.0`，而契约版本正好就是这两个值。
> 重编号时必须靠**上下文**分辨，不能按字面替换 —— 详见 §4。

## 2. 为什么要重定基线

原始计划本来是合理的（见 `roadmap.md`「交付进度」）：

```
0.1.0 M0 → 0.2.0 M1 → 0.3.0 M2 → 0.4.0 M3 → 0.5.0 M4 → 1.0.0 M5
```

`1.0.0` 被定在「五个里程碑全部交付」。**问题出在这之后**：每一次收口都动了 minor，
于是 minor 变成了"第几轮收口"的计数器 ——

| 旧号 | 内容 | 按规则 2 该是什么 |
|---|---|---|
| `1.2.0` | 知识库级 ACL | **minor** ✅ |
| `1.5.0` | 库级授权图形化入口 | **minor** ✅ |
| `1.7.0` | 两个"有名字没产生方"的事件接通 + 出口补齐 | **minor** ✅ |
| `1.1.0` | 产品全量更名 | patch ❌ |
| `1.3.0` | 体检项收口 | patch ❌ |
| `1.4.0` | 前端拆片 + 文档单一真相源 | patch ❌ |
| `1.6.0` | 备份运维收口 | patch ❌ |
| `1.8.0` | 工程化收口（**零新功能**） | patch ❌ |

两个后果：

1. **数字虚高**：产品还没 GA 却自称 `1.8.0`；而依赖的上游当时是 `0.2.0-rc.2`
   —— 两个数字摆在一起，读者必然误判成熟度。
2. **语义失真**：minor 不再表示"能力变化"，于是**从版本号看不出任何东西**。

处置：**整条历史重排回 `0.x` 线**（`0.1.0`–`0.5.0` 本来就诚实，不动），
并按规则 2 重新判定每个版本该动哪一位。

**文件随版本号改名**（引用已同步改写）：

| 旧路径 | 新路径 |
|---|---|
| `docs/assessment-1.2.0.md` | `docs/assessment-0.11.0.md` |
| `docs/history/assessment-1.0.0.md` | `docs/history/assessment-0.6.0.md` |
| `docs/history/assessment-1.0.1.md` | `docs/history/assessment-0.7.0.md` |

> **已打出的发布包保留原名，而且这个"原名"必须一路保持为真** ——
> 包是**当时真的按那个号**打出来的，**改名等于篡改产物的出处**：
> `1.8.0.zip` 里封的 `VERSION` 与 `README` 都写着 `1.8.0`，只改文件名就自相矛盾了。
> 所以 §3 的表要**双向**读：`1.0.1` ↔ `0.7.0` … `1.8.0` ↔ `0.13.1`。
>
> ⚠️ **重编号时在这里漏改过一处，0.13.1 收口已修**：脚本把文档里**引用包名的字符串**
> 也一并改成了新号（`README.md` 版本块里 12 条「发布产物」，加 `assessment-0.11.0.md`、
> `history/assessment-0.6.0.md` 各 1 条），于是文档开始声称一批**从未存在过的包**
> （如 `dist/sti-harness-0.12.1.zip`），而磁盘上躺着的是 `1.6.0.zip`。
> 这类失真最危险的地方是**它看起来很自洽** —— 版本号、条目数、字节数都"对得上"，
> 只有拿文档逐条去和 `dist/` 对账才会露馅。已全部改回当时的编号，并在 README §6 顶部留了说明。
>
> ⚠️ 同一次对账还查出**第二层**，而且这一层**不是重编号造成的**：`1.0.1`–`1.0.4` 这 4 个包的
> **前缀根本不是 `sti-harness`** —— 那时项目还叫 **`geoscene-harness`**（下表 `1.1.0` 一行才写着
> "全量更名 STI HARNESS"），而文档一直把它们记成 `sti-harness-1.0.x.zip`。这是**更名当次**落下的。
> 它同样"看着自洽"：字节数能对上（`geoscene-harness-1.0.4.zip` = **904079 B** ↔ 文档写的"约 90.4 万字节"）。
> 两层合计 5 处已改回 `geoscene-harness-*`。
> **结论：产物名这条线有三层可能出错的地方 —— 编号、前缀、留存 —— 只有"文档 ↔ `dist/` 双向对账"
> 这一个动作能同时盖住。**
>
> **留存规则**：`dist/` **只留最新一版**，更早的构建产物不必留着（0.13.1 收口时已按此清理）；
> 但**不要**为了"看起来一致"回头改留下的那些。

## 4. 已知例外（重编号时刻意不改的地方）

1. **`app/data/migrations/0015_drop_users_is_admin.sql` 里有一处旧文件名 `assessment-1.2.0.md`**。
   **刻意保留**：迁移内容参与 `sha256` 校验和（`schema_migrations.checksum`，见 `app/data/migrate.mjs`），
   **改一个字符就会让已部署的库报"已应用的迁移内容已被修改"**。历史迁移是不可变产物，
   存档在它里面的引用也一并不可变 —— 读到它时按本表映射即可。
2. **上游 DSH 版本与内核契约版本**（§1 规则 3）不是本产品版本，不参与重编号。
3. **`docs/feasibility.md` §2.3 的两个"交付档位"**（`v0.5`「部门级可用版」/ `v1.0`「完整企业版」）
   是**计划里的档位名**，不是版本号。重编号时**去掉了会误导的 `v1.0` 前缀**，只保留档位名 ——
   因为按规则 1，`1.0` 是保留给 GA 的，留着它等于在文档里暗示一个不存在的正式版。

## 5. 改版本号时的收口清单

1. `VERSION` 文件（唯一被代码读取的地方，见 `app/paths.mjs` 的 `readVersion()`）。
2. `docs/deploy.md` §10：**「当前版本（x）的诚实边界」**标题 +
   **「本版（x）可以做什么 / 还不能做什么」**两处。
3. `docs/roadmap.md` 版本表**追加一行**（旧行不动 —— 那是决策证据）。
4. `README.md` 追加**版本记录块**。
5. 跑 `node tools/gate.mjs`。其中一条守卫会**核对 `VERSION` 与 `deploy.md` 的「本版（x）」是否一致** ——
   此前这两处漂移过一次（标题写 `1.6.0`、内容已是 `1.7.0`），靠人工看没发现。

> **规则 2 的自我约束**：如果一个版本里**什么能力面都没变**，那它就是 patch。
> 若发现"这一版没什么可写"，正确做法不是硬造一条 minor，而是**把它合进下一次收口**。
