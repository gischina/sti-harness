# A. 冗余 / 无意义 / 建议去掉或合并

## A1. 🔴 真·逐字重复（同一段逻辑多份拷贝）

这是本次最扎实的一类问题：**改一处必须记得改三处**，漏一处就是永久漂移。

| # | 重复项 | 位置 | 差异 |
|---|---|---|---|
| 1 | `unwrap()`（service 结果 → HTTP 语义） | `routes/model.mjs:41`、`routes/notify.mjs:39`、`routes/schedule.mjs:43` | **逐字相同**（只差一句注释） |
| 2 | `audit()`（路由层留痕） | 同上三文件 | 仅 `resourceType` 字串不同（`'model'`/`'notify'`/`'schedule'`） |
| 3 | `rowById()` / `rowByName()` | `model/service.mjs:47,51`、`notify/service.mjs:152,156`、`schedule/service.mjs:119,123` | 仅**表名**不同 |
| 4 | `safeBaseName()`（文件名净化） | `routes/kernel.mjs:89`、`knowledge/service.mjs:344` | 仅兜底字串不同（`'attachment'`/`'document'`） |
| 5 | 安全 JSON 解析 | `readMeta`(model:55)、`parseJson`(schedule:127)、`parseEvents`(notify:160)、`safeJson`(capability.mjs)、`safeJson`(audit.mjs)、`parseJson`(parsers/json.mjs) | 6 份「try/catch + 兜底」变体 |

**为什么值得改**：项目自己的路由纪律写着「路由只做解析 → 调 service → 响应」，
而 `audit`/`unwrap` 恰恰是**每条路由都要用的横切件**，散在 3 份正好违背这条原则。
`safeBaseName` 更敏感——它是**防路径穿越/文件名注入**的那一层，两份拷贝意味着「加固了一处、漏了另一处」是可能的。

**建议**：
- `app/http/routes/_shared.mjs` → `auditOf(resourceType)` 工厂 + `unwrap(ctx, r)`
- `app/util/json.mjs` → `parseJsonSafe(raw, fallback)`
- `app/util/fname.mjs` → `safeBaseName(filename, fallback)`（**安全件必须单点**）
- 仓储层 → `rowBy(tenantId, table, column, value)`（表名走白名单，避免拼 SQL）

**预期收益**：约 −180~−220 行，且 5 类漂移风险归零。

## B2. 🔴 检索延迟：10 万 chunk 混合检索 **P95 ≈ 1.9 s**

`docs/benchmark.md` 的实测（**15 W 笔记本 CPU，作者自陈取的是保守下限**）：

| 路径 | P95 @ 10 万 chunk × 256 维 |
|---|---|
| FTS 常见词 | 430 ms |
| 向量暴力扫描 | **1,231 ms** |
| **服务层混合检索** | **1,931 ms** |

外推：20 万 → ≈2.4 s、50 万 → ≈6 s、100 万 → ≈12 s。

**且——全部是单请求串行测量，没有并发测试**（benchmark §9 自己写明「不是生产 QPS 上限」）。
即：**真实并发下的表现目前无人知道**。

**建议（按性价比排序）**：
1. **先做并发压测**（B11）—— 现在的数字只能说明「一次查询多慢」，说明不了「能扛多少人」；
2. 向量预过滤（先用 FTS 缩候选再算余弦，注明会牺牲纯语义召回，做成开关）；
3. 上 ANN（`sqlite-vec` 或外部），或按 B1 补上抽象后再换。

- 投递「最多 2 次 + 指数退避，失败入审计，**不做持久化重试队列**」（roadmap:690）。

→ 后果：**上游抖动 = 告警永久丢失**，只在审计里留痕，没有任何重投/可见的失败队列。
对「审计锚定失败」「备份失败」这类**必须被看见**的事件，这是生产硬伤。

**建议**：至少做「失败落 `notify_deliveries` 表 + 调度器定期重投 + 页面可见待重投数」；
再往上才是邮件/企微/钉钉 sink（属于产品决策，不是技术债）。

## B6. 🟠 无 HTTPS、无多实例（硬天花板，文档已诚实交代）

| 项 | 事实 |
|---|---|
| TLS | 平台**不实现** HTTPS（`deploy.md:479` 明确要求反代终止 TLS；`main.mjs` 无 `createSecureServer`） |
| 单进程 | SQLite 单写者；定时任务**无分布式锁**（`schedule/service.mjs:22-24` 自己写明）；并发配额是**进程内存**（`deploy.md:618`）；`/metrics` 计数器**重启归零**（`deploy.md:621`） |

→ 意味着：**只能单机单进程，不能横向扩，不能滚动升级**。
`feasibility.md:338` 自己给了结论：**部门级内网单点够用，集团级/千人并发不够用**。

这不是「缺陷」（作者反复标注过），而是**采购时必须先对齐的前提**。
**建议**：把这条提炼成**一页纸的「适用/不适用场景」**放在 deploy.md 最前面——现在它散在 7 份文档里。

## B7. 🟡 工具执行在真实内核上不可用

**审批门守着一条当前不存在的执行路径**。这属于**必须让使用者知道**的落差。

**建议**：在路由表/能力清单/前端明确标注「工具执行：当前内核不支持」，
不要让「工具策略页」暗示执行面可用。（或者：既然真实内核给不了，就该如实降级为「策略预置」语义。）

## B9. 🟡 知识库级授权无界面入口 —— **已在 0.12.0 关闭**（见 §D1）

上一轮 4.6 已交付后端（4 条路由 + 回归），**界面只有「可见性」下拉与徽标**，
授权名单的增删只能走 API。已如实排入 **0.11.1 之后**（0.11.1 排的是 A/B 组的缺陷修正，未含此项）。
→ 从生产可用性看：**能设「受限」但没有界面给人授权 = 容易把自己锁在外面**（虽有管理员防自锁）。
建议它的优先级高于其他 UI 项。

> **0.12.0 的处置**：0.11.2 交付后，"0.11.1 之后"这个承诺到期，本轮兑现 ——
> 知识库页新增「库级授权」面板（列名单 / 授权 / 撤权，主体与角色只从下拉选）。
> 落地时确认了这条建议的判断**是对的但不够准**：真正的坑不是"缺一个界面"，
> 而是**判定口径**—— 授权要的是「**该库**的 write 档」（路由门只要 `knowledge:read`），
> 所以面板**不能**按租户级 `knowledge:write` 预隐藏，否则"全局 viewer、本库 admin"的
> 库级管理员（这个面板唯一真正的服务对象）恰好会被挡在门外。
> 连带修掉两个真问题：① 授权主体**未在服务层校验**，仓储层的裸 `Error` 出网变 `500`
> （"账号已被删"显示成"服务器坏了"，而有界面之后这条路真实可达）；
> ② `test-http` / `test-frontend` 的知识服务**未与 `main.mjs` 同构装配**，
> 导致库级 ACL 在这两套端到端回归里**从未真正生效**。

## B10. 🟡 备份：默认不自动、恢复离线、主密钥不在包内 —— **已在 0.12.1 关闭**（见 §D1）

| 事实 | 证据 |
|---|---|
| 默认播种的定时任务**不含** `backup.create` | `schedule/service.mjs` 的 `DEFAULT_JOBS`（本条写于 0.11.0 时只有 3 个，0.11.1 起为 5 个：审批超时/审计归档/链尾锚定/会话清理/通知重投 —— 仍然不含备份） |
| 恢复**刻意不做在线接口** | `roadmap.md`；只能 `tools/restore-backup.mjs` 离线做 |
| 主密钥 `data/.secret` **不在备份包内** | `routes/operation.mjs` 明确要求单独保管 |

→ 后果：**开箱即用 ≠ 开箱有备份**。运维必须自己配 `backup.create` 定时任务 + 单独保管主密钥。
**主密钥丢失 = 所有托管凭据不可解密，无后门**（`credentials.mjs` 自己写明）。

**建议**：部署清单里把「① 配置自动备份任务 ② 单独备份主密钥」列为**上线前必做项**并给出命令，
而不是散在文档里让人自己拼。

> **处置（0.12.1）**：本条**建议对，但落到实现时发现它少说了一半**。
> 「不默认播种」本身是**刻意的产品决定**（备份是消耗型动作，"要不要占盘"该由运维定）——
> 推翻它不在本条授权范围内。真正的缺口不是"默认值选错了"，而是**这个状态不可见**：
> 没配备份既不会报错、界面上也看不出异常，直到需要恢复那天。
> 所以按 B1/B7 的同一条路数办 —— **补一处"如实呈现"的位置**：自检新增第 `[14]` 项
> 「备份与恢复」（把"任务没配 / 一份备份都没有 / `backup.failed` 没人订阅"直接问出来，
> 并给出可照做的命令与两条边界说明），部署文档给出「上线前必做两件事」清单。
> 顺带查出**本条没提到、但更严重的一件事**：`backup.failed` 自 0.8.0 起就在通知白名单与
> 部署文档里，**全项目却没有一个 emit 点** —— 即"备份失败会告警"一直是句空话。
> 0.12.1 把它接通（失败即出站 + 任务仍如实记 `fail`），并补了一张
> `NOTIFY_EVENT_PRODUCERS` 对账表与双向静态核验，防同类漂移复发。

## B11. 🟡 没有并发/长稳测试（feasibility 自定的标准未达成）

- `tools/` 下**没有** load / stress / soak 脚本，只有 `bench-search.mjs`（**串行**检索基准）；
- `feasibility.md:114` 自己要求：「**明确写入配额**：单进程的写入吞吐上限要在文档里给出**实测数字**（不是「很快」）」；
- 现状：**搜索有实测数字（benchmark.md），写入吞吐没有**。
  `benchmark.md` 里的 `1,631 chunk/s` 是**离线批量入库**，**不是并发请求吞吐**。

→ **全项目最重要的那个数（能扛多少并发用户）目前是空的**。

**建议**：补一个 `tools/bench-concurrency.mjs`——N 个并发回合 + 混合检索，输出
写入 P95 / 请求 P95 / 错误率 / 内存曲线，跑 30 分钟版。这是回答「能不能上生产」的**唯一硬证据**。
