## 1. 三分钟跑起来

### 1.1 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| Node.js | **≥ 22.13**，推荐 22 LTS 或 24 | 低于 22.13 时 `node:sqlite` 需要实验性开关，平台会**直接拒绝启动**并说明原因 |
| 操作系统 | Windows 10+ / Linux / macOS | 已在 Windows + Node 22.22.2 / 24.10.0 实测 |
| 磁盘 | 首年预留 **≥ 5 GB** | 数据库 + 上传文件 + 产物留存 |
| 内存 | ≥ 2 GB | 单进程，实测常驻远低于此 |
| 网络 | 仅需能访问上游内核（可选） | 没有上游内核也能跑，见 §4 |

**不需要**：Docker、npm install、数据库服务器、Redis、Python。

### 1.2 启动

**Windows**：双击 `start.cmd`
**Linux / macOS**：`./start.sh`

看到这样的输出就是成功了：

```
STI HARNESS 0.19.0 已启动
  地址        http://127.0.0.1:3090
  内核        已接入（http://127.0.0.1:3080，版本 0.2.0-rc.2）
  数据目录    …\sti-harness\data
  路由        146 条（public 9，session 81，admin 56；自检第 [9] 项现读）
  中间件      context → ratelimit → auth → tenant → rbac → quota → audit（七项全部实装）
  自检        node app/main.mjs --check
  停止        Ctrl+C
```

然后在浏览器打开 **http://127.0.0.1:3090**。

> ⚠️ **不要双击 `public/index.html`**。前端通过相对路径调 `/api/*`，
> 用 `file://` 打开时所有接口都会失效（页面会给出明确提示，不会白屏）。

### 1.3 首次启动会自动做什么

1. 创建数据目录骨架（`data/`、`data/storage/{uploads,artifacts}`、`data/logs`），并**真实写一个探针文件**确认可写；
2. 生成主密钥 `data/.secret`（AES-256-GCM，32 字节，权限 0600）；
3. 建 SQLite 库 `data/sti-harness.db`，应用全部迁移
   （`0001_init.sql` 建 29 张表 / 视图 + FTS5 虚拟表与同步触发器；`0002_documents_source.sql` 加文档来源字段；
   `0003_governance.sql` 给 quotas 加 `mode` 列 + 建 `tool_policies` 表）；
4. 探测上游内核，决定用外部内核还是降级为内置确定性内核；
5. 探测知识库的**外部解析命令**（`pdftotext` / LibreOffice）与**向量模型**配置，如实记录能力矩阵；
6. 监听端口，打印地址。

浏览器打开后，若库里还没有组织与账号，会自动进**初始化向导**（M1 起）：
填组织名 → 管理员账号与口令 →（可选）模型凭据 → 提交后建组织、物化 4 个内置角色、绑定 `owner`。
之后就是登录页。**全程不需要手写任何初始化脚本。**

登录后侧栏会出现**知识库**入口（M2 起，需 `knowledge:read` 权限）：
可以建库 → 导入文档（文件 / 目录 / URL / 纯文本）→ 看分块预览 → 跑召回测试。
**导入不需要预先配置任何东西**：没装 `pdftotext` 就只少 PDF，没配向量就只走文本检索 ——
页面上都会写明当前是哪种模式（见 §2.1）。

**空库到可用状态 = 一条命令**（+ 一次向导），不需要任何初始化脚本。

## 2. 自检

```
check.cmd          # Windows，双击即可
./check.sh         # Linux / macOS
node app/main.mjs --check    # 任何平台，最本质的调用
```

`--check` **不监听端口**，因此服务已在运行时也可以安全执行。
输出是纯文本，可以让现场人员整段复制发回来。

自检 15 项：

| # | 检查项 | 关注点 |
|---|---|---|
| 1 | 运行环境 | Node 版本是否达下限 |
| 2 | 数据目录 | 存在、可写、主密钥是否在位（附指纹，不泄露内容） |
| 3 | 数据库 | SQLite 版本、日志模式、表数量 |
| 4 | 数据库迁移 | 是否全部应用、有无断链或被人改动 |
| 5 | 前端产物 | `index.html` 引用的**每一个**资源是否齐全（前端按域分成 `public/app/*.js` 多片，清单由 `index.html` 现读） |
| 6 | 监听端口 | 目标端口是否空闲 |
| 7 | Agent 内核 | 用的是外部内核还是降级内核，降级原因是什么 |
| 8 | 契约与映射 | 契约方法是否齐全、事件类型数量 |
| 9 | 中间件与路由 | **哪些中间件已实装、哪些还是占位**（当前版本的防护边界）+ 路由数按里程碑分布 |
| 10 | 打开方式 | 正确的访问地址与注意事项 |
| 11 | 企业知识与检索 | **格式解析能力矩阵**（哪些内置可用、哪些外部命令缺失）、当前**检索模式**、向量模型、分块参数、解析并发方式 |
| 12 | 治理与审计 | 对每个组织**真实重算审计哈希链**（断裂 → fail）、配额规则数、用量采集口径 |
| 13 | 凭据表安全 | `credentials` 表**列名层面**有无明文字段（凭据只能以密文列存放） |
| 14 | 备份与恢复 | **自动备份任务配没配 / 有没有真备份 / 备份失败有没有人收得到**，外加"恢复是离线动作""主密钥不在包内"两条边界（见 §5.2） |
| 15 | 内核令牌落盘卫生 | **0.15.0 新增**：`data/config.json` 里的令牌是**密文还是明文**。0.15.0 之前写下的配置一律是明文（内嵌在地址的 `?token=` 后），而**那个形状不会报任何错** —— 服务照起、对话照跑、页面照显示"已接入"，代价是每一份备份包与快照都连带带走了上游凭据。发现明文时给出可照着做的一条命令：`node tools/seal-kernel-token.mjs`（只读报告；`--apply --force` 才写，写前备份、写后往返校验）。⚠️ 本项**只读**，自检绝不改配置 |

末行汇总是 `结果：无阻塞问题，N 个提示`；退出码 `0` = 可运行，`1` = 有阻塞问题。
标 `!` 的是**提示**（例如内核未接入、`pdftotext` 缺失），不影响服务启动，但建议看一眼。

### 2.1 部署前必须检查（M2 起新增）

M2 起知识库的能力**取决于这台机器上装了什么**。第 11 项自检就是这份"现场探测矩阵"，
**部署到客户机器前必须看这一项**，并据此告诉客户"能搜什么、不能搜什么"。

| 依赖 | 检查方式 | 有它 | 没它（会怎样） |
|---|---|---|---|
| **纯 Node 解析** | 永远可用 | `txt` / `md` / `csv` / `tsv` / `json` / `jsonl` / `html` **开箱即用** | — |
| **`pdftotext`**（poppler） | 自检第 11 项 | 可导入 PDF | ⚠️ **降级**：PDF 文档导入即置 `failed` 并保留原始错误（`未检测到 pdftotext…`），**页面会明确标注**，不假装成功 |
| **LibreOffice**（`soffice`） | 自检第 11 项 | 可导入 DOCX / XLSX / PPTX | ⚠️ **降级**：Office 文档同上置 `failed` |
| **向量模型凭据** | 自检第 11 项显示 `向量模型：none` | 语义检索（向量 + RRF 混合） | ⚠️ **降级**：自动退化为**纯文本 bigram + FTS5 bm25**，**知识库页状态条显示 `纯文本检索` 徽标** —— 这不是故障，是设计好的降级路径 |

安装命令：

```bash
# Debian / Ubuntu
apt install poppler-utils libreoffice

# macOS
brew install poppler
brew install --cask libreoffice

# Windows
#   poppler：下载后把 bin 目录加进 PATH
#   LibreOffice：官网安装包
#   自定义路径时可用 STI_SOFFICE 指向 soffice 可执行文件
```

> ⚠️ **「降级」和「故障」不是一回事，请向客户讲清楚**：
> 没有 `pdftotext` 时，**txt/md/csv/json/html 依然完全可用**；
> 没有向量模型时，**中文检索依然能命中**（走 bigram 分词，不是裸 `unicode61`）。
> 缺哪个就少哪块能力，页面上都会写明白 —— **本项目宁可显示"能力不足"，不显示"正在工作"**。

**配置向量模型**（启用语义检索）：

```
set STI_EMBED_PROVIDER=openai-compat
set STI_EMBED_BASE_URL=http://127.0.0.1:11434/v1
set STI_EMBED_MODEL=nomic-embed-text
set STI_EMBED_DIM=768
set STI_EMBED_CREDENTIAL=embedding-main
```

或写进 `data/config.json` 的 `embedding*` 段。配好后重启，自检第 11 项应从
`向量模型：none` 变为实际 provider 名；知识库页面状态条同步从 `纯文本检索` 变为 `混合检索`。

> ⚠️ **API Key 不写在环境变量里**，而是走凭据库：
> `STI_EMBED_CREDENTIAL` 填的是**凭据的名字**（如 `embedding-main`），
> 真正的密钥在平台的**凭据页**录入，AES-256-GCM 加密落库。
> 这样密钥不会出现在进程环境、`start.cmd` 或日志里 ——
> 接口只回 `hasValue`，**连密文都不回显**。备份时必须带上 `data/.secret`。
> （本机 Ollama 通常不需要密钥，此时可以不配 `STI_EMBED_CREDENTIAL`。）

## 3. 配置

优先级：**环境变量 > `data/config.json` > 内置默认值**。
自检与状态页会显示每个配置项的**来源**（`env` / `config.json` / `default`），不会让你猜。

### 3.1 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `STI_HOST` | `127.0.0.1` | 监听地址。**改成 `0.0.0.0` 或内网地址前，必须先读 §7.1** |
| `STI_PORT` | `3090` | 监听端口（刻意避开同权利人早期作品的 3081，两者可同时运行） |
| `STI_DATA_DIR` | `./data` | 数据目录。迁移到别的盘 / 挂载卷时用 |
| `STI_LOG_LEVEL` | `info` | `debug` / `info` / `warn` / `error` |
| `STI_LOG_MAX_BYTES` | `10485760`（10 MB） | 单个日志文件大小上限，达到即轮转（`runtime.log` → `.1` → `.2`…） |
| `STI_LOG_KEEP` | `5` | 轮转日志保留份数，更旧的删除 |
| `STI_RATE_LIMIT` | `600` | 每 IP 每分钟请求上限（内存滑动窗口） |
| `STI_RATE_LIMIT_LOGIN` | `30` | **登录接口单独**的每 IP 每分钟上限（比全局严一档；按账号的退避锁定另有一套，见下） |
| `STI_TRUST_PROXY` | 关 | **经反向代理部署时必须开**（`1`/`true`/`on`）；直连部署**必须保持关** —— 开了它才会采信 `X-Forwarded-For` / `X-Forwarded-Proto`，而直连时这两个头客户端可随意伪造。见 §7.1 |
| `DSH_ORIGIN` | `http://127.0.0.1:3080` | 上游内核地址，**可整段带 `?token=…`** |
| `DSH_TOKEN` | 空 | 上游内核令牌（与上面二选一） |
| `DSH_PROFILE` | `web` | 上游内核 profile |

**M2 起新增（知识库相关）**：

| 变量 | 默认 | 说明 |
|---|---|---|
| `STI_EMBED_PROVIDER` | 空 | 向量 provider：`openai-compat` / `ollama`。空 = **纯文本检索**（只用 FTS5，状态里报 `mode: none`） |
| `STI_EMBED_BASE_URL` | 空 | 向量服务地址（OpenAI 兼容 `/v1`） |
| `STI_EMBED_MODEL` | 空 | 向量模型名 |
| `STI_EMBED_DIM` | `0`（自动探测） | 向量维度 |
| `STI_EMBED_CREDENTIAL` | 空 | **凭据的名字**（不是密钥本身）。密钥在凭据页录入，加密落库 |
| `STI_WORKERS` | 按 CPU 核数 | 解析 / 分块 / 向量化的 worker 线程数。排查问题时可设 `1` |
| `STI_CHUNK_MAX` | `800` | 单块最大字符数（分块上限） |
| `STI_IMPORT_MAX_BYTES` | 见 `config.mjs` | 单文件导入体积上限 |
| `STI_SOFFICE` | 空 | `soffice` 可执行文件路径。LibreOffice 不在 PATH 时用它指定 |
| `STI_ALLOW_UNVERIFIED` | 空 | 允许上游版本不在已验证矩阵内继续启动（配合 §4 的版本门禁） |

**检索性能（B2 向量预过滤）**：

| 变量 | 默认 | 说明 |
|---|---|---|
| `STI_PREFILTER_VECTOR` | 关 | 向量检索**预过滤**：先按文本命中把候选缩到几百条，再在候选上算余弦。`1`/`true`/`on` 开 |
| `STI_PREFILTER_CANDIDATES` | `512` | 候选上限（最多取多少条文本命中）。**硬上限 900**（SQL 变量数），写更大只会被夹住并如实提示 |

> ⚠️ **默认是关的，而且这是刻意的 —— 它不是"纯优化"，是会改变答案的行为变更。**
>
> 实测（`tools/bench-search.mjs` 阶段 ⑤，5 千 chunk 合成语料）：开了之后向量扫描 5000 → 512 条、
> 检索 P95 **123 → 94 ms**；但**最终 top-10 与全量精确检索只有 3~5 条重合**（另 5~7 条被换掉）。
> 那个重合度是合成语料下的读数（合成向量与合成文本本就弱相关），真实语料下应好得多 ——
> 但**没有真实语料实测之前，不该把"改变答案"设为默认**。
>
> - **什么时候该开**：库大到暴力扫描成为瓶颈（如 > 10 万 chunk），且查询以**字面词**为主；
> - **什么时候务必关**：召回质量优先、查询常靠语义（近义/换述）命中；
> - **安全阀（与开关无关，始终生效）**：文本候选少于 `limit*3`（且不低于 32）时**自动退化为全量扫描**。
>   所以开了它之后，纯语义查询也不会静默失效 —— 只是那些查询仍按全量精确跑（慢，但召回无损）。
>   检索结果里 `retrieval.prefilter.reason` 会如实说明是「关」「生效」还是「退化」。
>
> 界面入口：知识库页的**召回测试**里有一个三态开关（跟随配置 / 强制开 / 强制关），
> 可以不改配置直接做 A/B 对照。

> 📌 **`STI_EMBED_*` 全为空是合法的默认状态**，不是配置错误：
> 平台会走**纯文本 bigram + FTS5 bm25** 检索，并在知识库页显示 `纯文本检索` 徽标。
> 详见 §2.1 与 `docs/benchmark.md`。

**0.8.0 起新增（调度 / 通知）**：

| 变量 | 默认 | 说明 |
|---|---|---|
| `STI_SCHED_TICK_MS` | `30000` | 调度器扫描间隔（毫秒）。**改小不会让任务跑得更准**，只会更频繁地查"有没有到期的" |
| `STI_NOTIFY_ALLOW_LOOPBACK` | 空 | 设为 `1` 才允许**往回环地址**（`127.0.0.1`）投递通知。**生产的默认是禁止** —— 回环是 SSRF 的典型载荷；只有"自测本地接收端"这一种正当用途，且测试脚本自己会显式打开它 |

> ⚠️ 关于 `STI_NOTIFY_ALLOW_LOOPBACK`：**别为了"让告警先跑通"而在生产打开它**。
> 出站目标由**平台管理员**在通知渠道页配置，若允许回环，被攻破的管理员账号就能让平台
> 去打本机上任何 HTTP 服务（包括本平台自己的接口）。要自测请在测试环境开，
> 生产把接收端放在另一台机器上（内网地址是**允许**的，`10./172.16-31./192.168.` 不受影响）。

**安全与凭据（2026-10 安全评审落地）**：

| 变量 | 默认 | 说明 |
|---|---|---|
| `STI_LOGIN_FAIL_MAX` | `5` | 同一账号连续失败几次后开始**退避锁定**（锁定期间即使口令正确也回 `429`，不是静默放行） |
| `STI_LOGIN_LOCK_BASE_MS` | `30000` | 退避基数：第 5 次失败锁 30 秒，其后按 2 的幂增长 |
| `STI_LOGIN_LOCK_CAP_MS` | `900000` | 单次锁定上限（15 分钟） |
| `STI_BACKUP_KEY` | 空 | 备份包加密密钥（hex / base64 / 口令均可）。不设时用 `data/backup.key`（首次备份时自动生成）；两者都拿不到才退化为每份备份一个一次性密钥。**保管纪律见 §5.2** |
| `STI_OLDER_SECRETS` | 空 | **主密钥轮换**期间保留的旧密钥（32 字节 base64，多条用逗号分隔），只供解密存量密文。启动时自动把旧密文重加密为当前密钥，全部归位后即可移除（见 §5.4） |

示例（Windows 命令行临时启动）：

```
set STI_PORT=3091
node app\main.mjs
```

Linux / macOS：

```bash
STI_PORT=3091 node app/main.mjs
```

### 3.3 知识库级可见性与授权（0.11.0 起）

知识库默认**全租户可见**（`visibility = tenant`）。需要收紧时把它改成**受限**
（`restricted`），此后**只有被授权的账号/组 + 管理员**能看到这个库 —— 权限判定
从"租户级"细化到了"逐库"。

| 概念 | 取值 / 位置 | 说明 |
|---|---|---|
| 库可见性 | `tenant`（默认） / `restricted` | 建库时给 `visibility`，或建完再改 |
| 库级授权 | 复用 `role_bindings` 的 `scope_type='knowledge_base'` + `scope_id=<库 id>` | **零新表**：这是身份模块早就预留的位置 |
| 有效角色 | **全局角色 ∪ 该库上的库级角色** | 并集**只作用于这一个库**，不影响其它库 |

**三条安全线**（都写进了回归，不是口头承诺）：

1. **不可见一律 404，不是 403**。受限库对无权限者是"**不存在**" —— 库的**存在性**本身是信息，
   403 等于承认"有这么个库，只是不给你看"。⚠️ 但要区分：**"看不见这个库" → 404**；
   **"看得见但档位不够" → 403**（两者都能从响应码读出来）。
2. **管理员（owner / admin）对受限库恒可见**。这是**防自锁**：把库设为受限后若连自己都进不去，
   就再没有入口把它改回来了。
3. **库级授权只能放宽"被授权的那个库"**；而且**授权名单本身要 write 档才能看** ——
   名单会暴露组织里的分工。撤权时绑定**必须属于该库**（拿别库的 `bindingId` 来撤 → 按 404 拒绝）。

**相关接口**（全部要登录；库级动作的档位判定在服务层）：

| 动作 | 接口 | 所需档位 |
|---|---|---|
| 建库时指定可见性 | `POST /api/knowledge/bases`，body 带 `"visibility": "restricted"` | `knowledge:write`（组织级） |
| 改可见性 | `PATCH /api/knowledge/bases/:id`，body `{ "visibility": "restricted" }` | 该库 **write** |
| 列授权 | `GET /api/knowledge/bases/:id/grants` | 该库 **write** |
| 授权 | `POST /api/knowledge/bases/:id/grants`，body `{ "subjectType": "user"｜"group", "subjectId": "...", "roleKey": "..." }` | 该库 **write** |
| 撤权 | `DELETE /api/knowledge/bases/:id/grants/:bindingId` | 该库 **write** |

可见性变更、授权、撤权**都强制入审计**（`knowledge.base.visibility` / `.grant` / `.revoke`）——
这是安全边界上的开关，事后必须能回答"谁在什么时候把哪个库从受限改成了公开"。

> ⚠️ **诚实边界（0.11.0，已在 0.12.0 修订）**：0.11.0 时**界面上还没有"库级授权"入口** ——
> 界面里只能**在知识库列表页切换可见性**（`全组织` / `受限` 下拉），给某个账号/组授库级权限
> 需要**直接调上面的接口**。图形化入口当时排在 **0.11.1 之后**。
> **0.12.0 已补上**：知识库页的「库级授权」面板可以列名单、授权、撤权（主体与角色都从下拉选）。
> 上表保留接口形态 —— 它仍是脚本化 / API Key 场景的正式通路。
>
> ⚠️ **面板的权限口径与全站别处不同，这一点必须知道**：「能不能列/改名单」取决于你在
> **这个库**上有没有 write 档（路由门只要 `knowledge:read`，判定在服务层）。
> 所以那个面板**不按全局 `knowledge:write` 关闭** —— 否则"全局是 viewer、本库被授成 admin"的
> 库级管理员就看不到它。服务端的拒绝会**原样显示**（`403` = 看得见但档位不够；
> `404` = 这个库对你不可见），两个数不会含混成一个。
>
> 另外，**`restricted` 是"放行名单"语义**：某主体在本库上的有效档位是
> 「全局角色 ∪ 库级角色」的并集 —— 把一个 viewer 授成本库的 `admin`，他就能**在本库**写；
> 反之**撤权后立即回到"看不见"**（不残留）。这条请务必在授权前想清楚。

### 3.4 通知渠道与失败重投队列（0.11.1 起）

**配置**：在「通知渠道」页登记 webhook（URL 加密落库、接口只回显 host），勾选要订阅的事件。
URL 的 scheme 必须是 `http`/`https`；**回环、未指定、链路本地（含云元数据 `169.254.169.254`）会被拒**，
内网地址（`10./172.16-31./192.168.`）允许 —— 内网部署的 webhook 目标本来就在内网。

**直达企微 / 钉钉自定义机器人（0.17.0 起）。** 填 `qyapi.weixin.qq.com` / `oapi.dingtalk.com`
的机器人地址即可直接对接，不需要中间转发器：平台按 host **精确**识别目标，自动换成这两类机器人
要求的 `{"msgtype":"text","text":{"content":"…"}}` 信封（content = 一行摘要），并且**按回执
`errcode === 0` 判定成败**。为什么强调这个：这两类接收端对不合规报文也回 **HTTP 200** ——
只看状态码会把「消息没渲染」记成「已送达」。现在 `errcode≠0`（key 失效、信封被拒、关键词不匹配……）
与**回执解析不了**（如中间有代理）都算失败，照常进重投队列，原因原文写在 `last_error` 里。
其余目标（通用 webhook）收到的报文**一字未变**，HTTP 状态码仍是其成败契约。

> ⚠️ 机器人安全设置请用「**关键词**」或 IP 白名单：平台发的是纯文本摘要，摘要里会带上关键词即可。
> **「加签」（DingTalk secret 签名）当前不支持** —— 平台不发签名参数，这类目标会被机器人拒收，
> 试发与投递记录里会看到非零 `errcode`（如实报错，不会假装成功）。要用加签请等平台支持或自建转发器。
> ⚠️ 识别是 host 精确匹配：售后域名、代理域名（哪怕转发到机器人）都走通用报文 ——
> 那种情况下请自行按通用 JSON 契约适配。

**投递语义：先尽力而为，失败落库重投。** 一次投递内联最多 2 次（指数退避）；仍然失败则写入
`notify_deliveries` 队列，由定时任务 `notify.retry` 重投：

| 项 | 值 | 说明 |
|---|---|---|
| 重投上限 | **6 次** | 只算"已被重投的次数"（不含首次内联的 2 次），页面显示 `已重投 X / 6` |
| 退避 | 10 分钟起、×2、**封顶 1 小时** | 第 1/2/3/4 次分别等 10/20/40/60 分钟 |
| 超限 | 转 `dead` | **不是删除**：保留可见、可手动重投（人常在修好接收端之后回来点它） |
| 终态保留 | **30 天** | `delivered` / `dead` 由 `notify.retry` 顺带清理；**`pending` 永不清** |
| 扫描间隔 | **10 分钟** | `notify.retry` 的默认规则 `interval:600000`（可在调度中心改） |

**4 类事件，各自"谁会产生它"**（**白名单 ≠ 有实现**，所以这张表要写到"谁产生"这一层）：

| 事件 | 什么时候发生 | 会产生几次 | 节流 |
|---|---|---|---|
| `quota.blocked` | 配额中间件拦下一次请求（403），或并发闸拦下一轮回合 | **会成串**：撞上配额之后，**每一次**提交/调用都匹配 | **10 分钟**合并（键 = 租户 + 事件 + **哪个指标**） |
| `backup.failed` | **自动备份任务**失败（带原始错误）。⚠️ 页面上「立即备份」失败**不**报此事件 —— 那是人在旁边看着的动作，错误直接给操作者 | 每个任务周期最多一次 | 无 |
| `model.probe.failed` | 模型探活巡检失败 | 每个巡检周期最多一次 | 无 |
| `audit.anchor` | 链尾锚定任务出站 —— **这是锚点第一次具备独立证明力的途径**（见 §10 边界） | 每个锚定周期一次 | 无 |

> ⚠️ 节流**合掉的是"通知"，不是"事实"**：每一次拦截都仍然**逐条**进审计，
> 所以"被合并"不会让任何事变得查不到。反过来也成立：**告警通道安静，不代表没发生** ——
> 判断"有没有被拦"请去看审计页，不要用"我没收到告警"当证据。
> ⚠️ 节流窗口是**进程内存**（与并发配额同一理由：单进程部署），**重启即重新计时**。

**运维动作**（都要求 `notify:read` / `notify:write`）：

| 动作 | 接口 | 权限 |
|---|---|---|
| 看队列 | `GET /api/notify/deliveries?status=pending｜dead｜delivered｜all` | `notify:read` |
| 立即重投一条 | `POST /api/notify/deliveries/:id/redeliver` | `notify:write`（会真的出站 POST） |

> ⚠️ **语义是 at-least-once**：重投时接收方**可能收到重复**。同一条投递的**首次尝试与所有重投
> 共用响应头 `X-STI-Delivery-Id`**，接收方据此去重 —— 平台做不到"确认对方只处理了一次"。
> ⚠️ **重投是本机单进程**的（与调度器同一约束：无分布式锁）：平台**整体停机期间**的告警仍会丢。
> 变的只是"上游抖一下不再等于告警丢失"。
> ⚠️ **试发（页面上的「测试」）失败不入队** —— 那是人在旁边看着的动作，丢进队列只会污染
> "待处理告警"这个数字。
> ⚠️ 渠道被**停用/删除**时，待重投记录**不消耗重投次数**（那不是"对方拒绝"，是"现在不该发"），
> 记录保持 `pending` 并如实写明原因。

## 4. 上游内核（必配）

平台把「智能体怎么运行」外包给上游内核（DSH Runtime），自己只负责企业化那部分。
**内核只有两种状态：接入了 / 没接入**（0.21.4 起；此前那套 `auto` / `external` / `mock` 模式开关，
连同"探测失败就降级到内置确定性内核"的机制已整体删除）。

**没接入内核时平台会拦住整个平台**，只留一个"接入内核"的界面 —— 身份 / 知识 / 治理 / 能力四块的
代码和数据都在，但一个能看能点、一发对话就报错的平台比拦住更糟（用户会以为功能坏了）。
接上内核之后那些页面立刻可用。

> 为什么删掉内置 mock 内核：它让"真接上了"和"没接上但装作接上了"变成同一种状态 ——
> 界面显示绿色徽章，用户却拿不到真实回答。那层降级换来的"平台看起来正常"，
> 代价是把一次明确的接入问题变成了一个诡异的"模型好像不太行"。

### 4.1 探测失败的原因

自检第 7 项会直接写出原因。常见的是 **`need-token`**：
上游要求浏览器会话鉴权，此时需要把带 `?token=…` 的地址交给平台。

配置方式（二选一）：

```
set DSH_ORIGIN=http://127.0.0.1:3080/?token=你的令牌
```

或写进 `data/config.json` 的 `dshOrigin`。

配好后重启，自检第 7 项应变为绿色并显示上游版本；同时自检会做**版本门禁**——
上游版本若不在已验证矩阵内，会**黄灯提示**（不静默放行，也不阻止启动）。

### 4.2 在页面上接入（0.15.0 起，推荐）

**不用再上服务器改 JSON**：用管理员账号登录（或**首次登录时按引导走**），到**概览页**的
「接入真实内核」面板：

1. **粘贴地址**：把内核启动时打印的那一整行（形如 `http://127.0.0.1:3080/?token=…`）**整段粘进去即可** ——
   整段里带的令牌会被自动识别并单独摘出来（不必手工拆）。也支持反向代理下带路径的形态。
2. **点「检测连接」**：会真的去连一次，并按**卡在哪一步**给结论与下一步。六种结论各自对应
   一种不同的处置（地址填错 / 连不上 / 有响应但不是内核 / 要令牌 / 令牌被拒 / 来源被拒），
   页面上会同时列出**可核对项**（HTTP 状态码、对面报的服务名与内容类型、版本、令牌来源）。
3. **点「保存并启用」**：**只有检测通过（绿色「就绪」）这个键才是亮的** —— 0.21.5 起没有
   「跳过检测直接保存」那条路，检测没通过时保存按钮点不动，服务端也会以 409 连同完整诊断拒绝。
   保存后令牌以**密文**写入 `data/config.json`（键名 `dshTokenCipher`），明文不会被写进任何文件。
   **保存即生效，无需重启**（0.21.3 起内核可热切换；正在进行的回合会用切换前的内核跑完）。
   接入成功后，若平台此前没接入内核（整页阻断态），页面会当场解除阻断并落到首页。

检测与保存都**需要管理员权限**（`system:write`）：服务端主动去连一个地址是 SSRF 形状的动作，
不该开给任何登录用户。**检测未通过就存不进去**（连不上 / 要令牌 / 令牌被拒 / 来源被拒 / 不是内核
/ 地址非法，一律拒绝并说清卡在哪一步、下一步干嘛）—— 这是刻意的：留住"稍后内核才启动"的口子，
换到的是"保存成功、平台却没接入上"这种最难自查的失败。

⚠️ 若 `DSH_ORIGIN` 环境变量已设置，它**覆盖**配置文件 —— 这时页面上会直接说「在这里保存不会生效」，
要去改那个环境变量（或去掉它再重启）。这是**唯一**还需要重启的常规情形。

`data/config.json` 的形状：

```json
{
  "dshOrigin": "http://127.0.0.1:3080",
  "kernel": "auto",
  "dshTokenCipher": "…（AES-256-GCM 密文，界面与日志都不回显）"
}
```

⚠️ **主密钥 `data/.secret` 是解密的唯一凭据**（它不在备份包内，需单独保管）：
丢了之后已存的令牌**永久不可解密，没有后门** —— 到时候按上面三步重填一次即可。

已在本平台验证过的上游内核版本维护在 `app/config.mjs` 的 `KERNEL_VERIFIED_VERSIONS`。
升级上游后，第一件事是跑回归（见 §6），而不是先上线。

### 5.2 备份

> ## ⚠️ 上线前必做四件事（0.12.1 起，自检第 [14] 项会把它们问出来）
>
> **开箱即用 ≠ 开箱有备份。** 平台**刻意不**默认播种自动备份任务（备份是**消耗型**动作，
> "要不要占盘、留多久"由运维定，见下），所以一台刚起来的机器上**一份备份都没有**，
> 而这件事不会让服务报错、界面上也看不出异常 —— 直到真的需要恢复那一天。
>
> **① 配自动备份任务**（登录后 → 「调度中心」→ 新建任务）：
>
> | 字段 | 填什么 |
> |---|---|
> | 名称 | 自动备份 |
> | 类型 | **自动备份**（`backup.create`） |
> | 规则 | `dailyAt:03:00`（UTC）—— 即北京 11:00，避开业务高峰 |
> | 参数 | `{"keep": 30}`（保留最近 30 份，更旧的自动轮转删除） |
>
> 等价的接口调用（`<TOKEN>` 为管理员会话令牌或 API Key，走同一条 `POST /api/schedule/jobs`）：
>
> ```bash
> curl -sS -X POST http://127.0.0.1:3090/api/schedule/jobs \
>   -H "authorization: Bearer <TOKEN>" -H "content-type: application/json" \
>   -d '{"name":"自动备份","kind":"backup.create","schedule":"dailyAt:03:00","params":{"keep":30},"enabled":true}'
> ```
>
> 想立刻验证一次（不等第二天）：同页点该任务的**「立即执行」**，或
> `POST /api/schedule/jobs/<id>/run`。执行完在「运维 → 备份」页能看到新出现的备份文件。
>
> **② 单独备份主密钥**：`data/.secret` **不在备份包里**（进了包就等于凭据明文搬家），
> 必须**另行拷走并单独保管**。丢了它，已加密落库的凭据**永久无法解密，没有后门**：
>
> ```bash
> # 停服后执行。★ 这份文件要和备份包**分开放**（同一个盘上丢了就一起丢）
> cp data/.secret /你的离线介质/sti-harness-secret-$(date +%Y%m%d).key
> ```
>
> **③（建议）让"备份失败"真的有人收到**：平台在自动备份失败时会出站 `backup.failed`
> 事件（0.12.1 起接通），但**前提是有一个启用渠道订阅了它** ——
> 到「通知渠道」页勾上该事件，并用「测试」按钮确认能通。没人在收 = 备份连续失败也悄无声息。
>
> **④ 备份密钥定一个去处**（备份包 `formatVersion 2` 起**整体加密**，密钥独立于 `.secret`）：
> 恢复一份加密备份需要**两样东西** —— 包 + 密钥。密钥的形态取决于你怎么配：
>
> | 形态 | 何时用 | 密钥在哪 | 恢复时怎么给 |
> |---|---|---|---|
> | `STI_BACKUP_KEY` 环境变量 | **推荐**（密钥进企业的密钥管理，不落数据盘） | 你自己的保管处 | 设回同一变量 |
> | `data/backup.key` | 默认（首次备份时自动生成，0600） | 数据目录里 | `tools/restore-backup.mjs` 会自动从目标数据目录找；跨机恢复需先把它单独拷过去 |
> | 一次性密钥（包旁同名 `.key`） | 兜底（`backup.key` 不可写时） | 每份包旁边 | 与 zip **一起**收走（恢复工具会自动识别同目录同名 `.key`） |
>
> ⚠️ **包与密钥分开存**：加密挡的是"有人单独拷走了包"；两者放同一块盘，丢盘时一起丢。
> 另注意：自动轮转清理旧备份时会**连带删除同名的 `.key`** —— 一次性密钥场景下，
> 一份备份的"生命周期"包含它的密钥。
> ⚠️ **演练过一次的备份才算备份**：`node tools/restore-backup.mjs <备份ZIP> <目标目录>`
> （停机离线动作，流程见 §12）。它会先验签名与逐文件哈希、再解密、再跑 `integrity_check`；
> **用错密钥会得到明确的"kid 不匹配"报错**，不会静默恢复出一堆坏数据。上线验收单（§7.4）要求真的恢复一次。

**必须包含**：`data/sti-harness.db*`、`data/.secret`、`data/storage/`，
以及**0.8.0 起新增的 `data/archive/` 与 `data/anchor/`**。

> ⚠️ **`data/archive/` 不是"可以再生成的东西"。** 审计归档会把超期记录**从主表删除**，
> 归档出来的 `.jsonl` 是那段时间的**唯一副本**。备份漏了它 = 那部分审计历史真的没了。
> 这也是"归档"与"删除"的分界线：少备份一次归档目录，就把"归档"退化成了"删除"。

```bash
# 停服后直接打包最省事（M0 数据量小，停服几秒即可）
#   停服：Ctrl+C
tar czf backup-$(date +%Y%m%d).tgz data/
```

> ⚠️ **`.secret` 与数据库必须一起备份**。只还原数据库、丢了 `.secret`，
> 已加密的凭据（M1 起）将**永久无法解密**，只能重新录入。
>
> **在线备份（`VACUUM INTO` 一致性快照）与恢复校验自 M5 起已提供**（见下）；手工停服打包仍然可用，两者不冲突。

**在线备份与保留策略（0.10.2 起）**

在线备份建议交给**调度中心**按时间跑，而不是靠人记得点：

| 项 | 值 |
|---|---|
| 任务类型（kind） | `backup.create`（自动备份） |
| 建议规则 | `dailyAt:03:00`（UTC，即北京 11:00） |
| 参数 | `{"keep": 30}` |
| 相关接口 | `POST /api/operation/backup`（手工建一份）/ `GET .../backup`（列举）/ `POST .../backup/verify`（校验） |

- **`keep` = 保留份数（默认 30）**。每轮**先建成功、再轮转**：只保留最近 `keep` 份，
  更旧的删除。轮转**只认** `backup-*.zip` —— 你手工放进 `backups/` 的其它文件一律不碰。
- **至少保留 1 份**：`keep` 给 `0` 或负数一律按 `1` 处理。
  （"磁盘满"是问题，"没有备份"是灾难 —— 所以宁可留一份旧的。）
- **删除动作单独入审计**：`operation.backup.prune`，明细含被删文件名与释放字节数。
- ⚠️ **没有 HTTP 删除接口**，这是**刻意的**：删备份不可逆，平台不提供"点一下就删"的按钮。
  轮转只发生在自动任务里 —— 无人值守、有保留下限、删的永远是最旧的。
- ⚠️ **备份任务不在默认任务集里**：需要在**调度中心**手工建一条（步骤与命令见 §5.2 的
  「上线前必做两件事」）。备份是**消耗型**动作，"要不要默认占盘"由运维决定 ——
  代价是**开箱即用 ≠ 开箱有备份**，所以自检第 [14] 项会把这个状态直接问出来。
- ⚠️ **轮转只发生在自动任务里**。`POST /api/operation/backup`（页面上的「立即备份」）
  建的备份**不会被自动清理** —— 只有 `backup.create` 这条任务跑起来才会裁到 `keep` 份。
  手工备份堆多了，只能到 `data/backups/` 里自己删（平台刻意不提供删除接口，见上）。
- 轮转失败**不会**把备份任务记成失败（备份确实做成了，记 fail 会让失败计数失去意义），
  原因会出现在该任务的执行明细（`rotateError`）里。
- ⚠️ **备份失败会出站告警**（0.12.1 起）：自动任务调用在线快照失败时发 `backup.failed` 事件
  （带原始错误信息），且该任务仍如实记 `fail`。报**只**发生在自动任务里 ——
  页面上「立即备份」失败时错误直接显示给操作者，不再往告警通道里灌一条
  （那会让通道被操作者的试错刷屏）。⚠️ 前提是**有启用渠道订阅了 `backup.failed`**，
  否则"会告警"仍是句空话 —— 自检第 [14] 项会检查这一点。

### 5.3 迁移到另一台机器

1. 拷贝整个目录（含 `data/`）；
2. 在新机器装好 Node ≥ 22.13；
3. 跑一次 `check.cmd` —— 若提示迁移有断链或文件被改动，按提示处理；
4. 启动。

路径全部按运行时推导，**没有任何写死的绝对路径或用户名**，换盘符 / 换目录名 / 换用户都不影响。

### 5.4 主密钥轮换（换了 `.secret` 之后）

`data/.secret`（主密钥）加密着全平台的凭据、通知渠道 URL、MCP 配置与内核令牌密文。
需要换掉它时（例如：怀疑泄露、合规要求定期轮换），**不要直接删掉或覆盖** ——
那等于把所有旧密文变成解不开的乱码。正确做法是**带旧密钥上任**：

1. 停服，备份 `data/` 全量（含 `.secret` 与数据库）；
2. 把旧 `.secret` 的**内容**（它就是 base64 形式的旧密钥）填进 `STI_OLDER_SECRETS`；
3. 删掉 `data/.secret` 后启动 —— 平台会生成一把新的（0600）；
4. 平台在后台逐项把旧密文重加密为当前密钥（幂等，每次启动扫一遍，日志有进度）；
5. 日志出现「全部存量密文已归位为当前密钥」后，才把旧密钥从 `STI_OLDER_SECRETS` 移除，再重启。

> - 全程**可读**：密钥环同时握有"当前 + 旧"，新旧密文都解得开，没有"停机换钥"的窗口；
> - 解不开的单元（旧密钥没给全）**保持原样、不丢数据**，日志会点名是哪些，补上旧密钥重启即可；
> - 覆盖范围是**枚举过的**：凭据表、通知渠道 URL、MCP 连接配置、`config.json` 里的内核令牌密文；
> - 第 5 步之前**别删旧密钥** —— 它是那些还没归位的密文唯一的钥匙。

> ⚠️ **开环定速必须配 `--open-sender=process`（独立发包端）**。用默认的 `--open-sender=inproc`
> 时发包循环与服务器**共用一个事件循环**：服务端一卡，发包节拍也被拖慢，
> 于是"目标 30 req/s 只发得出 17.6"会被误读成"系统扛住了"—— 这是**与事实相反**的结论。
> 正解是另起一个只发包的进程。⚠️ 但两个进程**仍同机**：它解决"发包节拍被拖慢"，
> **不**解决"客户端与服务器争 CPU"（后者要另一台机器，属多机压测，**未做**）。

末行是 `DONE fails=N`（`N` 是**基准断言**不达标条数）。口径、机器、规模边界见
[`docs/benchmark.md`](benchmark.md)（检索）与
[`docs/benchmark-concurrency.md`](benchmark-concurrency.md)（并发）。零依赖、自带临时库。

> ⚠️ 并发基准的 `fails` 记的是**正确性**问题（丢写 / 非预期响应 / 未捕获异常），**不是**"慢"。
> 而且它测的是**平台自身开销**（内核是测试替身，没有模型时间），**不能**读成端到端对话延迟。

全部脚本都**零第三方依赖**，末行输出 `DONE fails=0` 表示通过（沿用项目约定）。

> 📌 `test-http.mjs` / `test-knowledge.mjs` / `test-frontend.mjs` / `bench-search.mjs` /
> `bench-concurrency.mjs`
> 都自带**临时数据目录**并监听**随机端口**（`listen(0)`），
> 因此不依赖本机是否已启动服务、也不占用 3090、更**不会碰你真实的 `data/` 目录**。
> 服务正在跑的时候也可以直接执行。

**什么时候必须跑**：

- 升级上游内核版本前后；
- 改动 `app/kernel/` 下任何文件后；
- 改动 `app/http/` 或 `app/platform/identity/` 下任何文件后；
- **改动 `app/platform/knowledge/` 或 `public/` 下任何文件后**（M2 起）；
- **改动 `app/platform/schedule/` / `app/platform/notify/` / `app/platform/governance/audit.mjs`
  或迁移 0009 / 0010 后**（0.8.0 起）—— 归档与锚点会动 `data/archive/` `data/anchor/`，
  务必连带验一次"归档后链仍可校验"（`test-core` 有专门用例钉住这件事）；
- **改动 `app/platform/governance/cost.mjs` / `usage.mjs` / `app/platform/model/service.mjs`
  或迁移 0011 后**（0.9.0 起）—— 成本口径与归因都在这一组文件里，
  改完必须跑 `test-core`（纯函数口径）+ `test-http`（端到端算出来的金额）；
  页面上的一句话改动（比如把"未定价"写成 `0.00`）同样要跑 `test-frontend`；
- **改动 `app/http/security-headers.mjs` / `public/index.html` / `public/boot.js`，或往
  前端新增任何交互控件时**（0.9.0 起）—— CSP 的 `script-src` 已不含 `unsafe-inline`，
  **任何新写的 `onclick="..."` 都会被浏览器拒绝执行（点了没反应）**；交互一律走
  `act('方法名', 参数…)` / `actCh()` / `navAttr()` 产生 `data-*` 属性，由 `bindDelegates()`
  的事件委托派发。新增 `act()` 名字后跑 `test-frontend`（它会把 `data-act` 名字与 App 上
  真实存在的方法对账，并端到端验一遍委托派发）；
- **改动 `app/data/repositories/attachments.mjs` / `events.mjs`、
  `tools/kernel-stub.mjs` 的回合起点、或迁移 0012 后**（0.9.0 起）——
  附件仓储的**每一条 SQL 都必须同时带 `tenant_id` 与 `session_id`**（附件是按 id 直接寻址的资源，
  少了任一个就是"知道 id 就能下载别家文件"）；跑 `test-core`（仓储隔离 + **测试替身的回合起点**）
  + `test-http`（上传/下载/删除/注入的端到端 + 跨租户 404）；
  ⚠️ `events.mjs` 上原来还有一个 `searchEvents`（会话内检索），**0.21.7 已随该功能整块删除** ——
  它的两条纪律（`LIKE` 通配符必须转义、`events` 表无 `tenant_id` 故须先证归属）留在了原处的注释里。
- **导入真实文档后发现"搜不到"时**（先跑 `test-knowledge.mjs` 区分是解析问题还是检索问题）；
- 改动数据库迁移后；
- 出包前（见 §8）。

`audit-layering.mjs` 的判定是架构纪律的自动化体现：
**上游专有名词只允许出现在 `app/kernel/dsh-provider/`**。
若它报红，说明升级影响面正在失控，必须修掉再继续。

## 7. 对外提供服务

### 7.1 ⚠️ 改成非本机监听前必读

默认只监听 `127.0.0.1`（只有本机能访问）。这是**刻意的安全默认值**。

把 `STI_HOST` 改成 `0.0.0.0` 或内网地址之后，**必须**同时做到：

| 项 | 要求 |
|---|---|
| **TLS** | 由反向代理（Nginx / IIS / Caddy）终止 TLS。平台自身不实现 HTTPS |
| **信任代理头** | ⚠️ **必须设 `STI_TRUST_PROXY=1`**（或 config.json 里 `"trustProxy": true`）。不开它：所有外部用户会被当成**同一个 IP**（限流的真正来源读不到，一节车厢的人互相连坐），且"是不是 HTTPS"判定读不到反代传来的头 —— `Secure` cookie 不会加。开了它才采信 `X-Forwarded-*`，所以**只在前面确实是你自己配的反代时开** |
| **访问控制** | 反向代理上限制来源网段，不要直接暴露到公网 |
| **CSRF** | ✅ **已交付**（M1）。两道：cookie 带 `SameSite=Lax`；服务端另有 `Sec-Fetch-Site` / `Origin` 显式判定，跨站的状态变更请求回 `403 csrf_blocked` 并写审计。⚠️ 反代**不要**剥掉 `Origin` / `Sec-Fetch-*` 头，否则显式判定会退化 |
| **Cookie** | ✅ `HttpOnly` + `SameSite=Lax` 恒开；`Secure` 在**判定为 HTTPS 时**自动加上 —— 判定依据：直连 TLS，或 `x-forwarded-proto: https`（**仅当 `trustProxy` 打开时采信**）。所以反代**必须**设置 `X-Forwarded-Proto`，且 `STI_TRUST_PROXY=1` 必须打开 |
| **限流** | 平台内已有单进程限流（`STI_RATE_LIMIT`；登录接口另有更严的 `STI_RATE_LIMIT_LOGIN` 与按账号退避锁定），但公网入口仍应在反代上再限一层 |
| **会话超时** | `sessionTtlHours`（默认 12 小时） |

> 原因见 `docs/feasibility.md` §7.2：这个平台会在服务端持有模型凭据，
> 从「本机自用」变成「多人可访问」是**安全模型的分叉**，不是改个监听地址那么简单。

### 7.2 反向代理示意（Nginx）

```nginx
location / {
    proxy_pass http://127.0.0.1:3090;
    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    # 会话流式输出：必须关闭缓冲，否则事件会被攒着不发
    proxy_buffering off;
    proxy_read_timeout 3600s;

    # WebSocket 桥（实时流）
    proxy_http_version 1.1;
    proxy_set_header Upgrade    $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

> ⚠️ 两条与安全直接相关的反代纪律：① **不要**剥掉 `Origin` / `Sec-Fetch-*` 头（§7.1）；
> ② 反代配置里**不要**把 `X-Forwarded-For` 设成固定值或把整个 `$proxy_add_x_forwarded_for`
> 换成 `$remote_addr` 之外的假值 —— 平台在 `trustProxy=1` 时按**最左**地址做限流依据，
> 头写错等于限流形同虚设。

### 7.3 后台常驻与服务化（systemd / Windows）

`start.cmd` / `start.sh` 是**前台进程**：窗口关掉服务就停了，适合试运行。
正式上线要"开机自启、崩溃拉起、日志有人收"——用系统自带的服务机制，**不要用 `nohup` 挂着**。

**Linux（systemd）**：

```ini
# /etc/systemd/system/sti-harness.service
[Unit]
Description=STI HARNESS
After=network.target

[Service]
Type=simple
User=sti                             # 专用低权限账号，不要用 root
WorkingDirectory=/opt/sti-harness
Environment=STI_TRUST_PROXY=1        # ← 经反代部署必须；直连部署删掉这一行
EnvironmentFile=-/etc/sti-harness.env  # 敏感项（STI_BACKUP_KEY 等）放这里，权限 0600
ExecStart=/usr/bin/node app/main.mjs
Restart=on-failure
RestartSec=3
TimeoutStopSec=15                    # 给优雅退出留时间（在途回合收尾上限 5 秒）

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now sti-harness
journalctl -u sti-harness -f          # 看 console 日志；文件日志在 data/logs/runtime.log
```

> `Restart=on-failure` 依赖平台的**退出码纪律**：正常信号干净退出 = 0（不重启），
> 崩溃或收尾超时 = 1（自动拉起）。所以 `kill` 之后服务**不会**"神秘复活"，崩溃则一定会。

**Windows**：用**任务计划程序**（触发器「计算机启动时」；操作 = `node.exe`，参数 `app\main.mjs`，
"起始于"设为项目根；勾上"任务失败时按以下频率重新启动"），或用 NSSM 注册为服务。
两点注意：① 运行账户要能读写 `data/`（建议专用账户，不要挂在个人账户上——换人即断）；
② `STI_TRUST_PROXY` 等环境变量在系统环境变量里设，或写进 `data/config.json`（见 §3.2）。

## 8. 打包

打包目标是**一份绿色目录**：解压 → 双击 `start.cmd` → 能用，不装任何依赖。

打包时必须做到：

1. **排除运行时数据**：`data/`、`*.db*`、`.secret`、`config.json` 一律不进包；
2. **排除开发残留**：`node_modules/`（本工程刻意不用）、`tools/*-out.txt`、临时文件；
3. **保留**：`app/`、`public/`、`tools/`、`docs/`、`VERSION`、`start.cmd`、`check.cmd`、`start.sh`、`check.sh`、`README.md`；
4. **`.cmd` 文件必须是纯 ASCII**（`start.cmd` / `check.cmd` 头部注释已说明原因：`chcp 65001` 之后混入非 ASCII 字节会让 cmd.exe 解析错位，把注释当命令执行）；
5. **出包后必跑一遍扫描**，断言包内**不含**密钥、数据库文件、上传文件（打包即扫描这条纪律的来源）；
6. **出包前跑 §6 两个回归脚本**。

版本号**单点维护**在根目录 `VERSION` 文件，`start.cmd` / `check.cmd` / 自检 / 状态页都从它读。
M0 尚未提供自动打包脚本（`tools/make-dist.mjs` 计划随 M5 交付）。

> **单容器交付 ≠ 多容器编排**。若客户强制要求容器化，就交一个**单进程容器的 Dockerfile**
> （把整个绿色目录塞进镜像，`CMD ["node","app/main.mjs"]`），
> 但**不做** Compose 多容器编排 —— 那是本项目明确不做的事（见 `docs/architecture.md` §10）。

## 9. 排障

### 9.1 常见现象

| 现象 | 原因 | 处理 |
|---|---|---|
| `[x] Node.js 版本过低` | Node < 22.13 | 装 22 LTS 或 24：https://nodejs.org |
| `[x] Node.js not found`（双击 .cmd 时） | 未装 Node，或只装了微软商店的 stub | 从官网装正式版。启动器用 `node -v` 而非 `where node` 检测，正是为了识破商店 stub |
| `端口 3090 已被占用` | 上一次没退干净，或与别的程序冲突 | `STI_PORT=3091 node app/main.mjs`；或找出占用进程 |
| 自检第 7 项黄灯 `need-token` | 上游要求会话鉴权 | 按 §4.1 配 `DSH_ORIGIN`（带 `?token=…`） |
| 自检第 7 项黄灯（版本门禁） | 上游版本不在已验证矩阵 | **不阻止启动**，但应先跑 §6 回归再上生产 |
| 页面打开是空态 / 提示接口失败 | 用 `file://` 直接开了 `index.html` | 通过 `http://127.0.0.1:3090` 访问 |
| `数据库迁移被拒绝执行` | 有人改动了**已应用过**的迁移文件 | 不要改历史迁移。恢复原文件，或新增一个迁移文件 |
| 迁移提示断链（gap） | 迁移版本号跳号 | 补齐缺失的迁移文件，迁移链必须连续 |
| **接口 500，日志写 `no such column: <列名>`** | **跑着的是旧代码**：迁移已把该列删掉（`ALTER TABLE … DROP COLUMN`），而服务进程是在删列**之前**启动的，内存里仍是旧的 SQL。**公开接口往往全绿**（它们多半不读那张表），只有走到读该列的那条路径才炸 —— 例：`no such column: is_admin` 只在登录**成功**后才出现（登录失败走的是不含该列的查询），所以"随手试个错口令看着正常"不能说明服务没问题 | **重启服务**（`Ctrl+C` 后重新启动，或双击 `start.cmd`）。判据有三条，任一条成立即可确诊：① 启动横幅的**版本号 / 路由条数**与 `VERSION` 对不上；② `/api/system/status` 里 `platform.startedAt` **早于**最后一次迁移时间；③ `/api/system/routes` 与当前代码的路由表对账有差异。**改过 schema（尤其删列）之后一律重启** —— 这比排查快得多 |
| 日志里出现 `501 not_implemented` | 该接口尚未交付（计划在后续里程碑） | **预期行为，不是故障**。响应体会写明计划在哪个里程碑交付 |
| 响应头出现 `x-sti-passthrough` | **这不该发生**（M3 起七项中间件全部实装，该头应永远为空/不存在） | 缺陷。说明有中间件退化为占位了，请带 `requestId` 报回来 |
| `403 quota_blocked` | 触发了配额规则（`quotas` 表 block 模式） | **预期拦截**。管理员在「配额与用量」页调整规则或提高上限；`warn` 模式只加响应头 `x-sti-quota-warning` 不拦截。注意：token 类指标是**软闸**（已用量 ≥ 上限时阻断**下一次**提交），精确事前拦截要等 model gateway（尚未排期） |
| 登录后所有接口 401 | cookie 没带上（跨站 / 反代改了 `Host` 或剥了 `Cookie`） | 检查反代的 `proxy_set_header Host`；或改用 `Authorization: Bearer <token>` |
| `403 csrf_blocked` | 用 cookie 认证发状态变更请求，但来源被判为跨站 | **预期行为**。浏览器脚本请改用 `Authorization` 头；或确认反代没有改写 `Host` / 剥掉 `Sec-Fetch-*` |
| `409 不能移除组织最后一个所有者` | 保护规则：避免组织没人能管 | **预期行为**。先把另一个账号提为 `owner` |
| 改了口令却还能继续用旧会话 | ——（这不该发生） | 改密与停用都会吊销该用户全部会话。若没生效，是缺陷，请带 `requestId` 报回来 |
| **导入 PDF 后状态是 `failed`** | 机器上没装 `pdftotext` | **预期降级**。装 poppler-utils，或改用 txt/md/csv/json/html（见 §2.1）。文档详情页会写明具体缺什么 |
| **导入 DOCX/XLSX/PPTX 后状态是 `failed`** | 机器上没装 LibreOffice | **预期降级**。装 LibreOffice，或用 `STI_SOFFICE` 指向 `soffice` |
| **知识库页显示 `纯文本检索` 徽标** | 未配向量模型（`STI_EMBED_*` 为空） | **不是故障**，是设计好的降级。要语义检索就按 §2.1 配置 |
| **中文搜不到（英文能搜到）** | 分词没走 bigram（**这不该发生**，是缺陷） | 先跑 `node tools/test-knowledge.mjs`。中文检索**不得裸用 `unicode61`**，若回归红请带输出报回来 |
| 检索结果里某条显示"无定位信息" | 该分块来自无标题、无页码的纯文本 | **预期标记**（不是故障）。导入 Markdown 或带页的 PDF 可保留定位信息 |
| **检索比预期慢** | 向量那一路是暴力扫描，耗时与**库内分块总量**成正比 | 见 [`benchmark.md`](benchmark.md) §8 的规模边界；小规模库可临时关掉向量（清空 `STI_EMBED_PROVIDER`） |
| 改了 `fts.mjs` 的 SQL 后"常见词和稀有词一样慢" | 查询计划退化成全库扫描（`JOIN` 被重排） | 那处**必须**是 `CROSS JOIN`。跑 `node tools/bench-search.mjs --chunks=20000 --repeats=10` 看稀有线是否仍在 1 ms 级 |

### 9.2 看日志

M0 日志输出到控制台（`start.cmd` / `start.sh` 的窗口）。
提高详细度：`STI_LOG_LEVEL=debug node app/main.mjs`。

每条日志带 `requestId`（如 `[req_f8acb78d597a]`），响应头 `x-request-id` 是同一个值 ——
**从浏览器抓到的 requestId 可以直接在日志里定位那一次请求**。

### 9.3 请现场人员提供什么

出问题时，让对方跑 `check.cmd`，把**完整输出**（从 `STI Harness version:` 到 `end of report`）
连同启动窗口里打印的启动横幅一起发回来。
自检输出里已包含定位问题所需的全部关键信息（版本、路径、迁移状态、内核状态、端口、中间件边界），
且**不含任何密钥内容**（主密钥只报指纹）。

**0.15.0 新增：接真实内核从「登上服务器手改 JSON」变成页面上的三步**（评估报告 §3 阻断一里「配置门槛」那一半）

此前接真实内核**唯一的办法**是：SSH 上服务器 → 手改 `data/config.json` → 重启，而地址里还夹着一个令牌。
对企业的 IT 来说，这是最典型的「第一天就撞墙」。现在在**概览页**（管理员首次登录时还会有一层**阻断式引导**）
里三步做完：**① 粘贴地址 → ② 点「检测连接」→ ③ 保存并启用 → 重启**。

- **检测是独立的一步**，不是保存时顺带做的。它按**用户排查问题的顺序**给结论
  （地址 → 连通 → 识别 → 鉴权 → 版本），并给**可照着做的下一步**；六类失败给**六个不同**的下一步 ——
  分类错了就等于让人去改没坏的东西。页面上还摆着**可核对项**（地址 / HTTP / 服务 / 类型 / 版本 / 令牌来源），
  因为「连不上」和「连上了但令牌没被识别」必须能一眼分开。
- **保存前当场证伪**：`unreachable` 与「有响应但不是内核」这两种状态**默认拒绝保存**（`409`，
  并把完整诊断一起带回来）。**检测没通过就不保存**（0.21.5 起，没有"跳过检测"的口子）——
  前端把「保存并启用」置灰只是把话说在前面，判据在服务端。
- **令牌以密文落盘**（AES-256-GCM，键名 `dshTokenCipher`），同一事务里清掉明文键；
  界面、日志、`/api/system/status` 都不回显它。⚠️ **Windows 上文件权限不可靠** ——
  所以这里选的是「密文」而不是 `chmod 0600`（后者在 Windows 上基本等于没做）。
- **检测与保存都是管理员动作**（`system:write`，0.15.0 起管理员具备）：服务端主动去连调用方指定的地址
  是 **SSRF 形状**，不能开给任何登录用户（成员与访客连「检测」都发起不了）。
- **保存成功 ≠ 内核可用**：响应与页面把两件事分开说 —— `saved`（写盘了没有）与
  `switched.ready`（当场切换后内核能不能用）。后者为假是真实存在的一种结果
  （检测通过之后内核掉线了），界面照它说话，不替它乐观。
- ⚠️ **地址来自环境变量时**页面会明说「在这里保存不会生效」（环境变量覆盖配置文件）——
  不这么说，用户会反复保存、反复重启，然后认定这个功能是坏的。
- **不改老行为**：不填就还走环境变量与 `data/config.json` 的老路径，**升级后一个字符都不用动**。

**0.15.0 的真机验收 + 发版收口：抓出八个缺陷**（前四个的共同点是「测试全绿但真机不对」；
后三个是收口那几步抓出来的，共同点是「**没人报错，所以没人会去看**」。都已修并补回归钉子）：
① **上游产品名随运行期字符串穿透到界面** —— 在接入向导里填一个普通 Web 服务的地址，页面显示
「该地址有响应，但不像是 DSH（HTTP 200）」；`tools/audit-layering.mjs` 是**源码静态扫描**，
看不见运行期，所以审计全程是全绿的。现改为**三道防线**：静态审计（源码层）+ provider 只报**事实**、
话由产品层自己拼（设计层）+ 运行期抹名（兜住上游错误体这类我们控制不了的文本）；
并加了一条 **HTTP 级运行期扫描**（代表性接口的响应体里不得出现上游名）—— 它当场又抓出两处。
② **「需要重启」是个假警报**：配置里的 `kernel=auto` 是**解析策略**不是模式，与运行中的 `external`
永远不相等 ⇒ 每个默认部署都会常亮一条永不消失的提示；地址里内嵌令牌的历史配置同样恒不相等。
**恒真的提示等于噪声**（用户很快学会忽略它）。
③ **用量漏账**：上游**没有独立的 usage 事件**，用量挂在 `assistant/message` 上，而**记账与汇总两份实现
都只认** `type='usage'` ⇒ 真内核上每一轮都记 0 行，工作台显示「累计 tokens 0」—— 那不是「没数据」，
是一句**与事实相反的话**（实测一轮真实消耗 562 输入 + 6,656 缓存读 + 2 输出）。已合成**单一真源**；
并把外部验收里那句「用量可能为 0（上游未回报 usage 时）」的**假前提**改成「**有观测就必须有账**」的交叉核对。
④ 工作台「累计 tokens」只加输入+输出，**把缓存读漏掉** —— 一轮真实处理 7,215 token 的会话显示成 559。

**收口时又抓出三件，性质不同，但都属"没人报错所以没人会去看"那一类**：
⑤ **发布包里躺着一枚真令牌** —— 做的是"**独立解包 → 换一套规则复扫**"（不复用打包脚本自己的结论），
在 `tools/test-core.mjs` 里抓到一枚**从本机 `data/config.json` 整行抄来的真实内核令牌**。它会**随包分发**，
而打包脚本每次都报「泄漏 0」——因为它的内容扫描**只覆盖 `app/`**。已把令牌形态扫描扩到
`app/ + public/ + tools/ + docs/`，并把打包本身写成**门禁项 `packscan`**（详见本节末尾那一段）。
⑥ **门禁自己的取末行逻辑会"静默降级"** —— `judge()` 原先写的是 `metric === 'violations' ? … : fails`，
任何**新指标**都会被当成 `fails`，于是"末行名字对不上"被报成"没找到末行"，**指错排查方向**
（人会去怀疑脚本没跑完，而不是怀疑自己忘了登记新指标）。已改成按 `metric` 动态构造。
⑦ **老配置里的明文令牌没人提醒** —— 本版最大的改进是"令牌密文落盘"，但**在那之前写下的配置不会自己变**。
它的表现是**一切正常**：服务照起、对话照跑、页面照显示"已接入"，代价是每一份**备份包与快照**
都连带带走了调上游内核的凭据。按本项目自己的纪律（§10 第 14 条：**"不做也不会报错"的运维项
必须在自检里有位置** —— 备份就是先例），补了**自检第 [15] 项「内核令牌落盘卫生」**
（只读、不改配置，两种明文形状分开说）+ **`tools/seal-kernel-token.mjs`**（就地封存：默认只报告，
`--apply --force` 才写；写前备份、写后往返校验；**令牌不打屏，连地址里那一段也先隐去**）。
⑧ **门禁自己有个假绿**：`external` 这一项在"上游不在场"时自报 `DONE fails=0 skipped=1`，
而门禁只认一种 SKIP 拼法（`^SKIP$` 单独一行）——于是**"这次一条都没验收"被记成 ✓**，
汇总里的"通过 13/14"也跟着虚高。（它是第 ⑤ 步把配置封成密文后，外部验收当场 SKIP 才露出来的：
**顺手做的一步，反而把一段假绿照出来了**。）已改为按末行的**结构化字段** `skipped=N` 判，
提示语怎么写都不影响判据。⚠️ 修的时候又踩一次同一个坑：第一版从正则**匹配结果**里取"末行"，
而它只是 `DONE fails=0` 这一段、不含同行后面的 `skipped=1`，**改红实验里它仍然是绿的**。

**本版（0.21.12）还不能做什么**：

- **工作区没有「平台侧」的权限控制（0.21.6 起）**。工作区现在对**全组织可见**，工作区里的会话
  按**组织角色**定档（`owner` / `admin` = 完全权限，`member` = 工作区内修改，`viewer` = 仅可查看）。
  平台**不再提供"某个工作区单独授权给某个人"**，也没有 `open` / `restricted` 可见性 ——
  那套三档访问权限 + 工作区级授权名单在 **0.21.6 整块删除**。原因：上游内核自己有一份工作区权限
  三档，而平台**没有任何接口去改上游那一份**（真实内核 21 个契约方法里与权限沾边的只有工具调用
  审批，且走事件流、**不是 RPC**），平台这份是"**改了不生效的第二份真相**"——
  判据是「**一份改了不生效的权限配置，比没有权限配置更糟**」（它让人以为已经管住了，
  比"明确不管"危险得多，因为会改变人的谨慎行为，且不出错时毫无迹象）。
  **要隔离请用多租户 / 多组织**（那是平台确有把守的边界），不要指望工作区级授权。
  ⚠️ 一处随之变化的语义：从前"看不见的工作区回 404"，现在**全组织可见**，
  404 只剩"真的没有这个 id"一种含义；**档位不够是 403**（不是 404）。
- **自定义角色授权尚未接通**（0.20.0 落了 `role_grants` 表，**没有消费方**）：平台当前只有
  `owner` / `admin` / `member` / `viewer` 四个**内置**角色（`permissions.mjs` 的 `ROLE_MATRIX`
  硬编码），身份模块也只有 `GET /api/identity/roles` —— **建不了自定义角色，也授不了它的具体权限**。
  `role_grants` 表结构在库里（迁移 `0020`）但判定层不读它。这是**待收口项**；
  在接通之前，请按内置角色分配（`GET /api/identity/roles` 回的就是这四个）。
- **不要直接暴露到公网**。必须经 TLS 反向代理 + 来源网段限制（见 §7）。
  另外 CSP 的 `style-src` 仍带 `unsafe-inline`（内联样式属性还没迁到 class），
  所以不要指望 CSP 兜住"样式注入"这一类。
- **成本金额是估算，不是账单**。它按**当前登记的单价**算，**不追溯也不快照** ——
  改一次价，历史用量的金额就跟着变。要留证请在改价前先导出。
  而且**未登记单价的条目金额显示为「未定价」而不是 0**；**只有给会话登记过模型**的用量才归因得起来，
  其余落在「未归因」桶里（平台**不**拿默认模型的价去套）。
  真实计费以供应商结算为准，本平台也不转发请求（不是 gateway）。
- **附件分三条通路，页面会如实分别标注**：**图片**（PNG / JPEG / WebP / GIF，按**魔数**识别）
  作为内容块**真的送给模型**（本轮合计 ≤ 10MB）；**文本类**（单文件 ≤ 64KB、本轮合计 ≤ 96KB）
  的正文被拼进本轮 prompt；**其余二进制**（PDF / ZIP / DOCX…）**只登记、可下载、标注"不提交"**。
  ⚠️ 通用文件的"不提交"**不是"上游没有这个能力"** —— 官方契约里确有"模型收到一行**只读路径**"的设计，
  但 **2026-10-02 对着运行中的上游实测**后确认：那条通路**只对上游自己的浏览器入口开放**
  （host 侧内部投影），**不在对外 wire 契约上** —— 写入 `fileUploads/upload` 可用、却只返回
  **内容寻址 id（无路径）**，而 wire 的 `session/prompt` **不接受 `{type:'file'}` 内容块**、
  只读侧 20 个候选方法全部 404。所以本平台**无从接线**（详见 `roadmap.md` 的 B 档结案）。
  大文件请走**知识库导入**，不要指望对话附件。
- **知识库挂载是"上下文注入"，不是"模型自主检索"**。平台在**你按下发送**时对已挂库做**一次**检索
  （top-k **5**、注入片段合计 ≤ **16KB**），把命中片段拼进本轮 prompt 的**尾部**。所以有四条要清楚：
  ① **不是 agent 式多轮自主检索** —— 问一句查一次，不会为了追一条线索再查第二次（那要平台侧工具执行，
     而上游 wire 契约不提供）；
  ② **没有 rerank** —— 按检索得分排序取前 5，未接模型重排（与知识库页的能力矩阵一致）；
  ③ 命中片段与附件正文**共用同一段注入区**（都在用户原文**之后**），前端按标记**形态**把两者**一次**剥干净 ——
     气泡里永远只显示你自己打的字，注入内容只在**知识卡片 / 附件回执**上如实呈现；
  ④ 检索**同步发生在回合开始时**，会先占掉一点"首字之前"的时间；检索仍是 **FTS5 / 暴力扫描**那套，
     规模边界与 10 万 chunk 的实测分位见 [`benchmark.md`](benchmark.md) —— **别拿它去对 20 万+ 的库**。
- **助手正文的 markdown 是"安全子集"，不是完整引擎**。渲染器（`public/app/79-wb-render.js`，0.19.0 起）
  刻意只做常见子集：标题 / 列表 / 引用 / 代码块 / 行内代码 / 粗斜体 / 链接；**不渲染图片、表格、
  原始 HTML**（HTML 一律按字面文本显示），不闭合的语法按原样输出。要完整 CommonMark 需引入
  外部库，与零依赖红线冲突；UI 固定文案仍按纯文本写，渲染器只用于模型产出的内容。

- **"停止"不等于"上游已经停手"**。平台能保证的是"不再接收"，取消是**通知**；
  上游若忽略它，额度仍在消耗。页面会按 `upstream.ok` 分别提示，拿不准时请以用量页的数字为准。
- **OpenAPI 规格不是逐字段契约**。它给接口清单、权限模型与状态码语义，不含每个字段的 JSON Schema
  （平台用运行时校验）。想靠它自动生成严格类型客户端，会缺一层。
- **调度器不是 cron，也不是高可用调度**。只认 `interval` / `dailyAt` 两种规则且 `dailyAt` 按 **UTC** 解释；
  **进程不跑任务就不跑，且不补跑错过的**；没有分布式锁（单进程即单调度者）。
  把"进程保活"当成运维职责，而不是平台假装已经兜住。
- **告警不再因为"上游抖一下"就丢，但整体停机仍会丢**。0.11.1 起失败的投递**落库入队**
  （`notify_deliveries`），由定时任务 `notify.retry` 指数退避重投（最多 6 次，超限转 `dead` 但
  **保留可见、可手动重投**）；队列条数在**通知渠道页**可见。⚠️ 但队列的重投是**本机单进程**的
  （与调度器同一约束：无分布式锁）—— 平台**整体停机期间**发生的事件仍不会补发。
  关键告警请同时保留"人主动看页面"这条路径。⚠️ 语义是 **at-least-once**：接收方可能收到重复，
  请用响应头 `X-STI-Delivery-Id` 去重（同一条投递的首次尝试与所有重投共用同一个 id）。
- **4 类通知事件全部都有产生方了（0.13.0 起），但其中一类是"会合并的"**。白名单
  （`quota.blocked` / `backup.failed` / `model.probe.failed` / `audit.anchor`）
  只说明"**允许**投递"，不等于"**真的会**" —— 所以每个事件都有一行对账表
  （`app/platform/notify/service.mjs` 的 `NOTIFY_EVENT_PRODUCERS`，有回归双向核验，不会悄悄漂）。
  0.12.1 时 `quota.blocked` 订阅了也收不到任何东西（白名单里有名字，全项目**没有一个 emit 点**）；**0.13.0 已接通**，
  并且**同一次提交里定了节流**：同一「租户 + 事件 + 分键」在 **10 分钟**内最多出站一次
  （分键 = 哪个指标被配额拦下）。
  三条必须知道的口径：
  ① **合并掉的是"通知"，不是"事实"** —— 每一次拦截仍**逐条进审计**，
  所以合并不会让任何事变得查不到；反过来也成立：**告警通道安静不代表没发生**；
  ② **节流窗口是进程内存**（与并发配额同一理由：单进程部署），重启即重新计时；
  ③ 窗口是"**先确认有人订阅、再计时**"的 —— 你没配渠道的那段时间不会白白吃掉窗口。
- **备份默认不自动，恢复只能离线**。平台**刻意不**默认播种 `backup.create` 任务（消耗型动作，
  是否占盘由运维定）—— 所以**开箱即用 ≠ 开箱有备份**，一台刚起来的机器上可能一份备份都没有，
  而这件事**不会让服务报错**。请照 §5.2「上线前必做两件事」配好，并记住三条边界：
  ① `data/.secret`（主密钥）**不在备份包内**，丢了已存凭据**永久解不开、没有后门**，必须单独保管；
  ② **恢复没有在线接口**，是停机维护动作 `tools/restore-backup.mjs`（运行中换掉自己脚下的库不可接受）；
  ③ **轮转只在自动任务里发生** —— 「立即备份」建的备份不会被自动清理。
  **自检第 [14] 项**就是用来把这三件事问出来的，别只在文档里读它。
- **删除类动作没有回收站**。0.18.0 起补上的出口里有两处是**不可逆**的：**Skill 卸载**
  （ZIP 来源连安装目录一起删；`local` 引用与越界路径只注销登记 —— 想留着请改用**停用**）
  与**备份文件删除**（只删点名的那份，删了就没了；恢复只能靠剩下的备份 + `tools/restore-backup.mjs`）。
  备份删除留着**最后一份删不动**这条底线（只剩一份时该请求被 `409` 拒绝），
  但它**不能替代**你在别处多留一份 —— 平台没有异地复制。
  界面对这两处**先说清楚再动手**（确认弹层写明不可逆），并各留审计
  （`capability.skill.remove` / `operation.backup.remove`）。
- **锚点还在同一台机器上**。`data/anchor/` 与审计链同机时防不住"有库权限的人连锚点一起改"；
  只有把 `audit.anchor` 事件配到**外部**渠道，锚点才真正具备独立证明力。
- **审计保留期不是可以随手调小的参数**。它删的是审计记录本身，调小等于主动缩短可追溯窗口；
  且 `data/archive/` 必须进备份，否则"归档"就退化成了"删除"。
- **token 配额不是精确的事前闸**。一轮提交进来后才知道 token 花多少，平台能做的是「已用量 ≥ 上限时阻断下一次提交」；要精确事前拦截，需要 model gateway 本体（模型中心只做配置与探活，**不做转发**）。
- **模型中心不会替你转发请求**。它把「配了什么」与「本机实际能调什么」（探活结论）分开呈现，但不改变调用的物理路径 —— 别把它当成网关。
- **审计链只防"事后改数据"**。有写权限的人整表重写链仍防不住 —— 0.8.0 起多了"归档 + 链基准 + 链尾锚点"三件套，
  但**只有锚点出站之后**才第一次具备独立证明力（见上一条）。
- **per-tenant 可见性是保守并集**。契约层 `listTools` 不带租户概念，任一租户 deny 的工具对全部租户从模型清单消失（防跨租户泄漏的代价）；页面清单仍按租户精确显示。精确隔离待契约带租户。
- **库级 ACL 的图形化授权入口已在 0.12.0 补上**（0.11.0 时只有后端接口与回归，当时界面里只能**切换可见性**）。
  现在知识库页的「库级授权」面板可以列名单 / 授权 / 撤权。⚠️ 两条要知道的：① **面板的权限口径是按库算的**
  —— "能不能列/改名单"取决于你在**这个库**上有没有 write 档，所以它**不按全局 `knowledge:write` 隐藏**，
  服务端的 `403`（看得见但档位不够）与 `404`（库对你不可见）会**原样显示、不含混成一个**；
  ② **`restricted` 是"放行名单"语义**：授权后的有效档位是「全局角色 ∪ 该库的库级角色」，
  所以给一个 viewer 授本库 `admin`，他就能在本库写 —— 授权前请确认这确实是你要的。
  脚本化场景仍可**直接调 `POST /api/knowledge/bases/:id/grants`**（见 §3.3）。
- **更新检测的对象是平台磁盘**。`check-update` 比对安装目录内容快照；「上游发布了新版本」需要市场/源（未实装）配合，现在不做也不装作做了。
- **别把百万级语料一次性导进来。** 向量那一路是暴力扫描，**10 万是实测过的规模，20 万起开始吃力**
  （见 [`benchmark.md`](benchmark.md) §8）。真要上百万级，先谈索引方案再导。
- **两步验证是"可选加固"，不是默认开启**。要账号自己在「我的账号」里登记（票据 5 分钟、
  单票最多 5 次尝试；恢复码一次性、平台不存明文）。管理员只能**重置**（清第二因子与未完成票据），
  不能代替用户登记、也看不到任何密钥 / 恢复码 —— 设备与恢复码全部丢失时，
  只能由管理员重置后重新登记。
- **CSV 批量导入不做部分失败回滚**。逐行独立处理：失败行带**行号与原因**，可只重导失败行
  （已成功的行不会重复建），导入**永不回显口令**。

## 11. 从更名前的版本升级（0.10.1）

本版本做了一次**全量更名**：产品统一命名为 **STI HARNESS**，全部标识符改为自有命名。
下面把"变了什么 / 哪些自动兼容 / 哪些必须你动手"分三块说清 —— **不写"应该没问题吧"。**

### 11.1 变了什么

| 类别 | 新命名 | 影响面 |
|---|---|---|
| 产品显示名 | `STI HARNESS` / `STI Harness` | 界面标题、页头、进程横幅、自检首行、`NOTICE`、开放接口规格 `info.title` |
| 发布产物 | `dist/sti-harness-<版本>.zip` | 解压出来的目录名也变了 |
| **库文件名** | `sti-harness.db` | **数据目录里的文件**（见 §11.3） |
| 备份包格式串 | `sti-harness/backup` | 更名前产出的包仍可校验 / 恢复（§11.2） |
| 能力清单格式串 | `sti-harness/capabilities` | 更名前导出的清单仍可导入（§11.2） |
| 环境变量前缀 | `STI_*`（`STI_PORT` / `STI_DATA_DIR` …） | **你的启动脚本 / 服务单元要改**（§11.3） |
| Prometheus 指标名前缀 | `sti_*` | **破坏性**：面板与告警里的查询要改（§11.4） |
| 请求 / 响应头前缀 | `x-sti-*` | **破坏性**：读这些头的集成、用 `x-…-token` 携带令牌的调用方都要改（§11.4） |
| 会话 cookie 名 | `sti_session` | **破坏性**：需重新登录一次（§11.4） |
| 令牌前缀 | `sti_` / `stik_` | **破坏性**：更名前签发的令牌不再被接受（§11.4） |
| 附件注入标记 | `<<<STI-ATTACHMENTS>>>` | 前端**按形态**识别，历史会话仍可读（§11.2） |
| 采纳工具 | `tools/adopt-data-dir.mjs` | 把更名前的库文件认成规范名（§11.3） |

### 11.2 自动兼容的（你什么都不用做）

1. **更名前产出的备份包**：校验与恢复都照常 —— 格式串与包内库文件名改为**形态**校验，
   且恢复出来一律落成规范名 `sti-harness.db`（不会留下一个下个版本自己都认不出的库文件）。
   ⚠️ 代价说清：格式串的**前缀**不再参与比对（`formatVersion` 与逐文件 SHA256 仍在拦），
   因此"拿错产品的包、但形态恰好相同"这类极端情况少了一层拦截。
2. **更名前导出的能力清单**：导入同样照常。
3. **更名前落库的会话**：气泡仍能正确剥掉注入段（前端按标记**形态**识别，不认死某一个字面量）。
4. **账号、密码、组织、角色、凭据、知识库、审计链**：全在库里，**不随命名改变**。

### 11.3 需要你动手的（数据目录与配置）

1. **环境变量**：把启动脚本 / systemd unit / 容器 env 里的前缀改成 `STI_`
   （变量名对照见 §3.1，那张表已是新名）。
2. **数据目录里的库文件**：本版本**不会自动采纳**改名前的库文件 —— 替使用者自动挑一个库文件，
   是最容易造成「我的数据怎么不对」的那类魔法。程序启动时会在日志里**报告**发现了什么，然后由你决定：

   ```bash
   node tools/adopt-data-dir.mjs --dry-run     # 先看计划，不写任何文件
   node tools/adopt-data-dir.mjs               # 生成规范名快照
   ```

   该工具用 `VACUUM INTO` 生成**事务一致**的单文件快照，规则有三条：
   **只复制、绝不删除原件**；**绝不覆盖**已有的规范名库；目录里有多个候选时报「无法判定」而不是替你挑。

   ⚠️ **不要用"复制 .db"的办法**。本项目实测过一次：主库 360KB，而未检查点的 `-wal` 有 **684KB** ——
   只复制主文件会**静默丢掉那 684KB**。这正是本工具改用 `VACUUM INTO` 的原因。

   采纳后确认数据齐全，**再自行删除**原件及其 `-wal` / `-shm`。
3. **`data/.secret`（主密钥）留在原位** —— 不要在搬库文件时把它和库分开，否则已加密的凭据解不开。

### 11.4 破坏性的（必须改，否则会坏）

| 变更 | 你该做什么 |
|---|---|
| Prometheus 指标名前缀 `sti_*` | 改面板 / 告警里的查询（`GET /api/system/metrics` 的 HELP 文本会给出新名字） |
| 请求与响应头前缀 `x-sti-*` | 改任何直接读这些头的脚本 / 网关规则；用 `x-sti-token` 携带令牌的调用方要换头名 |
| 会话 cookie 名 | **重新登录一次**（旧 cookie 不再被读） |
| 令牌前缀 | 更名前签发的会话令牌与 API Key 不再被接受：**重新登录**、**重新签发 API Key**（账号与密码不受影响） |
| 界面主题偏好（`localStorage` 键） | 一次性重置为默认；重新点一次即可 |

## 12. 常规升级 SOP（停 → 备份 → 换 → 检 → 起 → 冒烟）

> 适用：**同主版本内的升级**（换程序文件 + 带新迁移的那些版本）。
> 换机器 / 换库路径属迁移动作，走 §5.3；跨大版本按实施方方案走。
> §5.2 ④ 的恢复演练与 §7.4 ③ 的"真的恢复一次"，用的就是下面「回滚」一节的命令。

**六步，全程只换程序、不动 `data/`。**

1. **停服（等它自己退干净）**。`systemctl stop sti-harness`（Windows：停任务 / 服务）。
   收到 SIGTERM 后进程会排空在途请求再退出（最多 5 秒，见 §7.3），日志末行
   「收到 SIGTERM，正在优雅退出…」且退出码 0 = 干净退出。
   ⚠️ **进程完全退出前不要动任何文件**；没退干净（超时强退）先查日志再动手。

2. **全量备份（回滚的真正依赖，不做别往下走）**。趁旧版本还健康做一次备份：
   页面上「立即备份」，或等自动备份任务跑完；把新包与**它对应的备份密钥**
   （§5.2 ④ 约定的形态）一起拷到**与数据盘分开**的地方。
   ⚠️ 新版启动时会**自动应用新迁移**。「只换回旧程序」不是回滚 —— 旧程序面对
   新库不保证成立，唯一有保证的退法是从这份备份恢复。

3. **换程序文件**。解压新版 dist 到新目录；**只替换程序树，`data/` 原样保留**。
   - 默认布局里 `data/` 在程序目录内：把整个 `data/`（含 `.secret`、`backup.key`、
     `backups/`）搬进新目录；若升级前已把 `STI_DATA_DIR` 指到程序树外，这一步
     就是纯粹的换文件。
   - 启动脚本 / systemd unit 里的环境变量对照新版本 §3.1 核一遍，有新增的补上。

4. **检（先检后起）**。`node app/main.mjs --check`（Windows 双击 `check.cmd`）。
   它会**先应用新迁移**（日志逐条「已应用迁移 …」）再跑自检 —— 看末行
   「无阻塞问题」与退出码；不通过**不要启动服务**。
   顺带核对自检输出里的**主密钥指纹**：应与升级前一致（不一致 = 你拿错了
   `data/` 目录，别继续）。

5. **起服务 + 冒烟**。启动后看横幅的版本号与路由条数对得上目标版本，然后最小冒烟：
   - 用真实账号登录一次；
   - 工作台发一句话拿到回复（真上游；若页面被「尚未接入内核」拦住，说明本机没接上游 —— 先按 §4 接上）；
   - 用量页看得到刚才这条的记账；审计页看得到刚才的登录与提交；
   - 备份页能打开、能看到第 2 步的备份包。
   任何一条不对 → 直接回滚，别一边怀疑一边继续用。

**回滚（数据 + 程序一起退，顺序别反）**

```bash
systemctl stop sti-harness
# 1) 库退回到升级前（停机离线动作）
node tools/restore-backup.mjs <升级前备份ZIP> <数据目录> --overwrite
# 2) 程序目录换回旧版本，再启动
systemctl start sti-harness
```

> ⚠️ 两条容易忘的：
> ① 恢复工具会打印「目标目录没有 `.secret`」——**原地恢复时忽略这条提醒**
> （它是给"恢复到新机器"场景的）。`.secret` 与 `backup.key` 不在备份包里，
> 也**永远不要**当"多余文件"删掉。
> ② 恢复成功看末行「✓ 校验通过并已恢复」（随后有 `integrity_check` 自证）；
> 用错密钥会在校验阶段明确报"kid 不匹配"，不会恢复出半套坏数据。

## 13. 监控接入（Prometheus / Grafana）

指标端点 `GET /api/system/metrics`，Prometheus 文本格式
（`text/plain; version=0.0.4`）。**权限：session scope + `system:read`** ——
不是公开端点（指标含调用方组织的审计链长，"平台规模"不该对能碰端口的人可见）。

采集器用**专用只读账号的 API Key**（viewer 角色的账号就够：

`system:read` 在内；比管理员账号安全，也不怕"人一走 Key 就断"）：

1. 建一个 viewer 账号 → 登录它 →「我的账号 → API Key」新建（`POST /api/identity/apikeys`），
   勾 `system:read`，按需设有效期。明文 Key 只在创建响应里出现**这一次**。
2. 验证：

```bash
curl -s -H "Authorization: Bearer stik_…" https://<你的域名>/api/system/metrics | head
```

**Prometheus 抓取配置**（标准 `authorization` 走 `Authorization: Bearer`，
与 curl 同一条通路）：

```yaml
scrape_configs:
  - job_name: sti-harness
    scheme: https
    metrics_path: /api/system/metrics
    authorization:
      credentials_file: /etc/prometheus/sti-harness.key   # 只读 API Key
    static_configs:
      - targets: ['<你的域名>']
```

**指标清单**（名字以端点返回的 HELP 文本为准）：

| 指标 | 类型 | 说明 |
|---|---|---|
| `sti_uptime_seconds` | gauge | 进程运行秒数（重启变小 → 用它做重启检测） |
| `sti_process_inflight_requests` | gauge | 在处理中的平台接口请求数 |
| `sti_http_requests_total{method,route,status}` | counter | 匹配到路由的 `/api/*` 请求 |
| `sti_http_request_duration_ms` | histogram | 接口处理耗时（5ms ~ 10s 桶） |
| `sti_turns_total{result}` | counter | 提交的回合数（ok / error） |
| `sti_tokens_total{direction}` | counter | usage 事件里的真实 token 数 |
| `sti_quota_blocked_total{metric}` | counter | 配额拦截次数 |
| `sti_notify_deliveries_total{result}` | counter | 出站通知投递（ok / fail） |
| `sti_schedule_job_runs_total{result}` | counter | 定时任务执行（ok / fail / skipped） |
| `sti_active_turns` | gauge | 在途回合数（并发闸实测值） |
| `sti_db_size_bytes` | gauge | 库文件字节数（WAL 未计入；-1 = 尚未落盘） |
| `sti_db_tables` | gauge | 表 + 视图数量 |
| `sti_audit_chain_length{tenant}` | gauge | **调用方所属组织**的审计链长（不给别组织开后门） |

**四条使用边界（写进告警口径，别读错）**：

1. **计数器是进程级的，重启归零** —— Prometheus 生态的标准语义（`rate()` 靠
   重启检测处理），不是数据丢失。重启检测用 `sti_uptime_seconds` 或自带的 `up`。
2. **只统计匹配到路由的 `/api/*`**：`/upstream/*` 透传与静态资源**不在**指标里
   （它们不是"平台接口"，混进来会污染 route 维度）。
3. **抓取本身也被计数**（route = `system.metrics`），采样间隔别设太密，30s 起步即可。
4. 建议先接三块面板：请求量 / 错误率（`status` 维度）、延迟（直方图
   `histogram_quantile`）、业务量（turns / tokens / quota_blocked / notify）。
