## 0. 三句话结论

1. **0.7.0 已经跨过"能不能用"的分水岭。** P0 打通真实内核 + P0-B/C 工作台与流式 + P1-1 模型中心之后，
   它第一次同时满足"最终用户能用"与"管理员能治"两件事 —— 这是一个**可交付的智能体生产平台雏形**，不再是"治理后台 + 跑不通的对话接口"。

2. **剩下的短板集中在三处，都不是核心链路，但都是企业采购清单上的硬项**：
   ①**治理闭环缺"最后一公里"**（无定时任务底座 → 审计归档/定期备份/知识重建/探活巡检都没有落脚点；
   无通知告警 → 审批待办与配额超限没人知道；审批**无超时**，`expired` 是个死状态）；
   ②**可观测与集成面为空白**（无 `/metrics`、无 OpenAPI 导出、无成本（token→金额）核算）；
   ③**两处"自己承诺过但没做"**（配额 `concurrent` 真闸、审计保留与链尾锚定）。

3. **真正不能加的东西比该加的多。** 这份材料花了近一半篇幅讲**不该加什么** ——
   因为本项目最大的风险不是"功能不够"，而是**定位漂移到 MOVO 的赛道**（多容器、Python/Vue、内容生成生产线、Skill 市场、工作流引擎），
   那会一次性摧毁它唯一真正的差异化：**零依赖 + 单进程 + 契约纪律 + 治理深度**。

> **一句话定位**：它是**企业内网的智能体生产与治理平台**，不是"什么都能干的全家桶"。
> 凡是"生成内容""编排复杂流程""跑本地终端"的事，本项目的正确答案几乎都是**做成 Skill / 工具挂到能力分发层**，而不是写进平台代码。

## 3. 🟡 需要**完善**的既有能力（不是缺功能，是现有功能有真实短板）

每项都带证据；按"企业采购清单上的硬项"排序。

### 3.1 ✅ 已施工（0.8.0）· 审批队列**没有超时**，`expired` 是个死状态　【证据：`approvals.mjs:28` / `governance.mjs:18`】

`APPROVAL_STATUSES` 里定义了 `'expired'`，但**全仓没有任何一条代码会把它写进库**。
后果：一个没人处理的审批会**永远停在 `pending`**，队列只增不减；发起方的回合会一直挂着。
**企业视角这是真问题** —— "审批卡住导致业务停摆"比"审批被拒"更难排查。

**建议**：加 `approvalTtlMs` 配置；由定时任务（见 4.1）or 惰性判定把它转 `expired`，
并在工作台上把超时回合明确置为失败（**不静默消失**）。回归：超时后 `decide()` 必须拒绝（不能批准一个已过期单）。

### 3.2 ✅ 已施工（0.8.0）· 配额 `concurrent` **至今未实装**　【证据：`quotas.mjs:16,26,60`】

`METRICS` 里有它，`consumed()` 如实返回 `0` + `unknownMetric: true`（诚实，但没有闸）。
企业最容易被"一个租户跑满并发拖垮平台"打穿。

**建议**：在内存里维护 `tenantId → 进行中回合数`（提交时 +1、收流/失败时 -1，用 `try/finally` 保证成对），
超限直接 429。**这是纯内存计数，零依赖**。回归：并发提交 N+1 时第 N+1 个被拒 + 收流后计数归零。

### 3.3 ✅ 已施工（0.8.0）· 审计**没有保留策略、没有归档、没有链尾锚定**　【证据：`audit.mjs` 全文无 retention/purge】

哈希链能防"事后改一行"，但**防不了"整表重写"**（有写权限的人重算整条链）。这一点 0.6.0 就写明了，M5 承诺过但没做。

**建议三件套**（全部零依赖）：
1. **保留期**：`auditRetentionDays`，超期记录归档到 `data/archive/audit-YYYYMM.jsonl`（只读落盘）后从主表删除，删除动作本身入链；
2. **链尾锚定**：每日把「当日最后一条 hash + 记录数 + 时间」写进 `data/anchor/YYYY-MM-DD.txt`，并由定时任务在日志中打印；
3. **可选的出站**：把锚点 POST 到外部（见 4.2 Webhook）—— 有了外部副本，整表重写才真的防得住。
**没有第 3 条时，锚点文件必须是只读挂载或异地**，否则锚点和链在同一台机器上等于没锚。这个边界要写进文档。

### 3.4 ✅ 已施工（0.9.0）· CSP 带 `'unsafe-inline'`　【证据：P0-D 记录】

前端大量内联事件属性，去不掉就只能带着 `'unsafe-inline'`，使 CSP 的 XSS 防护力大打折扣。
**建议**：内联事件改事件委托 + 外链脚本。这是纯前端重构，但收益明确（安全响应头从"形式合规"变"真防护"）。

**落地结果（0.9.0）**：`script-src` 收到 `'self'` —— 76 个 `onclick` + 2 个 `onchange` + 1 个导航
全改成 `data-act` / `data-change` / `data-nav` + 文档级事件委托，首屏两段内联脚本外链为 `public/boot.js`。
**顺带发现**：`javascript:` URI 同属 `script-src` 管辖，3 个 `<a href="javascript:void(0)">` 已一并改 `href="#"`
（若只改 `onclick` 会变成"点了没反应且不报错"的链接）。
**明确保留**：`style-src` 的 `unsafe-inline`（123 处内联样式属性，危害量级不同，理由写在 `security-headers.mjs`）。
详见 `architecture.md` §7.6 与 `roadmap.md` P1-3 / 3.4 段。

### 3.5 ✅ 已施工（0.8.0）· 知识导入**失败即终点**，无重试 / 无增量重建　【证据：`knowledge/service.mjs:239`】

文档解析失败置 `failed` 并留下真实错误（这点做得对），但**没有"重试"入口**，
补装 `pdftotext` / LibreOffice 之后只能删了重传。企业场景里"先导一批、发现缺依赖、装完再补"是常态。

**建议**：① 加 `POST /api/knowledge/documents/:id/retry`（复用原文件重新解析）；
② 知识库加"重新向量化"（换 embedding 模型后必须重算，否则新旧向量不同源却混在一起比 —— **这是个真实的一致性隐患**，
   现在模型中心能换默认向量模型了，这个隐患就**从理论变成了现实**）。

### 3.6 ✅ 已施工（0.9.0；附件的**图片通路** 0.10.0 补齐）· 工作台的"最后一公里"交互：停止 / 重生成 / 附件 / 会话内检索

四个"眼前项"全部可达，且都落在**服务端**（不是前端糊一层壳）。关键设计判断如下 ——
完整清单见 `docs/roadmap.md` 的 **3.6 交付清单**，实现细节与实测缺陷见 `docs/architecture.md §7.7`。

**① 停止 = 两件事，不是一个 `ok:true`**
断开读取是前端 `AbortController`（**不需要服务端端点**）；通知上游别跑了是
`POST /api/kernel/sessions/:id/cancel`（省的是上游算力 / token）。两者混成一个成功响应，
等于把"平台已停手"偷换成"钱不再花"。所以响应里 `upstream: {attempted, ok, error}` 是**独立字段**，
页面据此分别说话（"已停止接收"与"已通知上游"是两句不同的话）。

**② 重生成**：`wbRegenerate()` 复用 `wbRunTurn()` 重打一次流，**不撤销上一轮**
（按钮 `title` 里写明，不装"回退"的样子）。

**③ 附件**：迁移 `0012_session_attachments` + 独立仓储 `app/data/repositories/attachments.mjs`
（对象不是语义事件，生命周期与 append-only 的轨迹不同，所以**单独一张表**）。
- 上传契约**刻意不用 multipart**：元数据走 query（`?filename=`），body 就是文件本身。
  手写一个"差不多能用"的 multipart 解析器，出错方式是**静默地把文件截断或错位**，比不支持更糟。
- 文本 / 二进制**按内容判定**（有 NUL 字节或非法 UTF-8 序列 → binary），**不看扩展名**；
  它决定"能不能注入本轮上下文"。
- 只有 text 且 ≤ 64KB 的附件注入（本轮总量 ≤ 96KB，上传单文件 ≤ 8MB 超限 **413**）；
  **二进制附件**在 `attachments.skipped[]` 里**逐条点名带 `reason`**，页面上如实标注结局。
- ⚠️ **0.10.0 更正一处硬错误**：0.9.0 在这里写过一句**假话** ——「平台的 `readAttachment` 契约是
  "读上游**已有**的附件"，**没有**"给上游传一个新附件"的通道」。真相是**两条通路**，都不是"传不上去"：
  · **写入通道就在 `submitTurn` 的 `content` 内容块数组里**（上游 `PromptContentPart` 定义了
  `{type:'image', mediaType, data:base64, name?}`），而我们的 `toBlocks()` 对数组**一直原样透传** —— 这条路本来是通的；
  当时只看了 `readAttachment`（"读"）就推断"没有写通道"，是**只看了契约的一半**。
  · **0.10.0 已接通图片通路**：PNG/JPEG/WebP/GIF 按**内容魔数**识别后，作为 `{type:'image'}` 内容块**真的送给模型**
  （见下"0.10.0 补记"与 `architecture.md §7.7`）；其余二进制（PDF/压缩包…）走上游的**只读保存路径**通路，
  平台**尚未接通**，探针已列入 `tools/verify-upstream.mjs` 的候选清单。
- 删除**落到字节上**：只删元数据是假删除；删不掉要如实回报 `bytesDeleted: false` + 原因。
- 仓储层每一条 SQL 都带 `tenant_id` **且带 `session_id`**，不允许"先查会话再判断归属"的间接推理；
  `hydrate()` **不输出 `stored_path`**（部署机目录结构不进响应，换机器就成死链）。

**④ 会话内检索放服务端**：工作台一次只回放最近 2000 条事件，纯前端过滤会在长会话里给出
"搜不到"的**错误结论**。LIKE 通配符必须转义（用户输入一个 `%` 否则变成"匹配一切"）；
只认"可见文本（`text`/`delta`）"命中，把只命中结构化字段的假阳性**排除并如实报条数**
（响应带 `structOnlyMatches`），页面原样转述服务端的 `scope` / `note`。

**这一轮回归抓出 4 条真实缺陷**（都已修复并加用例钉住）：
① mock provider **串轮** —— 一次"停止"会污染此后每一轮（回合起点错位），
   修法是 provider 自己记 `turnBase`，**刻意不认**调用方给的 `fromSeq`（两套编号）；
② 中文名附件下载**必 500** —— HTTP 头值只允许 ASCII，修法是 ASCII 兜底名 + `filename*=UTF-8''`；
③ "请求体过大"被吞成 **500** —— `toHttpError` 只认 `AppError`，这是 M0 起就潜伏的缺陷，
   直到附件上传第一次真正走到 413 这条路才暴露；
④ 工作台的 `notice` **写了却从不渲染**（4 处写、0 处读）—— 最严重的是"模型已登记"那条，
   用户在成本页看到用量进「未归因」桶，而界面当时想说"已为本会话登记模型"。
四条里有 3 条属于"**写了但没接上**"型：不报错、日志干净、页面看着正常，
只有断言到"用户最终看到什么"才抓得住。

**0.10.0 补记 · 图片真的送给模型（把上面那处硬错误补上）**

上游对**图片**与**通用文件**是两条根本不同的通路（`@deepseek-ai/dsh-attachment` 官方文档原文）：

| | 图片（PNG / JPEG / WebP / GIF） | 通用文件（PDF / ZIP / DOCX…） |
|---|---|---|
| 字节是否到达模型 | **到达** —— 作为 `{type:'image'}` 内容块随 `submitTurn` 提交 | **不到达** —— 模型只收到一行**确定性句柄文本** + 一个**只读保存路径** |
| 上游做法 | 校验 → 规范化（EXIF 摆正、去元数据、缩放、转 WebP/JPEG）→ 送 `ImageBlock` | 字节原样存盘，模型用**文件工具**按只读路径读 |
| 写入通道 | `submitTurn` 的 `content` 内容块数组（**我们一直透传**） | `fileUploads/upload`（typert remote）+ 保存路径（**平台未接通**） |

**0.10.0 落地的四层改动**（零依赖、无猜测，全对着官方契约）：

1. **`app/platform/attachment/content.mjs`（新，纯函数）**：`sniffImageMediaType()` 按**文件魔数**判类型
   —— PNG 八字节签名 / JPEG `FF D8 FF` / GIF `47 49 46 38` + `'7'|'9'` / WebP 的 `RIFF` 与 `WEBP` **两段都判**
   （只判 `RIFF` 会把 `.wav`/`.avi` 认成图）；认不出返回 `''`，**绝不猜**。
   `toImagePart()` 对非白名单 `mediaType` **抛错**（硬约束）—— 因为上游准入会**校验字节与声明类型是否相符**，
   不符则**整条消息失败**（连文本一起不发）。
2. **`kernel.mjs`**：`composeWithAttachments()` 重写为「嗅探 → 能力闸 → 预算闸 → 组块」，
   返回 `{content, images, injected, sent, skipped}`；两条回合路由的读体上限从默认 **256KB** 放宽到 **16MB**
   （图片 base64 膨胀 4/3，这是**前置硬改动**，不改则大图必然 413）。
   预算不等式钉死在注释里：`IMAGE_TOTAL_MAX(10MB) × 4/3 ≈ 13.3MB + INJECT_MAX_BYTES(96KB) ≈ 13.4MB < TURN_BODY_MAX(16MB)` ✓。
   **刻意不另设"单张图片上限"**（它等于上传上限 `ATTACH_MAX_BYTES`，设了永远不触发 = 死代码 = 假防线）。
3. **能力三态**：垫片段声明 `SUPPORTS_IMAGE_ATTACHMENTS` → provider 用 **getter** 暴露
   `imageAttachments`（`true` / `false` / `null`，`null` 保守按不支持）—— 用 getter 而非快照，因为垫片是**异步解析**的；
   并加**启动预热** `ensureCompat()`，避免"第一次发图正好撞上未解析"。
4. **第二条跨端契约**：服务端 `describeImages()` 输出「本轮随附 N 张图片…」↔ 前端 `WB_IMAGES_RE` 从中回放数字，
   与既有的 `ATTACH_INJECT_BEGIN` ↔ `WB_ATTACH_MARKER` 一样，由 `test-frontend` 的**契约对账用例**提取两侧常量后比对钉住。
   图片数**从落库原文里读**，不另存字段（否则会出现"字段说 2 张、正文说 3 张"两个真相）。

**这一轮的教训（比改动本身更重要）**：**只看契约的一半就下结论，会把"没找到"写成"不存在"。**
把 `readAttachment`（"读"）当成附件能力的全部，于是漏掉了 `submitTurn` 里一直在的写入通道 ——
而且这条错结论**在 4 份文档里活了整整一个版本**（0.9.0），直到用户一句"原生 dsh 不是支持附件上传吗"才被戳破。
**纪律**：断言"平台**没有**某能力"之前，必须先把契约**正向找一遍**（有没有名字不像、但语义是的入口）。

### 3.7 前端 `PLANNED` / 文档中的历史陈述　【低危但清单要清】

`assessment-0.6.0.md` 里多处是 0.6.0 时点快照（已加脚注说明，可接受）。
但每次交付后要确认**没有新的"承诺了没做"**写进 README/roadmap —— 0.7.0 已核对一遍。

## 4. ➕ 建议**新增**的能力（真正缺、且有企业价值）

### 4.1 ✅ 已施工（0.8.0）· 定时任务底座（**建议最高优先级**）　Tier 1

**为什么是它**：3.1 审批超时、3.3 审计归档与锚定、4.2 告警、5.x 定期备份/探活巡检，
**全部依赖"有个东西能按时间跑"**。现在 `setInterval` 只用在限流清扫与流心跳（基础设施），没有业务调度。
没有这个底座，上面每一项都要各写一套定时逻辑。

**怎么做（零依赖）**：`app/platform/schedule/` ——
表 `scheduled_jobs`（迁移 0009）+ 单进程 `setInterval(tick, 30s)`（**不是 cron 解析器**，
只认 `interval` 与 `dailyAt` 两种）+ 一张调度页（列出任务/上次执行/下次执行/执行结果）+ 审计入链。
**诚实边界**：单进程 → 进程不跑任务就不跑；不给"高可用调度"的假承诺。

### 4.2 ✅ 已施工（0.8.0）· 出站通知 / 告警（Webhook）　Tier 1

**为什么**：现在**没有任何主动告知能力**。审批待办积压、配额被拦、备份失败、模型探活失败 —— 全靠人主动去页面看。
企业运维的基本要求是"异常主动找上门"。

**怎么做**：`app/platform/notify/` —— 表 `notify_channels`（id/tenant/name/kind/url_cipher/enabled/events）+
事件白名单（`quota.blocked` / `approval.pending` / `backup.failed` / `model.probe.failed` / `audit.anchor`）+
`fetch` POST JSON（零依赖，Node 18+ 自带）+ 失败重试退避 + 每次投递入审计。
**边界**：出站 URL 只允许 http/https，禁止私网地址穿透（SSRF 基本防护）；密钥走 `credentials` 加密表。

### 4.3 ✅ 已施工（0.8.0）· `/metrics`（Prometheus 文本格式）　Tier 1

**为什么**：企业一定有自己的监控栈（Prometheus/Grafana/Zabbix）。没有指标端点，平台在监控里就是黑盒。
**怎么做**：`GET /api/system/metrics`（`text/plain; version=0.0.4`）——
暴露 `sti_http_requests_total`、`sti_http_request_duration_ms`、`sti_turns_total`、`sti_tokens_total`、
`sti_quota_blocked_total`、`sti_active_turns`、`sti_audit_chain_length`、`sti_db_size_bytes`、`sti_uptime_seconds`。
**零依赖**：就是一个计数器字典 + 文本渲染。**注意**：`/metrics` 的鉴权策略要明确（建议单独 token 或限本机）。

### 4.4 成本核算：token → 金额　Tier 2

**为什么**：企业管的是"钱"，不是"token"。现在只有 token 数，财务看不懂。
**怎么做**：`model_providers` 加两列（`price_input_per_mtok` / `price_output_per_mtok`，迁移增量）+
用量页按 `租户 × provider × 模型 × 周期` 出金额（**按调用当时登记的单价快照计算**，改单价不影响历史）；
配额新增 `cost` 指标（真·事前拦截做不到精确，但可按"已用量 ≥ 上限"做软闸，与 token 同理）。
**诚实边界**：单价由管理员手填，平台**不内置任何厂商价目表**（那会变成需要维护的数据源）。

### 4.5 OpenAPI 3.0 导出　Tier 2

**为什么**：`/api/system/routes` 已经有全部路由元数据，**导出 OpenAPI 几乎是白送的**；
企业对接、生成 SDK、API 文档站都靠它。
**怎么做**：`GET /api/system/openapi.json` —— 遍历路由表 → `paths` + 手写 `components.schemas`（只写公共 Error/分页形状）。
**收益/成本比**：极高。一份文件就能让外部系统接进来。

### 4.6 知识库**库级 ACL**（授权给用户/组）　Tier 2

**为什么**：现在知识库隔离只到**租户**。一个租户内，"财务的库"和"研发的库"对所有成员都可见。
企业多部门场景下这是刚需。
**怎么做**：复用**能力分发的三级可见性模型**（`capability_bindings` 那套 allow/deny + subject user/group/tenant），
在 `knowledge_bases` 上挂同样的绑定。**不要新造一套权限模型** —— 直接复用是这里的关键。

### 4.7 定期备份 + 保留策略　Tier 2

**为什么**：备份现在只能手动点。企业要求"每天自动备一份、留 30 天"。
**怎么做**：依赖 4.1 定时任务底座 + 复用 `operation` 现有快照能力 + 保留 N 份滚动删除（**删备份要有审计 + 告警**）。

### 4.8 服务账号（机器主体）　Tier 3

**为什么**：CI/CD、外部系统调用平台时，用一个"人"的 API Key 在治理上是错的（离职就断）。
**怎么做**：`users` 加 `kind`（`human` | `service`），服务账号不能登录、只能持 API Key、可单独设配额与角色。

### 4.9 数据主体权利（合规导出 / 删除）　Tier 3

**为什么**：个保法/GDPR 要求"可导出、可删除某人的数据"。
**怎么做**：`GET /api/identity/users/:id/export`（打包该用户的会话/审计/产物，脱敏他人数据）+
`POST /api/identity/users/:id/erase`（**软删 + 匿名化审计留痕**，不物理删审计 —— 这是合规与审计的必然冲突，要写在文档里）。

### 4.10 rerank / 联网搜索　Tier 3

- **rerank**：检索质量提升项。现在"未实装"是诚实的；一旦有真实 rerank 模型（模型中心已能登记），
  接上即可 —— **建议等有真实模型再动，别先搭空壳**。
- **联网搜索**：企业很想要，但它需要外部 provider + 出网策略 + 结果落审计。**建议做成 Skill**（能力分发层），不写进平台。

## 5. 🚫 **不建议**新增的能力（明确不做 + 为什么）

> 这一节比上一节更重要。**每一项都能举出"别的产品有"，但本项目加了就是错。**

### 5.1 多容器编排 / Kubernetes / 多实例 HA / 换掉 SQLite
**为什么不做**：这是**架构级承诺**（`architecture.md §10` 明写）。换库 = 丢掉"双击即用"，
= 引入依赖管理，= 交付形态从"一个 zip"变成"一套运维体系"。**这会摧毁本项目最大的卖点。**
**真需要横向扩展时**：SQLite 换 Postgres 是一条**已在 `db.mjs` 预留**的路（驱动抽象），
但这应该是**另一个产品线**的决定，不是 harness 1.x 的事。

### 5.2 Python / Vue / MongoDB / Redis / Weaviate
**为什么不做**：零依赖是红线。任何一个引入都会带来"装环境"这一步，进而毁掉"双击即用"。
本项目已经用 Node 内置能力等价实现了它们的职责（SQLite 代 Mongo、内存/DB 代 Redis、暴力向量代 Weaviate）。

### 5.3 fork 或 patch DSH 上游源码
**为什么不做**：DSH 是快速迭代的上游，**契约隔离**（`app/kernel/dsh-provider/` 单目录收口）是应对它变更的唯一防线。
一旦 fork，就要背合并上游变更的债，`audit-layering` 的隔离保证也失效。

### 5.4 内容生成生产线（docx / pptx / xlsx / pdf / 翻译）
**为什么不做**：这是 **MOVO 的赛道**，不是平台该干的事。
平台该做的是"**让一个 Skill 能安全地跑起来并留下审计**"，而不是自己内置一套 Office 排版引擎。
**正确做法**：把它做成**一个 Skill**（`capability` 层已支持 ZIP 安装、启停、三级可见性）。
> 关键判断：**"平台能力"与"Skill 能力"的边界** = 前者是"所有智能体都要的横切面"（身份/权限/审计/配额/模型/知识），
> 后者是"某些任务才要的纵切面"（生成 PPT、查天气、跑爬虫）。**内容生成明显是后者。**

### 5.5 多模态生成（图片 / 视频 / 3D）
**为什么不做**：同上 —— 是**能力**不是**治理**。平台提供"模型中心 + 工具网关 + 审计"，
具体调哪个文生图服务，应该是 Skill/工具的职责。

### 5.6 自研 Agent 工作流编排引擎（DAG）
**为什么不做**：这是最容易"看起来必须做"的陷阱。企业确实常要编排，但：
① DSH 上游若已提供多会话/子智能体，平台自造一套就是**再造一个运行时**，与"契约优先、DSH 只是 provider"直接冲突；
② 真要做，也应该用**现有会话/回合 API 组合成一个 Skill**，而不是在内核里加新引擎。
**结论**：**先不造**。等上游明确不提供、且客户明确要求时，再以 Skill 形态做。

### 5.7 Skill 市场 / 中央 Hub
**为什么不做**：市场需要有**中心服务 + 信任分发 + 审核机制**，与"单机零依赖"根本冲突。
**已有替代**：**脱敏导出 + 幂等导入**已经能完成"在另一套部署里复现能力清单"这件事，够了。
真要做分发，用"共享网盘放 zip"就够了，不需要平台承担中心服务角色。

### 5.8 模型微调 / 训练 / 评测平台（重型）
**为什么不做**：完全不同的产品。轻量的 **Eval 评测台**（数据集 + 用例 + 批量跑）倒是零依赖可做，**列为 Tier 3 可选**，
但"训练/微调"请直接排除。

### 5.9 向量 ANN 索引（**现在**不做）
**为什么不做**：暴力扫描实测 10 万 chunk P95 1.2 s，**当前规模完全够用**。
过早引入 ANN = 引入索引构建/持久化/召回率调参的复杂度，而收益在 20 万以下基本看不见。
**已经在 `knowledge/search.mjs` 预留 `VectorIndex` 抽象** —— 到规模了再换，不改调用方。

### 5.10 i18n（**现在**不做）
**为什么不做**：目标客户是中文内网环境。加 i18n = 每个文案抽 key + 双语维护，
**纯成本、零当前收益**。真有多语言需求时再抽，届时改动是机械的。

### 5.11 对象存储 / KMS / Vault（**现在**不做）
**为什么不做**：本机 FS + AES-256-GCM + `data/.secret`（0600）在当前"单机内网"模型下是自洽的。
引入 S3/Vault 会带来新依赖与新故障面。**留抽象即可**（`architecture.md` 已写"超出后走适配器"）。

### 5.12 浏览器 Agent / Code Agent 本地执行
**为什么不做**：需要本地终端与桌面会话，**架构明确不做**（`architecture.md §10.4`）。这是 MOVO 桌面端的职责。

### 5.13 计费与商业套餐
**为什么不做**：明确不做。本项目是**生产与治理平台**，不是 SaaS 计费系统。
（注：4.4 的"成本核算"是**给管理员看的内控口径**，不是"向客户收费"——两者别混。）

### 5.14 自研 WebSocket 双工 / 自研前端框架
**为什么不做**：回合流式用 **POST + NDJSON 分块**已实测首字 237 ms（`roadmap.md` P0-C），
`EventSource` 只支持 GET（提交回合必须 POST），WS 双工在本场景用不上。
前端用原生 JS + hash 路由已支撑 20 页，引入框架 = 引入构建步骤 = 破坏"零构建"。**两条都没有技术理由。**

## 6. 最终建议

### 6.1 分场景判断

| 你的目标 | 建议 |
|---|---|
| **交付给客户试用（内网）** | **现在就够了。** 0.7.0 已是完整可用的平台。只需补 3.1（审批超时）+ 3.3（审计保留）这两条"合规硬项"再出门。 |
| **成为企业正式生产系统** | 按 §6.2 做 **Tier 1 三件套**（定时任务 / 通知告警 / metrics）+ §3 的完善项。**这是从"能用"到"可运维"的必经之路。** |
| **做行业标杆 / 对外开卖** | 再叠加 Tier 2（成本核算 / OpenAPI / 库级 ACL / 定期备份）+ SSO（需真实客户环境驱动）。 |
| **想快速加很多功能** | ⚠️ **这是最危险的方向。** 见 §5 —— 加错的东西比不加更伤。 |

### 6.2 建议的施工顺序（依赖优先，每项都带回归）

```
第 1 步（底座，收益最广）
  4.1 定时任务底座  ──► 解锁后面所有"按时间跑"的能力
  4.2 通知/告警出站 ──► 治理闭环的"最后一公里"
  4.3 /metrics       ──► 企业监控接入
                    └── 这三项做完，平台从"能用"变"可运维"

第 2 步（合规与闭环，硬项）
  3.1 审批超时（消灭 expired 死状态）
  3.3 审计保留 + 归档 + 链尾锚定
  3.2 配额 concurrent 真闸
  3.5 知识重试 + 重新向量化（模型中心能换模型后，这条从理论变现实）

第 3 步（集成与体验）
  4.5 OpenAPI 导出   ── 白送的对接能力            ✅ 0.9.0
  4.4 成本核算        ── 企业内控口径              ✅ 0.9.0
  3.4 CSP 去 unsafe-inline                        ✅ 0.9.0
  3.6 工作台最后一公里（停止/重生成/附件/搜索）    ✅ 0.9.0

第 4 步（按客户需求触发，不要提前做）
  4.6 库级 ACL · 4.7 定期备份 · 4.8 服务账号 · 4.9 数据主体权利 · SSO/OIDC
```

### 6.3 最小可信交付路径（一句话版）

> **补完 3.1 + 3.3（合规硬项）即可交付试用；补完 Tier 1 三件套（4.1 + 4.2 + 4.3）即可作为企业正式系统运行；
> 其余全部按客户需求触发 —— 而 §5 的十四项，除非战略定位改变，一项都不要加。**

### 6.4 一句话总结

**这个平台的护城河是"契约纪律 + 治理深度 + 零依赖单进程"，不是"功能数量"。**
接下来的每一次功能决策，标准问题应该是：
**"这件事是平台级的横切能力，还是某个任务的纵切能力？"**
—— 横切的进平台代码，纵切的一律做成 Skill。守住这条线，它就不会变成另一个 MOVO。
