## 0. 三句话结论

1. **治理层是真本事，不是脚手架。** 身份/权限/审计哈希链/配额/审批门/能力分发/知识混合检索七块，设计自洽、有回归钉住、边界如实标注。这部分可以直接进企业环境。

2. **但"Agent 生产平台"的核心链路未打通 —— 这是最大风险。** 真实 DSH 下「建会话 / 发回合 / 拉历史 / 选模型 / 应答审批」**全部默认返回 501**（`compat/0.1.5-rc.2.mjs` 里 11 个写路径方法 `verified:false`，`callMapped` 直接拒调用）。而且这些 `verified` 标记**来自对 dsh-console 源码的静态核查，不是对运行中 DSH 的动态验证**（compat 文件第 20 行自述）。**当前 3090 服务实际跑在 `kernelMode: mock`。** 换句话说：**现在它是一个"治理后台"，还不是一个"能用的智能体平台"。**

3. **前端只有管理后台，没有用户工作台。** 无流式渲染、无工具卡片、无对话内联审批卡；「会话与回合」页实际是一个单行文本框 + 事件平铺。布局层面与"生产平台"定位不符。

> ✅ **好消息（改变结论的那条）**：本机 **3080 端口有一台真实 DSH 在跑**（HTTP 401 需鉴权），`dsh` CLI 在位，`dsh-console/dsh-config.json` 里也有可用令牌。所以第 2 条**现在就能修**，不是"等客户环境"。这让 P0 从"阻断"变成"可执行"。

## 2. P0 硬伤（已逐条实证）

### P0-1　真实内核对话链路 501（阻断落地）

`app/kernel/dsh-provider/compat/0.1.5-rc.2.mjs` 逐条核实结果：

| 状态 | 方法 |
|---|---|
| ✅ `verified:true`（可调用） | `modelCatalog`(=llm/listConfigurableProviders)、`listSkills`(=agents/skills)、`listPendingApprovals`、`listArtifacts`、`readAttachment` |
| ❌ `verified:false`（**默认 501**） | `createSession`、`listSessions`、`renameSession`、`forkSession`、`cancelSession`、`disposeSession`、`submitTurn`、`cancelTurn`、`selectModel`、`respondApproval`、`sessionHistory` |

`index.mjs:32-41` 的 `callMapped` 对未核实方法抛 `unverified_upstream_method` 501，除非显式设 `STI_ALLOW_UNVERIFIED=1`。

**后果**：external 模式下，「建会话、发一轮对话、拉事件历史、切模型、应答审批」**全部不可用**。README 与前端却把它们当已交付能力展示。这是当前"宣称 vs 实装"的最大落差。

**为什么当时没发现**：项目从 DSH 未接入的假设出发，`verified` 只能靠静态核查 dsh-console 源码推断；而回归全在 mock 下跑，永远不会暴露这条。

#### ✅ P0-A 完成记录（2026-10-01）

**做了什么**：新增 `tools/verify-upstream.mjs`（对运行中的 DSH 逐条实测）+ 重写垫片为
`compat/0.2.0-rc.2.mjs`（动态核实）+ `compat/index.mjs`（按版本选垫片）+ `sessionlog.mjs`
（历史/增量读上游会话日志）+ 新增 `tools/test-external.mjs`（外部模式端到端回归）。

**实测发现（静态核查想不到的三件事）**：

1. **上游实际版本是 `0.2.0-rc.2`**，而 `config.mjs` 此前刻意把它排除在验证矩阵之外
   （理由"没跑过就不许标已验证"）。现在真的跑过了，已正式纳入矩阵。
2. **方法名错得比预想的多**：0.1.5 垫片里 9 个方法名在上游**根本不存在** ——
   `session/submit`（实为 `session/prompt`）、`session/setModel`（实为 `session/selectModel`）、
   `agents/skills`（实为 `skills/list`）、`session/interrupt`/`session/dispose`/`session/history`、
   `approval/request`/`approval/respond`（审批走 `$events` 事件流，非 RPC）、
   `deliverables/presented`（这是**事件类型**不是端点）。
3. **参数形状错**：上游几乎全部要求 `{request:{…}}` 信封；`session/prompt` 的 `content`
   必须是**内容块数组** `[{type:'text',text}]`（传字符串报的错完全没提 content）；
   `mode` 只接受 `queue`/`steer`（传 `chat` 同样只报 "boundary validation"）。
   这些报错信息都极不友好，因此在垫片里做了归一，不指望每个调用方都记得。

**上游架构澄清**：DSH 是**两层**接口 ——
RPC（HTTP，建会话/发回合/改名/选模型…）与 **Stream（WebSocket，`session/follow` 事件流、
`session/control` 投影、`$events` 审批 waterfall）**。审批、工具清单、产物**不走 RPC**。
这解释了为什么 0.6.0 里 `listTools`/`listPendingApprovals`/`listArtifacts` 恒空 ——
它们被映射到了不存在的方法名。现在改为如实标注 `streamSourced`。

**历史从哪来**：上游没有 `session/history` 端点，`session/follow` 是 WebSocket。
P0-A 选择读**上游自己的 append-only 会话日志**
（`<DSH_HOME>/sessions/<cwd 派生键>/<sessionId>/session.v4.jsonl.zstd`，拼接 zstd 帧容器）。
这是上游写的真数据，不是我们伪造的第二份 —— 符合"不落第二份数据"的**原意**。

**验收证据**：`node tools/test-external.mjs` → **12 用例全过**，其中核心一条实测输出：

```
✓ 发一轮对话并收集到真实事件（这是"能不能用"的判据）
    事件 17 条，类型：lifecycle turn-start message turn-end
```

即：**平台接上真实 DSH 后，"建会话 → 发一轮 → 拿回事件 → 落库 → 用量采集"整条链路是通的。**
mock 侧 260 用例同时保持全绿（两条路径都回归，见 `tools/test-external.mjs` 头注释）。

**顺带修掉的**：`versionGate` 的警告文案此前还在说"尚未交付 fixtures 回归"（M0 就交付了），
且 `test-core` 拿 `0.2.0-rc.2` 当"越界版本"样本 —— 版本一入矩阵该用例就失败。
两者都已更正，并把用例改成**构造**必然越界的版本，不再写死字面量。

### P0-2　前端无对话工作台

- `pageSessions()` 是一个 `<textarea>` + 「提交」按钮，提交后把整轮事件 `<div class="ev">` 平铺。
- 全文件 grep **无 `EventSource` / `WebSocket` / `stream`**。
- 无工具卡片（tool 事件只是 `name + JSON` 文本）、无审批内联卡（审批在独立管理页）。
- 服务端 `ws-bridge`（字节管道）只桥到上游 DSH，前端**根本没用它**。

### P0-3　回合非流式

`kernel.mjs` 的 `collectTurn` **同步收集整轮**再返回 `events[]`，超时 20s。真实 agent 一轮可能跑几分钟，且用户看到的是"转圈 → 一次性全出来"。企业平台的体验基线是**逐字流式**。

| P0-A | **对着运行中的 DSH 逐方法核实**：用 3080 的实例把 11 个写方法跑通，把 `verified` 置 `true`，并录制为 fixtures | external 模式下「建会话→发回合→拉历史」端到端可用；`record-fixtures.mjs` 产出真样本 |
| P0-B | **前端对话工作台**：新增独立"工作台"壳（左会话列表 / 中对话流 / 右上下文与工具），与后台并存 | 最终用户能像用 ChatGPT 一样提问；后台仍归管理员 |
| P0-C | **流式回合**：服务端接 WS/SSE 增量推事件，前端逐字渲染 + 工具卡 + 内联审批卡 | 首字延迟可见、工具调用过程可见、审批就地操作 |
| P0-D | 顺手修 §4 的 1/2/3/4/5/6 号小缺陷 | 死配置接线、补 tenant_id 列、前端陈述更正、补备份页、listTools 接内核 |

> 风险提示：P0-A 需要真实 DSH 的 CALL 权限与一次完整会话跑通；若 DSH 侧方法名与静态推断不符，需改 compat 映射（这正是 compat 文件存在的意义）。P0-B/C 是纯前端 + transport 增量，不动治理层。

### 方案 P1 · 企业级补齐（按"平台必备"排序）

1. **模型中心**：平台侧多 provider 配置 + 连通性测试 + 默认模型/降级链（现在只能透传上游）。
2. **安全响应头 + 会话 TTL 策略**：CSP/HSTS/`X-Frame-Options`，把 §4-7 补掉。
3. **审计保留与链尾锚定**：保留期策略 + 每日链尾 hash 外发/落只读文件，解决"整表重写"边界（M5 承诺过但未做）。
4. **配额并发闸**：`concurrent` 目前是 `unknownMetric`，补真闸。
5. **定时任务**：单进程内 setInterval 调度 + 表 + 页（MOVO 有，harness 无）。
6. **会话分享**：同租户只读分享链接（MOVO 有）。
7. **通知/告警**：配额超限、审批待办、备份失败。
8. **group 实体表**：补齐 `role_bindings` 的 group 语义。

### 方案 P2 · 增强（可选，部分与设计原则冲突）

| 项 | 说明 | 与原则冲突？ |
|---|---|---|
| 可观测性 `/metrics` | Prometheus 文本格式，零依赖可做 | 否 |
| Eval 评测台 | 数据集 + 用例 + 批量回归 | 否 |
| Webhook 出站订阅 | 事件推送 | 否 |
| OpenAPI 导出 + 极简 SDK | 从路由表生成 | 否 |
| i18n | 界面多语言 | 否 |
| 对象存储适配器 | S3/MinIO（现本机 FS） | 否，需破例引入签名逻辑 |
| 联网搜索 | 需外部 provider | 需网络+密钥 |
| 内容生成（docx/pptx/xlsx） | MOVO 强项 | **与"平台 vs 生产线"定位冲突** |
| SSO / LDAP | 企业常要求 | 需目标客户环境 |
| 浏览器 / Code Agent | 需本地终端 | **架构明确不做** |
| HA / 多实例 / K8s | 需换数据库驱动 | **架构明确不做** |

## 6. 建议

- **如果目标是"能交付给客户用"**：P0 是分水岭。不做 P0，交付的是一个治理后台 + 一个跑不通的对话接口；做完 P0，它才真的叫"智能体生产平台"。
- **如果目标是"内部治理工具"**：那 §3 的治理对照已经够看，P0 可降级，优先做 §4 的缺陷修复 + P1-2 安全项。
- **不建议现在动 P2 里的"内容生产线"** —— 那是 MOVO 的赛道，harness 的差异化在"零依赖 + 契约纪律 + 治理深度"，铺内容生成会稀释定位且违背 §10「不做的事」。

**最小可信交付路径建议**：P0-A（打通内核） → P0-B/C（工作台+流式） → §4 缺陷清理 → P1-2（安全头） → P1-1（模型中心）。
